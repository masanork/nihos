# C6 time response loss: Tab5 qualification

On 2026-11-01, a single Tab5 ran an explicitly instrumented native P4 image
with `NIHOS_C6_TIME_OFFLOAD=1`, `NIHOS_C6_TIME_FAULT_TEST=1` and IPv6,
XY workspace, normal storage, camera ID, and SQLD disabled. P4 source commit
`3e509b32d4bec67571bb2940888c1eaeadd3afd1` produced app SHA-256
`23973fdb2379c6d5e1e8db847052ce2d7561e0f19ebcbef10a364e88b1724f0d`.
The C6 application was not rewritten.

The P4 intentionally discarded two frames (the acknowledgement and result)
for the first C6 time request and shortened that request's deadline to three
seconds. It observed one time-request timeout, then issued more requests. On
attempt 29 the P4 accepted a synchronized result and applied it to the RTC.
Its matching sample was 2026-11-01 12:38:44 UTC. Subsequent valid RTC reads
advanced by six seconds. Wi-Fi reported one acquisition, zero reconnects and
zero network failures with the same IPv4 address; BLE remained ready with zero
reported timeouts. Display frames and both core ticks advanced between the
fault and recovery.

The [redacted machine-checked summary](evidence/2026-11-01-c6-time-loss.json)
contains the capture hash and counters, not the address or credentials. The
checker and negative tests are `tools/c6_time_fault_evidence.py` and
`tools/c6_time_fault_evidence_test.py`. Before installing the candidate all
16 MiB of P4 flash were backed up and verified; afterward the original spans
were restored and the entire flash matched that backup. The RTC was left set.

This is one response-loss injection, not a natural AP outage, C6 reboot,
malformed/partial transport, repeated long soak, or cold-power RTC retention
test. The test changes the timeout to three seconds; the ordinary deadline is
unchanged. The next 28 polls include unsynchronized C6 time results and are
not evidence that every NTP packet succeeded or failed. No iroh/QUIC result or
CPU-saving measurement is implied.

## Repeat after rebasing on nihos main

After rebasing on main `db4d851cc46e972a9b181785edbc188267a08692`, the
instrumented P4 candidate built from commit
`6cf8074dc3c7940216ca59bf2d2edf127b35ba3b` had SHA-256
`eabaecf7bb85b91cc301322ebf78bafa07ab012febb959f4bd2aa98bdb10f351`.
Its bytes differed from the previous candidate only at the embedded ELF hash
(offset `0xb0`, 32 bytes), the image checksum and validation hash at the end;
the remaining bytes matched. Both images passed their native image audits.

On Tab5, the one-shot injection dropped two time response frames, one timeout
was recorded, and a later synchronized time updated the RTC. Its readback
advanced 10 seconds; there were zero Wi-Fi reconnects, BLE remained ready, and
UI/core counters advanced. Full P4 flash restoration was verified. The
[redacted checked summary](evidence/2026-11-01-c6-time-loss-rebased.json)
records the counters. This candidate preceded the report and UI asset-manifest
refresh commits; neither is an assertion of an exact-final-head device run.

## Repeat on main after WAMR integration

A later candidate built on nihos main `20110ca721c09d2a7f287439456c640bb75ea210`
at source commit `46afe7b85c4714da4f5fff1d832e3cc41e8c85c6` had P4 app
SHA-256 `cbb970b5009151488b390bf1618dafc4e7bcefb871b5f54b8b0dd2e65dc9fa37`.
It used the same opt-in fault-test profile. The native audit reported 49,344
bytes of primary heap against a 49,152-byte floor; this is a 192-byte margin
for this profile, not a full-product memory qualification.

The Tab5 run dropped two time-response frames, recorded one timeout, and
successfully updated the RTC after retry. The validated RTC advanced by four
seconds, the Wi-Fi reconnect count remained zero, BLE remained ready, and UI
and both core counters advanced. The full P4 flash was restored and verified.
The [redacted checked summary](evidence/2026-11-01-c6-time-loss-main119.json)
records this run. Later report-only commits do not constitute a new physical
candidate; the ID and image hash above identify the actual tested code.
