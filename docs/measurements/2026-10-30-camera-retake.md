# Camera retake prototype (2026-10-30)

The shell `camera` command now takes another snapshot after dismissal. The prototype retains the same pinned PSRAM frame allocation and started DMA channel lease for the whole boot. It reconfigures the sensor, CSI/ISP and channel for each new capture, without returning either resource to an allocator or another owner. A successful prior completion, clean cleanup, matching live token, no latched common fault, disabled channel, empty FIFO and masked/disabled DMA notifications are required. Faults reject retake for that boot. This is an experimental restart path, not a general DMA retirement or release implementation.

An initial retake was rejected because the code read the bridge enable register after its module clock had been gated. The corrected check avoids that register while gated; CSI preparation subsequently restores the clock and verifies the bridge is disabled before DMA starts. Host register replay covers this distinction, active DMA, pending events and interrupt configuration, while preserving display channel state.

One physical Tab5 ESP32-P4 rev 1.3 run (MAC `e8:f6:0a:e2:e8:9c`) completed three captures and three serial Escape returns to shell. The captured sample hashes differed on all three captures and all three CPU framebuffer comparisons reported zero mismatches. Frozen app SHA-256 `81c2ed56a2264e8a4a4737ed5b841e8fb358f4cc93c7c993c9c5358997a5ad56`; ELF SHA-256 `bbc5660563de5fe4eaa0a3a4c0161edf8977f062fc5a222656b877d1a73a6f33`. The display frame counts at presentation were 1040, 1552 and 2051; these are progress observations, not a video throughput qualification. The full receipt is retained in `/private/tmp/nihos-camera-retake-fixed-20261030/result.json`.

Optical appearance and scene identity have not been independently checked. Three completed cycles do not qualify indefinite reuse, abort recovery, video or normal network/storage coexistence. This candidate's transaction verified its exact bytes after capture, restored both prior erase spans with full readback and issued a hard reset; no restored-system boot was captured.

Earlier attempts in `/private/tmp/nihos-camera-retake-20261030` and `/private/tmp/nihos-camera-retake-reason-20261030` rejected retake and restored the prior spans. Their capture exceptions skipped post-capture candidate verification. A subsequent faster candidate in `/private/tmp/nihos-camera-retake-fast-20261030` failed the raw preview-log completeness checker and likewise restored; no complete scene log was saved by that checker exception. It is not counted as a successful qualification.

## Faster interactive candidate

Cache preparation now batches at most 16 KiB per foreground poll, and ordinary shell captures suppress raw pixel serial output. The two internal sample passes and CPU framebuffer comparison are retained. An asynchronous snapshot record starts on a new line so that a preceding shell prompt cannot hide it from the checker. The preceding trial `/private/tmp/nihos-camera-retake-ui2-20261030` timed out because the snapshot record followed `nihos>` on the same line; that log shows completion of the first snapshot, but not three captures. It restored both spans and is not counted as a successful qualification.

The final candidate completed three new captures, three zero-mismatch framebuffer comparisons and three Escape returns to shell. All three sample hashes differed. Host-observed time from sending `camera` to receiving the snapshot result was 3,265 ms initially, then 2,441 ms and 2,332 ms. These measurements include serial input/output and host observation; they are not a video frame rate or a hard latency bound. The final checker requires sequential snapshot numbers, one accepted request per capture, successful presentation with zero pixel mismatches, increasing display frame counts and a shell repaint after each dismissal. Raw pixel log completeness is no longer part of the ordinary-shell checker; the firmware presentation path still requires both internal sampled passes to agree.
