# Camera reset recovery prototype (2026-10-30)

The camera-enabled build now checks CSI clock/ownership flags before PSRAM allocation, display initialization and CPU1 scheduling. Clear flags permit normal boot. Nonzero flags after a USB chip reset (ROM reasons 22/23) invoke an LP-WDT full-chip reset using the ESP32-P4 sequence also used by esptool. Nonzero flags after other reset causes, including the recovery watchdog reset, fail rather than request another firmware reset. A bounded fallback reports a reset timeout if the watchdog does not fire. Normal builds without camera support do not run this path.

This handles more than CSI register configuration: a failed trial with CSI flags 7 also failed in the sensor-clock preparation stage, with cleanup failure. Recovering just the receiver was insufficient. The attempted receiver-only recovery and an experimental stale-register injector were removed; the final implementation requests a whole-chip reset before allocation instead of adopting partly initialized peripherals.

## Observations and qualification boundary

USB resets did not consistently leave the same state in these experiments. In `/private/tmp/nihos-camera-reset-recovery-20261030`, boot reported flags 0 both initially and after resetting with CSI prepared; the complete live-preview workflow passed, but a checker incorrectly required retained flags and rejected the transaction. In `/private/tmp/nihos-camera-csi-recovery-20261030`, the post-reset boot reported flags 7. In `/private/tmp/nihos-camera-csi-recovery-final-20261030`, initial boot reported flags 7 and sensor-clock preparation failed. These incomplete transactions restored the previous spans but skipped post-capture candidate verification because capture raised an exception. They support the state distinction, not final candidate qualification. The earlier explanation that USB reset always clears CSI was too broad.

The final reset policy is host tested for clear flags, both USB reset reasons, and refusal to reset-loop for watchdog, power-on, software and other reasons. Normal USB boot and live operation also ran in `/private/tmp/nihos-camera-usb-recovery-final-20261030`; its checker rejected the absence of a naturally triggered recovery, so that attempt is not the final identity-matched qualification.

The exact final candidate was physically exercised on Tab5 ESP32-P4 rev 1.3, MAC `e8:f6:0a:e2:e8:9c`, as follows:

1. Boot with a host USB reset, observing flags 0 and reason 23.
2. Use the explicit camera-only `:camera-reset-hold` fixture to retain the configured sensor and CSI at the phase before ISP/DMA start.
3. Use `:camera-recover` to call the same recovery function used at boot. This fixture is admitted only at the held pre-ISP phase with no DMA token and no uncertain DMA. The function observed flags 15 (the three clocks plus this fixture's software ownership bit) and USB reason 23, and invoked the firmware LP-WDT reset sequence.
4. Reopen serial once under the same owner lock and kernel-exclusivity checks, observe a new boot with flags 0, and complete five automatic live updates, visible stop, a manual snapshot, initial-loading stop and a shell `mem` command. All five live hashes differed; all six presented framebuffer comparisons had zero mismatches. Captures 6 and 8 drained without presentation.

This validates the reset decision's hardware path and reset routine through the explicit prepared-CSI fixture. Naturally retained flags triggering the automatic early-boot branch on this exact final candidate were not observed; that entry point shares the tested function and has host-tested policy. The serial reopen produced USB reset reason 23 in the retained boot log, so the raw watchdog reset cause was not captured. This is not a cold power-cycle or active-DMA abort qualification. The cause of the earlier three-update runtime failure remains unestablished; five updates are not a sustained-operation test.
