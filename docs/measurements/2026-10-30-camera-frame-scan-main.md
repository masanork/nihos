# Full-frame stability diagnostic (2026-10-30)

On base `d824feaa8acc66dc16810fc9fa95887f5efc642d` with the uncommitted camera integration, the default-off `:camera-frame-scan` diagnostic captures one frame and scans its 921,600 bytes twice in 900 chunks of 1,024 bytes. It checks per-chunk FNV values and a whole-frame SHA-256, with a 50 ms inter-pass gap. The frame and started DMA channel remain pinned until reset. Each scan step checks the retained frame identity, stopped receive state and shared DMA fault state and invalidates the relevant cache span. Foreground work is batched with a soft time budget; a single chunk is not subject to a hard execution-time bound.

One physical trial on Tab5 ESP32-P4 rev 1.3, MAC `e8:f6:0a:e2:e8:9c`, reported 900 chunks, zero changed chunks and matching SHA-256 values. Both terminal reports describe the same two passes of the same frame, not separate captures. The first and second passes took 1,624,567 and 1,601,178 microseconds respectively, including scheduling. The maximum recorded chunk step was 310 microseconds, the maximum batch was 1,185 microseconds, and 450 batches covered 1,800 steps. Display and CPU counters progressed. These are observations for this run, not hard latency guarantees or a video frame rate.

The frozen app image SHA-256 was `90b2487cfbaec06afd753050118c31f222abb7090373221cf5749b0e6151f9f6` and ELF SHA-256 was `aee5a77d5f2ebd54632a5c0f3b838729ca300ddefee88806a3f6da5a78165398`. The transaction verified the candidate, restored both previously backed-up loader and app erase spans, verified their complete readback, and issued a hard reset. No restored-system boot was captured. The [receipt and image audit](evidence/2026-10-30-camera-frame-scan-main/) contain no image pixels; raw serial and backup files remain outside the repository.

The scan and sampled preview use mutually exclusive scratch storage. A compact loop-based SHA-256 avoids the standard implementation's expanded code exceeding the existing 48 KiB SRAM heap floor. Host tests compared it with the standard implementation across block boundary lengths and a full-frame-sized input. The diagnostic image retains 50,752 bytes between heap bounds, 1,600 bytes above that floor; this is not a measurement of available application memory. An isolated investigation copy temporarily relaxed the linker floor to measure the code size; it was not flashed, and the diagnostic candidate retained the original floor and image audit. Host suite: 828 tests passed; diagnostic and normal native builds passed image audit, with network and normal storage disabled.

Matching digests are evidence of observed stability, not a mathematical proof of byte equality or of DMA/IRQ quiescence. This trial did not establish scene identity, optical or panel correctness, safe DMA/frame reuse, repeated captures, or streaming.
