# Camera in the normal native profile (2026-10-30)

The camera prototype has been integrated onto main base `d43280d`, preserving the newer PMP/task-control work. The previously measured camera work is checkpointed as `f82efeb` and imported onto this base as `be01ba2`. Earlier physical receipts remain measurements of their original candidates, not of this newer base.

The public interactive `sh tools/build-native.sh device` profile now includes camera alongside network, normal storage and the other on-demand devices. `camera` takes a snapshot; `camera-live` updates automatically until a key stops it. The current output remains an 80×45 grayscale sample enlarged to 320×180, with updates on the order of a few seconds. `NIHOS_NATIVE_CAMERA_ID=0` omits camera; explicit USB/PMP and standalone peripheral fixtures retain their existing defaults. Explicit `NIHOS_NATIVE_CAMERA_ID=1` builds retain detailed diagnostics by default; the public camera profile uses `NIHOS_NATIVE_CAMERA_DIAGNOSTICS=0`. Reset/hold and other camera diagnostic commands are rejected in that profile.

## Resource changes

The first combined build overflowed the fixed read-only Flash-table region. Compiling detailed camera telemetry only for diagnostic profiles removed that overflow without extending its mapping. A subsequent build was 22,080 bytes below the existing 48 KiB SRAM heap floor. A separate, non-deployed size-probe ELF with a relaxed assertion measured this shortfall; production builds retain the original assertion.

The preview/scan scratch union is now allocated in pinned PSRAM on first camera use rather than occupying 3,800 bytes of resident SRAM. It is reused for the bootstrap owner's lifetime. Allocation failure rejects a request before starting hardware. The frame and started channel retain their existing boot-lifetime ownership; this is not a resource-release implementation.

Five CPU0 foreground entry points now use the existing mapped Flash device-code region: board polling, device requests, network/device dispatch, UI polling and session key handling. They run with the loader's Flash mapping available. Interrupt handlers, trap paths and cache-off control remain in SRAM/ROM. Image auditing admits only those named functions and the two specific UI generic prefixes in addition to the previous mandatory device allowlist; arbitrary names and malformed generic suffixes remain rejected. The resulting normal image passes audit with 51,776 bytes between heap bounds, 2,624 bytes above the unchanged floor. That span is not measured free application capacity.

## Physical workflow and limits

One exact candidate ran on Tab5 ESP32-P4 rev 1.3, MAC `e8:f6:0a:e2:e8:9c`, with network, normal storage, devices and camera enabled and camera diagnostics disabled. The trial rejected the reset-hold and recovery diagnostic commands, then completed five automatic live updates, serial Escape stop, a manual snapshot, stop during initial loading and a subsequent shell `mem` command. The five live sample hashes differed. All six presented framebuffer comparisons had zero mismatches, and pending captures 6 and 8 were discarded after stop. Network heartbeat frame and both CPU counters advanced across the workflow.

Wi-Fi configuration was disabled, so no AP association or Internet communication is qualified. Normal filesystem service started, attempted a read and reported status 4 (`rejected`) with error -262; this trial does not qualify mounting or SD file reads, nor simultaneous sustained Wi-Fi/SD traffic. Optical appearance, physical keyboard/touch, video and sustained camera operation remain separate gates. The trial started with an identity-checked host watchdog reset; it does not qualify cold power-on or natural activation of the automatic boot recovery branch.
