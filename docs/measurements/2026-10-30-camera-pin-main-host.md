# Camera pinned memory on current integration base: host and build evidence (2026-10-30)

Base `d824feaa8acc66dc16810fc9fa95887f5efc642d` plus uncommitted integration changes. The current task ledger supports pinning only raw whole allocations. Normal free, task-close draining and generation reuse cannot reclaim a pinned allocation; release requires the trusted owner and an identical live token. Closing owners with only pinned entries do not block draining other tasks. Existing extent-group behavior remains intact, and host tests cover a pinned frame and an extent group in the same closing task alongside a second task, plus wrong owners, duplicate pins, stale tokens and failed releases.

A default-off camera fixture adds a 921,600-byte workspace using task-owned pinned PSRAM. `:csi-memory` allocates it, performs bounded 1,024-byte cache writeback/invalidation chunks, erases it, writes back the erasure and releases the pin without starting DMA. This is a diagnostic pre-DMA path, not a safe retirement protocol for a started DMA. Uncertain cache or release failures retain the pin. The workspace and identity/CSI probes reject overlapping requests. Host workspace tests exercise aborts, cache failures, uncertain DMA stop, erase and generation handling; these tests cannot establish real hardware quiescence.

RV32 compile-time `@sizeOf` comparison against the same base gives `Resources(buddy,4,2)` 504 → 568 bytes and `ResourcesWithGroups(buddy,4,2,1,32)` 1,560 → 1,624 bytes. The native heap keeps one ledger per hart, hence this is 64 bytes per hart (128 total) of additional ledger structure in the corresponding configuration. This is a structure-size comparison, not a runtime measurement of all resident memory, fragmentation or application capacity.

Debug host tests, normal and diagnostic native builds and image audits passed. The Tab5 serial port was absent on the attempted physical run; the tool stopped before opening the device and did not write flash. A later, separately recorded [physical trial](2026-10-30-camera-memory-main.md) ran after reconnection with full backup/restore and identity-matched capture. No claim is made here about actual PSRAM DMA capability, cache synchronization, a started transfer, continuous capture or physical-device evidence.
