# Explicit native CPU clock — 2026-10-27

Base `960bb10`, isolated `codex/native-console` worktree. The user expected
CPU 400 MHz and PSRAM 200 MHz. The application already used an independent native
kernel; CPU initialization was missing, leaving the loader's 90 MHz divider.
PSRAM200 x16 DDR had been qualified separately.

The physical unit is ESP32-P4 rev1.3, ST7121, 32 MiB PSRAM, MAC
`e8:f6:0a:e2:e8:9c`. [Espressif's revision comparison](https://documentation.espressif.com/en/PCN202600801_ESP32-P4_Chip_Revision_v3.2_Upgrade_Chip_Revision_v1.3_Demand_Collection_and_EOL_Plan_Description.html)
lists the old rev1.3 profile as CPU 360 MHz / PSRAM 200 MHz and the newer rev3.2
profile as CPU 400 MHz / PSRAM 250 MHz. The pinned ESP-IDFv5.4.4 rev1/2 driver
accepts90/180/360 MHz, and the local MeOS `sdkconfig.tab5` selects 360 MHz.
This implementation targets the normal 360 MHz profile; no 400 MHz qualification
or unsupported PLL retuning is claimed.

## Initialization and ownership

`NIHOS_NATIVE_CPU_MHZ` defaults to 360 for device images and0 for the emulator;
0 is also an explicit loader-clock baseline for devices. Other values,
including 400, are rejected for this rev1/2 native profile.

The new boot-only function runs before PSRAM mapping and CPU1 release, with
IRQs masked. It verifies the silicon family, CPLL source, integer divider
state, and read-only CPLL parameters. Unknown sources/PLLs/fractional states
are rejected before divider writes. No CPU PLL, SPLL, MPLL or voltage retune
is performed. It follows pinned SDK upscaling order APB -> SYS -> MEM -> CPU,
committing each step through a bounded hardware update handshake. Host-model
checks verify every intermediate state stays within supported bus rates.

Fixed ROM ABI calls `ets_update_cpu_frequency` at 0x4fc00044 and
`ets_get_cpu_frequency` at 0x4fc00040 update/read timing calibration. Frequency
is independently sampled against the TG0 XTAL40/40 timer before and after;
the normal live sampler uses dedicated TG1.T0. Scheduler timer rates remain
independent of CPU frequency.

The image audit permits one additional exact boot role,
`cpu_boot.run__func_N`, inside the existing bounded Flash boot page, alongside
PSRAM probe/mapping. Its execution PC is checked in the device log. Ordinary
positive boot strings use fixed 128-byte read-only tables in the existing
diagnostic Flash span; failure text/output remain SRAM-resident. This retains
the 48 KiB SRAM heap minimum, unchanged address regions/permissions and no RTOS
linkage. Final SRAM heap: 49,344 bytes. Mergeable Flash data was rejected during
development; the fixed tables retain the original strict read-only flags.

## Failed attempt and validation

[Initial failed log](2026-10-27-native-cpu360-guard-failed.log) /
[artifact receipt](2026-10-27-native-cpu360-guard-failed.json): the revision
guard initially read the wrong eFuse word at 0x5012d034. It failed with code 6
before measurement or divider changes. The reference is corrected to the
SDK's `EFUSE_RD_MAC_SYS_2_REG`, 0x5012d04c, with a compiled SDK static assertion
and host revision-family tests. The failed attempt is not normal qualification.

209 Zig tests pass in Debug, ReleaseSafe and ReleaseSmall; 143 Python tests
pass, including bounded clock ordering/unsupported-state tests, narrow Flash
boot-role coverage, missing/wrong/late clock records and runtime clock agreement.
The normal console candidate and default device/emulator images pass image
audits. Emulator build success is not physical-clock execution evidence.
ShellCheck, formatting and native core/display evidence checks pass. Runtime
source/data hashes match the retained build manifest.

User optical feedback on the final candidate is pending. MPLL was reused at
400 MHz; fresh cold-power PLL calibration remains a separate observation gate.
