# Camera DMA channel SRAM transfer on the current integration base (2026-10-30)

Base `d824feaa8acc66dc16810fc9fa95887f5efc642d` plus the uncommitted camera integration worktree. The explicit default-off `:camera-dma-test` fixture acquires the camera's shared DW-GDMA channel, marks its generation-specific lease started before programming the hardware, and transfers a 64-byte pattern between dedicated aligned SRAM buffers. Completion requires the DMA done event, disabled channel, empty observed FIFO, no channel/common fault, cache invalidation and matching bytes. The lease and both static buffers remain retained until reset even on reported success; further camera diagnostics are refused once this test begins.

One Tab5 ESP32-P4 rev 1.3 physical trial, MAC `e8:f6:0a:e2:e8:9c`; application SHA-256 `9f1bdf767d0f3877564a21541bc6e598cb537599f5bf52e67a6dde0e7ebcfa82`, ELF SHA-256 `2da6a94afbab0b9695fcf6814649f700dd0d452837755e2d36df738ee535ef33`. [Receipt and image audit](evidence/2026-10-30-camera-dma-sram-main/). After two idle reports, request kind 12 was accepted and two repeated terminal reports gave state 3/result 1. The launcher was ready and the display frame count and both CPU tick counters advanced across the request. These are repeated observations of one transfer.

Host replay of the real diagnostic logic covers successful copy, timeouts, corrupted data, stuck disable, common errors and admission failure; it is not a silicon DMA simulation. Debug host tests and diagnostic native image audit passed. This trial does not exercise camera sensor or CSI, PSRAM destination, actual camera pixels, continuously operating video, physical input, or prove FIFO/IRQ retirement sufficiently to reuse a started channel. The original loader and application erase spans (24,576 and 155,648 bytes) were restored and verified with full readback, then hard-reset; restored-system boot was not captured. Serial logs remain private.
