# Camera live capture: incomplete transfers and bounded soak (2026-10-31)

Two independent normal-profile Tab5 trials each completed 120 seconds of live capture followed by ten stop/restart cycles, a manual snapshot, and an idle-to-cold snapshot. The live segments presented 2,308 and 2,310 images at approximately 19.2 updates/s. The tests exposed and fixed capture termination on a single incomplete frame; incomplete frames are now rejected before publication while capture continues within a bounded recovery policy.

## Failure exposed and recovery policy

The prior continuous-capture image stopped with `reason=0x04000002` before its first displayed image in one trial and after 159 images in another. ESP-IDF v5.4.4's ESP32-P4 revision-1 CSI bridge register definition identifies bit 2 as DISCARD: an incomplete frame was sent. The simultaneous channel event was DMA transfer completion. This was a real firmware failure, not an observer timeout.

The IRQ now rejects that transfer without advancing the frame pool generation or publishing its payload. It acknowledges only the owned bridge's DISCARD bit and rearms the same DMA slot. An existing borrowed or ready valid frame remains protected. At most three consecutive DISCARD-only completed transfers are tolerated; the fourth, DISCARD without DMA completion, any other bridge error, DMA error or controller-common error still stops rearming and follows the pinned failure path. A clean completed frame resets the consecutive count, and the existing five-second progress watchdog remains active. The electrical/timing cause of the incomplete transfers has not been established; this change recovers from them rather than eliminating them.

`NIHOS_NATIVE_CAMERA_STREAM` adds `incomplete`, separate from `dropped`. The latter counts valid frames dropped by the producer/consumer pool; `incomplete` counts rejected transfers, which never become consumable generations. The two long sessions each counted 3,340 valid completions and 264 incomplete transfers; valid-frame drops were 1,032 and 1,030. Both reported zero fatal stream faults. This is not a claim that the camera link produced no errors.

Production register replays cover three rejected incomplete transfers without publishing a buffer, a clean transfer resetting the streak, rejection while the other buffer is borrowed, scoped W1C acknowledgement preserving unrelated bridge bits, and fatal controls for a fourth consecutive discard, combined bridge overflow, DMA error, and discard without transfer completion. Channel 0 state remains unchanged.

## Stop/restart, memory and observer

Each full workflow starts with a heap measurement, runs the long view, then alternates five loading-stage cancellations with five short displayed live sessions. It measures the heap after every stop, then checks a manual capture and a second capture after one second idle. There were eleven live sessions per workflow, eight shell repaints, fourteen heap samples, and 2,339 / 2,340 total presented images. All image framebuffer comparisons matched, capture sequences and display counters advanced, and no image followed its session's drain record. Frames received before the 30 ms Escape decoder recognized dismissal are permitted.

Before camera use, reusable PSRAM capacity and free space were both 15,072,576 bytes, used zero. All thirteen later samples in each workflow were identical: free 12,971,328 and used 2,101,248. This is the existing 2 MiB frame reservation plus 4 KiB scratch, retained until reset. No allocation growth was observed across these cycles; this does not prove arbitrary-duration leak freedom. The audited SRAM heap span is 50,496 bytes above the unchanged 49,152-byte floor, not measured free SRAM.

The new `tools/camera_live_soak.py` consumes UART lines incrementally and fails on bad sequences, mismatches, post-drain images, resets, a live-image gap over two seconds, incomplete workflows, heap growth, fatal stream faults, or stalled service counters. Heartbeats must advance their display and both hart counters, with gaps limited to 7.5 seconds (the five-second report interval plus tolerance). Manual captures require an accepted request; stream records must include the incomplete count and enough non-dropped generations to cover every displayed image. Non-finite timestamps are rejected. Ten host tests exercise the protocol, corrupted evidence, finite serial reads and the committed physical traces. One early fixed-firmware trial finished 120 seconds but the observer incorrectly waited for a repaint after loading cancellation: no image overlay had opened, so no repaint was necessary. That condition was corrected before the two full successful workflows; the earlier trial is retained as a failed workflow.

Reproduce observer checks with `python3 -m unittest discover -s tools -p camera_live_soak_test.py`. Replay the committed evidence with `python3 tools/camera_live_soak.py docs/measurements/evidence/2026-10-31-camera-live-soak/trial-1.jsonl` (and `trial-2.jsonl`). These public traces retain protocol records and timestamps; other log lines become timer events, and scene hashes become ordinal equality labels preserving uniqueness without publishing their original values. `--sanitize-to` performs this transformation and requires an unchanged replay result. Raw hashes and public-trace hashes are recorded separately in the summary.

The public tool's capture function must run inside an identity-checked, exclusive backup/restore transaction; it does not provide an unguarded flashing CLI. It sets a finite 200 ms read timeout and requires a reconnect callback that reclaims verified kernel exclusion under the writer lease before returning. The physical collector at `72b3ba3` already used a 200 ms timeout and a protected serial class that checked kernel exclusion and other process owners after every reopen. The final interface makes that reconnect obligation explicit. The strengthened final replay validates both existing physical traces with exactly the same results; these observer changes do not change the tested firmware. Each frozen directory retains the exact private transaction wrapper, transaction module and original observer under `qualification-tools/`.

The Debug and ReleaseSafe suites each passed 921 host tests, the Python suite passed 500, and static analysis, native image/source audits and production CSI register replays passed. The native source identity check retained its five negative controls. Trials held shared write ownership and kernel serial exclusivity, verified the exact candidate before and after capture, restored both original flash spans, verified full readback and issued a hard reset. The restored system's boot was not captured; board write ownership was then released.

Network service heartbeats continued, but Wi-Fi was unconfigured. The current filesystem volume still failed its read with error -262. Optical quality, physical keyboard/touch operation, cold power-on, hours-long capture, color/full-resolution video, and configured Wi-Fi/SD load remain separate gates.
