# 起動スプラッシュの残存ちらつき経路

## 統合状態と今回の範囲

調査ベースは `origin/main` の `e1cfd0caa2e426c07088c7b33ed77464cbf3d899`。
前回の改修 `e0bd5272`（PR #91、merge `de76df02`）はリモートmainに含まれる。
調査開始時の主checkoutは `1c7935aa` で76 commits遅れており、この改修を含まなかった。
そのcheckoutからビルドすると前回修正前の経路が残る。本体の現在のFlash識別子は今回照合していないため、
ユーザーが見たちらつきの実機上の原因を旧イメージと断定するものではない。

主checkoutの未コミット4ファイルを保全し、別worktreeで追加修正した。
今回の実装・ホスト検証・通常deviceイメージ監査と、実機表示確認は別の段階である。
本体への書込み・リセット・SD操作は今回行っていない。新規修正のmainへの統合も未実施。

## mainに残っていた経路

1. `boot_graphics.paint(.milestone)` はタイトルを保持するようになった一方、状態欄の全領域を背景色で消してから選択中の文字を描いていた。
   DMAは同じ可視framebufferを読むため、完成画像が同じでも消去途中が見える余地があった。
2. `diagnostic_ui.service` は状態が同じでもrevisionが変わるとmilestone更新を行い、同じ状態文字を消して描き直せた。
3. 染色部分しか変化しない更新でも `present()` が1,843,200 bytesの全画面を1,024 bytesずつキャッシュ同期していた。
   不要な同期量・割込み禁止区間の反復があり、実機の滑らかさを確認する前に削減できる負荷だった。
   この量の削減を、そのまま実機の所要時間やfpsの改善と読み替えてはいけない。

## 修正

状態文字は透明runも含めて各画素の完成色を直接書き込む。
新しい文字領域の外側に残る古い文字の末尾だけを背景色に戻す。
全状態のmaskが同じ原点と高さを持つことはコンパイル時に検査する。
タイトル・碑文は保持し、状態が同じrevision更新では状態文字を描かない。

通常の染色更新ではタッチボタンを再描画せず、変更領域だけを64-byte cache lineへ拡張して同期する。
領域は埋込みspriteから求め、回転方向とstrideに従って物理rowへ変換する。
追加framebuffer・heap確保・待機時間・パネル再起動・バックライト消灯は導入していない。
増えた描画と同期のコードは既存のforeground Flash関数内へ置き、SRAMの48 KiB基準を維持する。
ログ画面からスプラッシュへ戻る明示的な操作では、従来どおり全画面を再構築する。

| 更新 | 同期bytes | 全画面比 |
| --- | ---: | ---: |
| 従来の各染色更新 | 1,843,200 | 100% |
| 染色・マーカー | 53,120 | 2.88% |
| 状態変更を含む | 77,824 | 4.22% |
| 状態変更・タッチボタンを含む最大 | 100,864 | 5.47% |

## 検証

- スプラッシュ単体10 tests成功。全7状態×7状態×縦横2配置の98遷移について、各描画span後の画素が旧値か完成値であることと、最終画像の一致を確認した。同状態への更新も含む。
- 旧来の状態欄の先行消去を意図的に戻すと、同じobserverが744件の不正な途中画素を検出して失敗した。[negative control](evidence/2026-10-31-splash-smooth/negative-control.txt)を保持した。
- 染色・状態変更で変わる全画素が同期矩形に収まり、矩形をcache lineへ拡張してもバッファ外へ出ないことを検査した。stride padding・guardと不正geometryの既存検査も成功した。
- ReleaseSafeは69/69 build steps成功。最初の実行は1,008/1,008 tests、最終実行の未cache部分は768/768 tests成功。イメージ監査のPythonテストは39件成功。fmt・ZLint・diff検査も成功。
- 通常/trace deviceビルドとイメージ監査が成功した。primary SRAM heap spanは通常49,728 bytes、trace49,600 bytesで、両方とも48 KiB（49,152 bytes）基準を維持した。数値は割当て前のheap範囲であり、実機の使用後空き容量ではない。候補識別子・監査・テスト記録は[検証index](evidence/2026-10-31-splash-smooth/index.json)に保持した。

## 残る確認

ホストobserverは描画spanの境界を検査するモデルであり、パネルの光学観測ではない。
本体の現行イメージ識別、修正候補のFlash照合、warm/cold起動時の目視または動画確認が必要。
通常更新は同じ走査バッファへ書く構成を保つため、VSYNCでの原子的なフレーム切替や全tearingの消失を証明していない。
今回の修正は、先行消去が露出する経路と不要な全画面同期を除くもの。
