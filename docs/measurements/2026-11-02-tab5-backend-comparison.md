# Tab5 desktop backend: first comparison

This is a bounded boot investigation on Apple M3, macOS 27.2 (26B123), arm64, on 2026-11-02. It is not a device qualification or a speed comparison between equivalent boot paths. Base nihos commit: `7f994648c97c62a011d9474f45c14c73bed68dfd`. The interpreter directly loads an ELF; ESP-EMU boots a merged flash image through ROM and the bootloader. Both used the same nihos build; MeOS was tested as an existing, separately identified binary pair.

## Display interface investigation

The pinned v0.50.0 CLI exposes GDB memory access and a generic register-file I2C device. The latter can acknowledge and store registers, but its documented interface does not provide live touch event injection. Its CLI help and peripheral overview do not document a Tab5 DSI scanout or live framebuffer stream. This is a documentation/interface observation, not proof that the emulator cannot be extended. The release repository carries an Apache-2.0 license; binary distribution and third-party notices still need checking for the intended packaging.

## Decision and next experiments

Keep the existing GPUI interpreter as the known-working nihos interaction baseline. ESP-EMU is a promising P4/IDF boot backend, but neither backend is established as a universal replacement. Before choosing, (1) identify the nihos PSRAM failure with GDB and a controlled negative/positive fixture, (2) build MeOS from a clean, fixed source revision and demonstrate a scheduler-driven observable action, (3) establish whether the pinned ESP-EMU exposes live Tab5 scanout and touch interfaces without guest changes, and prototype them, and (4) compare identical milestones with repeated timings. GDB memory polling can be an investigative bridge but does not establish a supported, efficient production display interface. Verify the pinned release's interface and distribution/license terms before integrating it.
