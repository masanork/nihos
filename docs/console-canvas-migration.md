# Splash and console: Canvas migration

The native splash and console currently write RGB565LE into the display owner's borrowed 720 × 1280 buffer. Their landscape views rotate logical `(x, y)` to physical `(y, 1279 - x)`. The display owner, scanout and cache handoff remain responsible for presentation; a Canvas does not own or present the frame.

The splash decodes Flash-resident, run-length encoded glyph masks and mixes RGB colors before packing to RGB565. It can use Canvas for its background and marker, but a general A8 blit is not a drop-in replacement for its current compressed, rotated glyphs or its RGB-before-quantization blending. Partial recoloring must continue to update only the intended sprites and marker. A rotated mask or bounded streaming mask adapter would let it use the shared compositor without allocating a second full framebuffer. Any visual changes should be assessed for readability rather than assumed pixel compatible.

The console maintains a grid, incremental cell repaint, a fixed header, damage and a bounded scroll step. Its live basic-face scroll is a leftward copy in physical scanlines because the logical display is rotated. `console_canvas_scroll_test.zig` compares that copy with Canvas on the real console geometry, including row padding and guards, for one- and two-line scrolls. It tests the movement only: production still performs its own copy and repaints the exposed band. Other font faces currently repaint rather than use this scroll path.

Before replacing the live copy, use the row-copy Canvas optimization from PR #35, preserve the current single-step update, exposed-band repaint and damage, and measure the actual path under boot load. The original Canvas implementation copies individual pixels and can be slower than the existing aligned word-copy loop. Likewise, a per-pixel call for each glyph would not automatically make rendering faster. A logical rotated view and a bounded glyph-mask interface are shared-engine improvements to evaluate rather than a second renderer-specific API.

The migration should be staged: first exercise the actual console and splash drawing through a borrowed Canvas in host and RV32 tests; then compare complete frames and state transitions, native image size and SRAM/stack placement; finally check startup, scroll responsiveness, panel cache/DMA handoff and visual quality on Tab5. Host or ESP-EMU results are not physical panel or timing evidence. No new application ABI or WASM runtime is implied.
