# Splash and console: Canvas migration

The native splash and console currently write RGB565LE into the display owner's borrowed 720 × 1280 buffer. Their landscape views rotate logical `(x, y)` to physical `(y, 1279 - x)`. The display owner, scanout and cache handoff remain responsible for presentation; a Canvas does not own or present the frame.

The splash uses Canvas for its background, status marker and glyph spans. Its Flash-resident run-length encoded masks are decoded in bounded row spans and rotated before drawing; colors are still mixed in RGB before packing to RGB565. Partial recoloring continues to update only the intended sprites and marker. A general A8 blit is not a drop-in replacement for this compressed, rotated data or its blending. A reusable rotated-mask or bounded streaming-mask interface remains a possible shared-engine improvement. Any visual changes should be assessed for readability rather than assumed pixel compatible.

The console maintains a grid, incremental cell repaint, a fixed header, damage and a bounded scroll step. Its live basic-face scroll is a leftward copy in physical scanlines because the logical display is rotated. The scroll step now calls Canvas.copyRect, then retains its existing exposed-band repaint and damage tracking. `console_canvas_scroll_test.zig` independently compares that copy with the old scanline movement on the real console geometry, including row padding and guards, for one- and two-line scrolls. Other font faces currently repaint rather than use this scroll path.

This depends on the row-copy Canvas optimization from PR #35; the original Canvas implementation copies individual pixels and can be slower than the former aligned word-copy loop. Measure the new path under boot load before drawing device performance conclusions. Likewise, a per-pixel call for each glyph would not automatically make rendering faster. A logical rotated view and a bounded glyph-mask interface are shared-engine improvements to evaluate rather than a second renderer-specific API.

The migration should be staged: first exercise the actual console and splash drawing through a borrowed Canvas in host and RV32 tests; then compare complete frames and state transitions, native image size and SRAM/stack placement; finally check startup, scroll responsiveness, panel cache/DMA handoff and visual quality on Tab5. Host or ESP-EMU results are not physical panel or timing evidence. No new application ABI or WASM runtime is implied.
