# nihos における ML-KEM・ML-DSA 実験報告書

作成日: 2026-10-29

対象: nihos の ESP32-P4 / Tab5 向け native 実行系

位置づけ: **実験報告。main 未統合、製品機能ではない**

## 1. 結論

ML-DSA-65 の署名検証と ML-KEM-768 の鍵生成・カプセル化・デカプセル化は、固定テストデータを使うヘッドレスの ESP32-P4 エミュレータ上で動作した。両者を Flash に配置した単一の試験イメージでは、同じ独立ワーカー用スタックを順に再利用し、両方の処理を実行できた。

通常のデバイス向け UI・ネットワーク・デバイス構成に両アルゴリズムのコードをリンクすることも、試験用の配置変更により可能だった。ただし、その構成には KEM の実際のサービスや専用ワーカーは組み込まれていない。SRAM と Flash の余裕は小さく、実用上の成立はまだ判断できない。

**実装済みと実行確認済みなのは試験用フィクスチャの範囲である。Tab5 実機、実乱数・実秘密鍵、通常 UI との共存、Flash 書き込み中の安全性、製品のセキュリティは未検証。** 今回の対象は ML-DSA 署名検証と ML-KEM-768 の基本操作であり、ML-DSA 署名生成、他のパラメータセット、FN-DSA の実装は含まない。

## 2. 試験対象と証拠の区別

| 対象 | 行ったこと | 結果が意味する範囲 |
| --- | --- | --- |
| ML-DSA-65 | 固定署名の検証、改変メッセージの拒否、割り当て失敗時の回収 | ホスト試験と RV32 ヘッドレスエミュレータ試験 |
| ML-KEM-768 | 固定テスト鍵による鍵生成・カプセル化・デカプセル化、改変暗号文、割り当て失敗 | ホスト試験と RV32 ヘッドレスエミュレータ試験 |
| 両者の同居 | 一つの Flash 配置イメージで ML-DSA、続いて ML-KEM を実行 | 同じ監査済みイメージによるヘッドレスエミュレータ試験 |
| 通常デバイス構成 | UI・ネットワーク等を含む構成へのコード配置とイメージ構造の検査 | リンク・イメージ検査のみ。通常 UI から KEM は呼び出していない |
| 実機 | 書き込み・実行なし | 実機性能、動作、安定性は不明 |

評価対象は作業ブランチ `codex/pqc-resource-study`、報告対象の実装先頭は `b4964d8`。測定ごとに異なる候補イメージを使用したため、下記の各値は、特に断りがない限り同じ試験条件の中だけで比較する。主リポジトリの main への統合は行っていない。

## 3. 実験した実装

### 3.1 暗号実装と作業領域

既存の独立した実行系と比較した後、ポータブル C の `mldsa-native` と `mlkem-native` を外部チェックアウトから固定リビジョンでビルドした。ソースはこの実験でリポジトリへ vendoring していない。

- ML-DSA: `33031ee66dfe0231cc5995dd1d4ced467df6b8de`
- ML-KEM: `e0e0ae95765f4c48585dc8cdaa0656d4eda46a06`
- コンパイラ: Zig 0.17.0。エミュレータは ESP-EMU 0.50.0、ローダーには ESP-IDF 5.4.4 を使用。

両実装の大きな内部作業領域には、呼び出しごとに所有する試験用アリーナを利用した。これは単調増加型の簡易アロケータであり、公開された一般用途のメモリ API や製品用暗号サービスではない。外部実装の custom allocation 設定は実験的な機能であり、すべてのスタック使用をアリーナへ移すものではない。

### 3.2 ワーカーと回収

試験用に 8,192 B の専用 SRAM スタックを静的に予約し、CPU0 の独立タスクで暗号処理を実行した。割り込み時のフレームとスタックガードを検査し、タスク終了後に所有リソースの台帳をクリーンにしてからタスクを回収する。スタックは回収後も静的に予約されたままで、ヒープへ戻るわけではない。

ML-DSA の試験では、3 ジョブの逐次実行、タスクスロットの世代更新と古い識別子の拒否、PSRAM 不在、部分的な割り当て失敗後の回収を確認した。キャンセル試験では、実行中の C 処理を強制停止せず、処理が戻って領域を回収した後に試験上の取消結果を記録した。強制終了、並行ジョブ、長時間運用やクロスハートのキャンセル競合を保証するものではない。

解放エラーの注入では、台帳が対象の所有記録を保持し再利用を拒むことを別の観察用経路で確認した。既存の通常回収経路では同じエラーにより CPU0 が停止した。エラーを呼び出し元へ返して隔離・復旧する製品用の機構は実装していない。

### 3.3 入力コピー

ML-DSA の入力として、公開鍵 1,952 B、署名 3,309 B、コンテキスト最大 255 B、メッセージ最大 4,096 B を収める 9,612 B の試験用スナップショットを確保した。コピー後に依頼側の元バッファを変更しても、ワーカーがコピー済みの内容を検証することを確認した。

さらに、協調する単一の書き手がコピー途中で変更する決め打ちのスケジュールでは、世代カウンタの変化を検出し、検証前にそのコピーを拒否した。**任意の書き手が変更できるメモリ、コピー中のすべての競合、クロスハートのメモリ順序、カウンタ周回に対する安全性は証明していない。** 呼び出し元の認証・ポインタ検証・入力固定の契約が別途必要。

スナップショット確保後のアリーナ確保失敗と、直前の成功後にスナップショット自体の確保が失敗する場合も検証した。後者では、結果構造体の初期化を外した対照イメージに前ジョブの `valid=1` が残る不具合を再現し、修正と検査の有効性を確認した。これらの失敗はタスク台帳の枠不足による `Full` の試験で、実 PSRAM の容量不足や断片化の試験ではない。

## 4. エミュレータでの資源測定

### 4.1 同一イメージでの逐次実行

Flash 配置のヘッドレス試験イメージで、4 MiB のエミュレートされた PSRAM を使い、ML-DSA と ML-KEM を逐次実行した。同じイメージで PSRAM 不在時も両タスクの終了・回収を確認した。

| 項目 | ML-DSA-65 署名検証 | ML-KEM-768 |
| --- | ---: | ---: |
| 専用 SRAM スタック予約 | 共通の 8,192 B | 共通の 8,192 B |
| 観測されたスタック使用 | 2,896 B | 最大 4,912 B |
| PSRAM アリーナのペイロード | 16,304 B | 32,688 B |
| アリーナの buddy 課金 | 16,384 B | 32,768 B |
| 別のテスト I/O バッファ | この試験ではなし | 6,144 B ペイロード、8,192 B 課金 |
| そのジョブで同時に確保した PSRAM | 16,384 B | **40,960 B** |

両ジョブは逐次実行したので、この試験での暗号ジョブの最大同時課金は 40,960 B である。両方を同時実行した値でも、呼び出し元の入力コピーを含む製品サービスの総使用量でもない。別の入力コピー試験では、依頼側の 9,612 B、コピー 9,612 B、ML-DSA アリーナ 16,304 B の３領域を同時保持して 49,152 B が課金された。

スタックの数字は、今回の固定入力と割り込み・計測を含む観測値であって最大使用量の保証ではない。ML-KEM の単独イメージでの操作別観測は、鍵生成 4,784 B、カプセル化 4,624 B、正常デカプセル化 4,816 B、改変暗号文のデカプセル化 4,688 B だった。これらはいずれも既存の 4 KiB ワーカースタックを超えた。別イメージのため、逐次実行イメージの 4,912 B と同一条件の比較値ではない。

試験中にタイマーと CPU0・CPU1 の合成処理の進行を確認したが、タッチから表示までの遅延や実 UI の応答時間は測っていない。アリーナの CPU から見えるゼロ化と割り当て解放を確認したが、物理 PSRAM の消去、キャッシュ書き戻しや秘密データの全コピーの消去を保証しない。

### 4.2 通常デバイス向け構成のリンク予算

以下は同条件の通常デバイス向け構成をビルドした際の**主 SRAM のリンク上の数値**。ヒープ範囲は実行時にアプリが利用できる空きメモリの測定値ではない。ML-KEM の入口を残した２構成は、隔離した作業ツリーでリンカ・試験用監査を変更したもの。

| 構成 | 静的占有 | リンカ上のヒープ範囲 | アプリイメージ |
| --- | ---: | ---: | ---: |
| PQC 無効 | 100,992 B | 62,848 B | 185,648 B |
| ML-DSA 検証試験 | 102,976 B | 60,864 B | 206,336 B |
| ML-DSA と ML-KEM のテスト処理全体を保持 | 111,104 B | 52,736 B | 232,032 B |
| ML-DSA と ML-KEM の API 入口を保持 | 105,728 B | **58,112 B** | 226,096 B |

ML-KEM API 入口のみを保持した構成は PQC 無効時比で静的 SRAM が 4,736 B 増える。既存の 49,152 B ヒープ下限に対する余裕は 8,960 B だが、**専用 8,192 B ワーカースタックはこの構成に含まれない**。それだけを単純に差し引くと 49,920 B、下限を 768 B 上回る計算になる。実際にはワーカー本体、状態、アラインメント、要求・結果処理などの追加が必要であり、実ワーカーを含むビルドで成立することは示していない。

テスト処理全体を保持した構成では、同じ単純計算で 44,544 B となり、下限に 4,608 B 不足する。いずれもリンク計測の比較であり、通常画面、Wi-Fi、周辺機器が動作中のアプリ向け残容量ではない。

### 4.3 Flash 領域と配置

両方をすべて SRAM に置いたヘッドレスの試験構成は、49,152 B のヒープ下限を満たせなかった。下限だけを緩めた**別の ELF 診断**ではヒープ範囲は 33,920 B で、下限に 15,232 B 足りなかった。これを実行可能な製品イメージとして扱っていない。

両方の試験コード・定数を Flash に移したヘッドレスのエミュレータ用イメージは、静的 SRAM 85,888 B、ヒープ範囲 77,952 B で下限を維持し、上記の逐次実行に成功した。Flash の試験用実行コードは 32,196 B、読み取り専用データは 11,872 B だった。

一方、通常デバイス構成では既存の Flash ２領域が先に不足し、全てを置くリンクは実行コード側で 3,508 B、定数側で 2,208 B 超過した。試験用データを除いて一部の ML-KEM 関数を SRAM に置いた API 入口保持イメージは構造監査に通ったが、その Flash 実行コード領域の残りは **302 B**、定数領域の残りは 2,592 B だった。コンパイラ変更やサービス追加に対して余裕が小さい。領域の分割・追加には、既存の SQLite、UI、ストレージやローダーのマッピングと衝突しない設計が必要。

## 5. 利用候補と必要な追加設計

| 用途 | 今回の成果との関係 | 利用前に必要なもの |
| --- | --- | --- |
| 更新ファイルやオフライン文書の ML-DSA 署名検証 | 小さな固定メッセージでの署名受理・改変拒否を試験 | 信頼する公開鍵の選択、対象バイト列の固定、文脈・形式、鍵更新、失効、ロールバック対策 |
| 通信での ML-KEM による共有鍵確立 | 固定データで鍵生成・カプセル化・デカプセル化を試験 | 実乱数、相手とアルゴリズムの認証、鍵導出・鍵確認、秘密鍵の所有と寿命 |
| 応答を保つ非同期暗号処理 | 独立タスク、逐次実行、一部キャンセルと回収を試験 | 通常 UI に接続した要求 API、入力所有、再利用、失敗通知、実際の応答時間 |

ML-KEM の改変暗号文試験では、デカプセル化 API が成功を返し、元とは異なる共有秘密を生成した。成功の戻り値だけで相手の認証や鍵一致を判断してはならない。ML-DSA も、任意の公開鍵で署名が数学的に正しいことと、その署名者を信頼して更新を許可することは別である。

## 6. 製品化前の未解決事項

1. 通常デバイス構成へ、実際にスケジュールされるワーカー、専用スタック、要求・結果・所有権管理を追加し、48 KiB 下限と Flash 配置を再測定する。
2. Flash 実行コードに対する独立した呼び出し経路監査を行い、Flash 消去・書き込みやキャッシュ無効化の前に、両 CPU と関連 DMA を停止・再開できる協調機構を実装・検証する。現在の試験用監査は、観測した関数一覧に基づくもので、完全な呼び出しグラフやキャッシュ無効時の安全性の証明ではない。
3. 秘密鍵・共有秘密・作業領域の所有、CPU 可視メモリとキャッシュの消去、実乱数の準備、鍵保管、エラー時の隔離・復旧を設計する。実験用の固定 seed や coins を実鍵に使わない。
4. 依頼元の認証、入力の長さ・ポインタ検証、変更中のスナップショット、期限、キャンセル、複数ジョブ、タスク終了・再利用を実装系で検証する。
5. 通常 UI・ネットワーク・ストレージと同時に動かし、実際の SRAM/PSRAM 空き、割り込み、入力から表示までの遅延、長時間動作とエラーを測る。
6. 同一の候補バイナリを識別して Tab5 実機で検証し、電源投入・電源断、ストレージ操作、回復、サイドチャネル等を個別に評価する。ホスト試験・エミュレータ・イメージ監査は実機検証や FIPS 認証を意味しない。
