# SICPを読みながら試すための教材構造と学習セッション

2026年10月31日。第1段階の教材構造化と、第2段階のRAM上の選択・編集・実行・本文への復帰を実装。ホストとnativeビルドで検証した。実機検証・永続化・処理系拡張は未実施。
実装可能性の根拠は[精査報告](../measurements/2026-10-31-sicp-structured-examples.md)。
第2段階は読書基盤が統合されたorigin/main `0cb0ee4f` 上に整理した。通常checkoutの既存変更は保持する。

## 1. 最初に成立させる体験

読書画面で「このページの例題」を開き、例題を選ぶ。演習画面には原文から取り出した
コードが入り、編集して実行すると値またはエラーが出る。「本文へ戻る」で同じ箇所へ
戻り、再び演習を開くと編集内容と実験環境が残っている。

最初は1.1.1の整数の式を対象にする。平方根の節追加とR7RS対応を前提にしない。
例えば `(+ 137 349)` を487になる式へ変更したとき、出力が487になることを確認できる。
原文の答え486は別の参考欄に置き、実行するコードへ混ぜない。

本文は参照用、演習コードは編集用、メモは説明用として、それぞれ独立した文書にする。
どの画面を表示しているかと、文書や評価環境の寿命を分ける。

```mermaid
flowchart LR
    X[固定した原典XML] --> C[Scheme側を選ぶ教材コンパイラ]
    M[IDと実験手順を定める編集用manifest] --> C
    C --> I[本文ブロックとコード・参照の共通モデル]
    I --> T[読書用本文と位置情報]
    I --> S[例題表と実験手順]
    T --> R[本文を読む]
    S --> L[例題を選び編集する]
    R -->|このページの例題| L
    L -->|明示的な実行| V[学習専用のScheme環境]
    V --> O[値・出力・エラーと実行履歴]
    L -->|帰還位置を保持| R
```

## 2. 三つのモデルに分ける

| モデル | 責任 |
| --- | --- |
| Snippet：原典のコード断片 | コードそのもの、原典位置、表示範囲、出典、参照名を保持する |
| Experiment：実験手順 | どの定義を準備し、何を編集し、どの式を呼び出すかを指定する |
| LearningSession：利用者の作業 | 草稿、メモ、評価環境、実行結果、本文への帰還位置を保持する |

コード断片と利用者の作業を同じレコードにしない。原典を更新しても草稿を上書きせず、
同名の手続きを使う別の実験も混線しない。

### 2.1 原典XMLから引き継ぐ情報

| 原典 | 採用する意味 |
| --- | --- |
| `SNIPPET/SCHEME` | 実行候補のコード。通常の文章中の`SCHEME`とは区別する |
| `SCHEMEOUTPUT`、`SCHEME_OUTPUT` | 本文に表示する参考出力。実行しない。出力だけのSNIPPETにも実行ボタンを付けない |
| `NAME` | 原典内の参照名。利用者データの主キーとは別に保存する |
| `REQUIRES` | 前提となる定義への参照。この関係だけを依存グラフの基本とする |
| `EXAMPLE` | 定義を試すための呼び出しへの参照。前提定義とは異なる関係 |
| `EXPECTED` | 原典が示す検証用情報。文字列として保存し、Schemeコードとして評価しない |
| `HIDE="yes"` | 元の見せ方の指定。準備コードや呼び出しとして保持し、本文の選択候補とは分ける |
| `EVAL="no"` | 表示専用候補。実行可能とは判定しない |
| `SOLUTION`、言語分岐 | 解答とJavaScript側を通常の抽出対象へ混ぜない |

`EXPECTED`と本文の参考出力は同一視しない。定義が返す値と、その定義を使った
呼び出しの値も区別する。比較版のメタデータがSchemeにもそのまま適用できるかは、
有効化する実験ごとに確認する。

`SCHEME`があるだけで機械的に実行可能にしない。展開過程、擬似コード、意図的な
エラー例などは編集用manifestで役割を指定する。解答の自動読込みは行わない。

### 2.2 安定したIDと更新

利用者の草稿に紐づくIDは `sicp.expressions.addition` のように編集側で固定する。
配列番号、ページ番号、コードのhashを主キーにしない。

原典との対応は、版・原典ファイルhash・NAME、またはコードhashと文脈を使う。
NAMEがない断片には編集側でIDを割り当てる。hashは原典の照合に使い、コードの修正で
利用者の草稿IDを変えない。同じコードが複数箇所にある場合は文脈で明示的に区別する。
照合不能・多重一致・重複IDは生成時に止める。

英語本文と将来の日本語本文の位置情報は別に持つ。同じ概念の実験IDを共有できても、
翻訳前後のbyte offsetは共有しない。原典・本文・演習パックの版とhashを一緒に記録する。

### 2.3 本文と例題の位置を一度に生成する

現在の `sicp_text` の結果を後から正規表現で解析する方式は採用しない。
先に文章・コード・出力・見出しを表す中間ブロックを作り、本文を書き出す際に同時に
UTF-8 byte範囲を記録する。空白やLaTeXの変換は各ブロックの生成前に完了させる。
位置を確定した後の全文への空白置換は行わない。

各コードブロックについて `[body_start, body_end)`、snippet ID、表示上の役割を持つ。
読書ページの範囲と交差するコードを選択候補にできる。ページがコードの途中で切れても、
取り出すコードはsnippet全体とする。同じ例題が前後のページに出ても同じIDに紐づく。
表示された一部分をそのまま評価する操作にはしない。

## 3. 実験手順を明示する

原典にある次の関係は、単純な一種類の依存グラフへまとめられない。

```text
Ackermannの定義 --EXAMPLE--> (A 1 10)
(A 1 10)       --REQUIRES--> Ackermannの定義
```

これは有効な定義と使用例の関係であり、依存循環として拒否しない。
実行準備ではREQUIRESだけをたどり、実験手順が選んだ対象定義と呼び出しを順に評価する。
同じ定義を重複して評価せず、本当のREQUIRES循環・未解決参照は生成時に拒否する。

具体的な手順は次のようになる。

| 実験 | 準備 | 編集する対象 | 呼び出し |
| --- | --- | --- | --- |
| 整数の加算 | なし | `(+ 137 349)` | 編集した式を一度だけ評価 |
| 再帰版の階乗 | なし | 再帰版`factorial`定義 | `(factorial 5)` |
| 局所反復版の階乗 | なし | 局所`iter`を持つ定義 | `(factorial 5)` |
| 反復版の階乗 | なし | `factorial`と`fact-iter` | `(factorial 5)` |
| 加算の再帰・反復を比較 | `inc`と`dec` | 選んだ一方の`+`定義 | `(+ 4 5)` |
| Ackermannから派生する手続き | `A`の定義 | `f`、`g`、`h`、`k`の定義 | `(k 4)` |

再帰版と反復版を同じ環境へ順に自動投入しない。原典中で同じ名前を再定義することは
教材の意図なので、それぞれに実験IDを持たせる。比較は別の実験の結果を並べて行える。

加算の例を表す実験レコードの概念例：

```json
{
  "id": "sicp.expressions.addition.try",
  "editable": "sicp.expressions.addition",
  "prepare": [],
  "evaluate": {"kind": "editable_expression"},
  "reference": {"kind": "integer", "value": 486},
  "context": "sicp.expressions.addition.try"
}
```

定義の実験では`evaluate`が「編集した定義を読み込む→別の呼び出しを評価する」になる。
呼び出しも変更できる独立した小さな入力欄を用意する。元の定義・呼び出しは常に参照できる。
前提定義は最初の実行時に読み込み、「準備コード」に出典とともに表示する。
学習者が前提を変更する場合は実験側の草稿として保存し、原典を変更しない。

「すべての例題を読み込む」操作は用意しない。原典の順序はページ順であり、
安全な実行順や一つの名前空間への結合を意味しない。

## 4. 読書と演習を行き来するUI

最初は一画面の切替で実装する。読書画面の「試す」または未使用の`e`キーから、
現在のページにある例題一覧へ進む。例題を一つ選ぶと演習用文書を開く。
この段階では、本文の範囲選択やコードのタップ判定を前提にしない。

演習画面は横書き・等幅のコード、実行する呼び出し、値/出力/エラー、メモを扱う。
Tab5ではコード・結果・メモを切り替えて表示し、同時に複数の大きな描画面を確保しない。
Macの横並び表示は、共通の操作が成立した後の表示上の拡張とする。

主な操作は「実行」「準備からやり直す」「原文のコードに戻す」「本文へ戻る」。
コードの復元と評価環境のリセットを別の操作にする。草稿やメモは画面移動では破棄しない。
本文へ戻って再度同じ実験を開いた場合は、同じRAM上の実験環境を使える。

帰還位置は、本の版・節ID・ブロックID・ページ先頭byte位置・表示設定を持つ。
演習画面の横書き設定を読書画面へ押し付けない。原典更新で本文hashが変わっていたら、
以前のoffsetを無条件に使わず、同じブロックまたは節の先頭へ戻す。

## 5. 学習用の評価環境

同じ処理系の実装を共有しても、VMインスタンスと名前空間はエディタ拡張と分ける。
学習用host adapterにはエディタ編集、設定変更、SQL、ファイル、カメラの操作を渡さない。
演習で`+`や`car`を再定義しても、xyの操作は継続できることを受入条件にする。

最初はRAM上で一つの実験環境を稼働させる。同じ実験では定義を保持し、変更した定義を
再評価して続きを試せる。別の実験に切り替えると新しい環境を作り、以前の草稿・メモ・結果は
保持する。複数の実験のVMをすべて保持する設計にはしない。

各実行に、実験ID、環境世代、草稿revision、準備コードの版を紐づける。
実行中の入力は固定したスナップショットを読む。完了が遅れて届いても、別の実験や
新しい草稿の結果として表示しない。編集後の以前の結果は「変更前の結果」と表示する。

初期の小さなVMでは、実行前の状態を候補VMへ複製し、成功時だけ採用する方式が取れる。
エラー・予算切れでは最後の正常な状態を保持し、途中の出力は未完了として扱う。
これには二つ分のVM容量が必要。PSRAMで確保し、実装時にサイズと描画との共存を測定する。
将来大きなVMへ移すときもコピー方式を固定条件にせず、同じ公開契約を保てる方法を再検討する。

現在のstep/depth制限は有限な復帰を保証する仕組みで、実行中のキーによる中断とは異なる。
本格的な反復を扱う段階では、評価を一定量ずつ進めるAPI、キャンセル要求、実行予算、
末尾呼出し、評価中のGCを整える。単に深さ上限を引き上げてR7RS対応とは扱わない。

エラー位置は今の評価器にはないので、最初は対象コードとエラー種別を表示する。
次段階でreader/evaluatorのsource spanを追加し、草稿・前提定義・呼び出しのどこで
失敗したかを区別する。位置が取れない状態で推測した赤線を付けない。

## 6. 参考値と対応範囲

原文の参考値は、利用者が自由に変更したコードを採点する基準にはしない。
元コード・呼び出し・前提のhashが承認済みケースと一致した場合だけ参照結果と比較する。
変更後の式が487になれば正常な実験結果であり、原文486と違うことをエラーにはしない。
演習の解答や参考値は、必要に応じて利用者が開けるようにする。

実行可能性は、曖昧な「Scheme対応」ではなく、処理系の版と検証済みケースで表す。
構文・数値・リソースの条件を実験に持たせ、対応判定は空のVMで準備と呼び出しまで
実行するCI結果へ紐づける。定義をロードできただけで、その呼び出しまで動くとは判定しない。
未知の手続き名を単純検索するだけの機能判定もしない。

初期対応は1.1.1の整数例。除算・小数・`>`・`cond`が必要な例題は、理由を示して
参照・編集はできるが、対応済みとは表示しない。現在factorial 5が成功しても6でDepthになる
制約を隠さない。再帰と反復を教材として扱う段階では、より十分な処理系検証を別途行う。

## 7. 保存と再開

最初のRAM版では「画面を行き来して続ける」までを受入条件にし、再起動後の再開と区別する。
永続化では次を保存する。

- 版・節・snippet・実験ID、元コードのhash。
- 編集した定義と呼び出し、変更した準備コード、それぞれのrevision。
- メモ、本文への帰還位置、利用者が残した実行結果。
- 実行結果に対応するコード・準備コード・処理系の版と、完了/失敗/中断の状態。

VMの生メモリやクロージャのアドレスは保存しない。再起動時は草稿を復元しても
プログラムを自動実行せず、利用者の実行操作で準備から構築する。
手入力した一時的な定義を再現したい場合は、保存する準備コードへ明示的に加える。
保存されていない対話履歴から環境が完全再現できるとは説明しない。

Macは既存の`user/init.scm`世代保存と学習用テーブルを分ける。
Tab5は同じ保存APIの先を`staged -> committed`へ接続し、電源断後の復元を別に検証する。
書込み失敗時に草稿を保持し、保存済みとは表示しない。

## 8. 格納と実装配置

本文と演習表を同じ中間モデルから生成し、本文のhashで対応付ける。
native向けには、既存の読書パックを再利用する演習用の別表を追加する。
ヘッダに形式の版・長さ・読書パックの識別hashを持たせ、レコードはoffsetとlengthで参照する。
名前やコードの解決を端末上のJSON解析へ依存させず、必要な実験だけをRAMへ取り出す。

実装した学習用モジュールと後続案：

| 配置案 | 責任 |
| --- | --- |
| `tools/xy_sicp.py` | Scheme側の構造化、編集manifestの照合、本文と演習表の生成 |
| `tools/xy_learning_pack.py` | 同じデータからnative向けのoffset表と文字列領域を生成 |
| `src/xy/learning_catalog.zig` | 範囲検査、本文との版照合、ページに対応する例題列挙 |
| `src/xy/learning_session.zig` | 草稿・帰還位置・環境世代・実行結果の共通状態 |
| `src/xy/learning_session.zig` 内のVM | 成功時だけ候補VMを採用する。非同期評価・取消は後続案 |
| Mac/Tab5の既存adapter | 入力と画面遷移、保存APIへの接続 |

原典hash、著者、ライセンス、変換履歴は本文と演習側の双方から参照できるようにする。
生成スクリプトと同梱教材のライセンスを混同しない。

今回の25断片に含まれるコードは合計1,154 UTF-8 bytes、参考出力は22 bytesだった。
これはコード内容だけの測定であり、ID・索引・VM・文書・スタックの容量を含まない。
Flashへの格納、4 MiB factoryパーティションへの適合、SRAMの下限、PSRAMの所有と解放は
最終候補のビルドと実機で検証する。全巻への拡大が同じ容量で済むとは推定しない。

## 9. 実装順と受入条件

| 段階 | 実装と確認 |
| --- | --- |
| 1. 教材の構造化 | 25断片のID・code/output分離・依存/呼び出し分離。重複、参照切れ、実際の依存循環、本文hash不一致を拒否。byte範囲が実際のコードと一致することを確認 |
| 2. RAM上の往復 | 整数例を選択・編集・評価。ページをまたぐ例題も全体を取得。本文位置、通常文書、Undo、演習草稿、メモを保持。エラー後も操作継続 |
| 3. 定義を使う実験 | 専用VM、準備コード、呼び出し、再定義、リセット。二種類のfactorialと二種類の加算が互いの環境を汚さない。結果のrevisionと対応を確認 |
| 4. 処理系の拡張 | 除算・小数・比較・cond、末尾呼出し、GC、予算と取消。原典のケースと変更実験で検証し、対応表を更新 |
| 5. 保存・発展 | 草稿・メモ・本文位置の保存/競合/障害復旧。Tab5の再起動・電断試験。平方根の節と前提を取り込み、必要な数値処理の確認後に有効化 |

各段階でMacとTab5共有coreの同じシナリオを実行する。native候補は既存のメモリ・image監査を
通し、実機の入力と表示を確認する。hostのプローブ成功を実機での学習体験の成功とは呼ばない。

## 10. 第1段階の実装状況

`tools/xy_sicp.py` と編集manifestが、原典に固定した安定IDで25断片を構造化する。
本文とコード・参考出力のbyte範囲を同時に生成し、隠れた補助断片4個は本文へ出さず
例題表に保持する。本文から選ぶ実験は21個。実行手順はREQUIRESとEXAMPLEを分けて構築する。
全実験は`unqualified`であり、期待値も未承認の参考情報として保存する。

`assets/xy/sicp-learning.json` は本文のlibrary hashと節ごとの本文hashに結合する。
Macビルドは原典からの再生成一致を検査し、同JSONをアプリへコピーする。
Tab5向けにはXYREAD01ヘッダの未使用領域を使って、XYLAB001の例題表を追加格納する。
既存の本・フォントのレコード配置は維持する。新しい表の読出しは
`src/xy/learning_catalog.zig` に分離した。第2段階ではUIから現在のページの例題を照会する。

生成と検証は次で行う。既存フォントのcoverageが足りないとrefreshは失敗するため、
その場合は原典フォントから生成し直す。

```sh
python3 tools/xy_sicp.py
python3 tools/fonts/build-xy-reader.py --refresh-manifest
python3 tools/xy_sicp.py --check
python3 tools/xy_sicp_test.py -v
```

第1段階の[実装と検証の記録](../measurements/2026-10-31-sicp-structured-examples.md)を参照。


## 11. 第2段階の実装状況

読書画面の `e` /「このページの例題」から、例題を選択して演習へ進める。
Macは例題選択ダイアログとCocoaの操作バー、Tab5は共有描画の例題一覧とタッチ操作を使う。
本文のbyte範囲と交差する例題を列挙し、ページ途中でも完全なコードを開く。
演習は横書きに固定し、読書の縦横・書体・サイズ・ページ履歴を変更しない。

共有の `learning_session.Session` が24個までの草稿とメモを保持する。
現在の本文に選択可能な21断片をすべて保持でき、満杯になった場合も既存の作業を追い出さない。

## 12. 本文とソースを読み分ける書体

SICPの英語本文にはCentury Schoolbook L系のTeX Gyre Schola 2.005から作成した
`nihos Book Serif`、コード・参考出力・文中の`SCHEMEINLINE`にはSource Code Proを使う。
英文らしさを推測せず、XMLから得たUTF-8範囲をXYLAB001 version 2の追加表へ渡す。
原文の本文bytes・例題ID・位置は変更しない。version 1も読み出せ、書体情報のない版は従来表示に戻す。

書体の計測と描画で同じ範囲と字幅を使い、cacheの書体IDも分ける。
SICPだけは不要なルビ領域を確保せず、行間を本文サイズの1/5以内、空行を行送りの1/4にする。
日本語の本・通常文書・演習バッファの表示設定には反映しない。
Macは最大900、nativeは最大960文字を候補として、固定1,024 glyphs内へ収まるページを選ぶ。
描画workspaceの2MiB上限とforeground stackの256KiBは維持する。実機のstack watermarkは未測定。
