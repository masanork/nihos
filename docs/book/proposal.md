# nihosを教材にしたOS書籍の企画案

2026年10月25日。中心読者・書名・分量は検討案。実装状況の記述は、調査時のカーネル側コミット `2517d126bfd5636e7a322ac2e701570ea11ea27f` と対応する測定記録を基準にする。

nihosの書籍は、Zigで書かれた小さなOSを読み、変更し、実機で確かめながら、OSの設計判断を身につける本にしたい。読了後に残る成果は、起動画面と一式のソースだけでなく、「どの資源を誰が持ち、何を守れば正しく動き、どの測定なら判断の根拠になるか」を説明できる力である。

仮題は『小さなOSを育てる』、副題は『ZigとRISC-Vで学ぶ、実機のしくみと設計判断』。Tab5は具体的な実験機として表紙・紹介文で明示する。書名にnihosだけを掲げるより、OSや組込みに関心を持つ読者へ到達しやすい、という編集上の仮説である。実際の読者インタビューで確かめたい。

## 読者と持ち帰れるもの

中心読者は、Cなどで関数、ポインタ、構造体、ビット演算を使った経験がある、OS自作の初学者を仮置きする。xv6を読んだ人には実機・DMA・SMP・性能設計への次の一歩を提供する。Zigの習得は前提にせず、slice、optional、error、comptime、atomicを使う場面で説明する。

| 読者 | 本書でできるようになること | 必要な導線 |
| --- | --- | --- |
| OSを初めて作る人 | 起動からタスク切替までの実行経路を追い、小さく変更する | 最小限のCPU・ABI・Zig解説と、各段階の動くチェックポイント |
| xv6などを学んだ人 | キャッシュ、DMA、SMP、周辺I/Oの制約を測定して設計する | 一般原理とESP32-P4固有条件の対応、比較実験 |
| Tab5で作品を作る人 | 画面・入力・音・保存を使う小さな機能を実装する | 早い段階の目に見える成果と、将来のアプリ開発ガイドへの接続 |

三者を同じ深さで扱うと本が膨らむ。本文は初学者が辿れる一本道にし、経験者向けの考察と、アプリ・移植の手引きはWebの補足に分ける。初学者といってもプログラミング未経験者まで含めない。

## RISC-Vの類書と教材

RISC-VでOSを学ぶ選択肢はすでにある。「RISC-Vだから新しい」「現代的な言語だから読む価値がある」という立て方だけでは弱い。以下は代表例であり、網羅的な市場調査ではない。内容はリンク先の公式・著者資料で確認した。

| 書籍・教材 | 学習の中心 | nihosの企画に与える示唆 |
| --- | --- | --- |
| [xv6とMITの教材](https://pdos.csail.mit.edu/6.1810/2025/xv6.html) | 小さなUnix系OSを通して、プロセス、ページテーブル、ロック、ファイルシステムを学ぶ | OSの基本概念を読める実装と結びつける強い先例。nihosにも概念とコードの対応が必要 |
| [OS in 1,000 Lines](https://operating-system-in-1000-lines.vercel.app/ja/) | Cで小さなRISC-V OSを段階的に作る。例外、プロセス、ページテーブル、ユーザーモード、ディスクなど | 最短の完成体験に強い。nihosは実機の資源制約と測定を中心に構成したい |
| [自作OSで学ぶマイクロカーネルの設計と実装](https://seiya.me/blog/microkernel-book-2023) | HinaOSというC製RV32マルチサーバOSを使い、IPC、ドライバ、ファイルシステム、SMPなどの設計を考える | 日本語・RV32・設計重視・SMPという点まで重なる。IPCやマイクロカーネルだけでは差が出ない |
| [rCore Tutorial](https://rcore-os.cn/rCore-Tutorial-Book-v3/chapter0/0intro.html) | RustとRISC-Vで、実行環境から保護、プロセス、ファイルシステム、並行性へ段階的に進む | 実験、演習、段階別実装を本と一緒に提供する好例 |

HinaOSは[著者のサポートリポジトリ](https://github.com/nuta/microkernel-book)も公開されている。rCoreの[実験環境の説明](https://rcore-os.cn/rCore-Tutorial-Book-v3/chapter0/5setup-devel-env.html)も、教材と再現環境をセットで考える参考になる。これらの教材にも実装・実験・設計の価値があり、それらをnihos固有の発明として扱わない。

## 読む価値をどこに置くか

最も有力なのは、画面と入力のある小さな端末を、測定と失敗実験を通して育てる構成である。たとえば「画面更新中に保存すると入力が遅れる」という読者が観察できる問題から、スケジューリング、DMAの所有権、Flash実行制約、コア間協調を学ぶ。個別の問題を、他のOSや組込み機器にも持ち出せる設計原理に戻す。

| 候補 | 強み | 課題 | 位置づけの案 |
| --- | --- | --- | --- |
| Zigでゼロから作るOS入門 | 入り口と完成目標がわかりやすい | 言語とビルド環境の変化への追従が大きく、既存入門とも重なる | 導入の一部 |
| Tab5を使いこなす開発ガイド | 所有者が試しやすく、成果が目に見える | 特定機器の操作手順に寄りやすい | Webの実用ガイド |
| 実機で学ぶ小さなOSの設計 | OS原理と実機の制約を一緒に学べる | native移行と周辺機器の検証が必要 | 書籍の主軸 |
| nihosの開発日誌 | 判断の経緯と失敗を残せる | 開発順は必ずしも学習順にならない | 制作ノートとADR |

Zigは設計を読みやすくする道具として扱う。C ABI、範囲のあるデータ、明示的な失敗、allocatorの選択を説明する一方、言語だけでデータ競合やDMAの安全性が保証されるとは教えない。

ESP32-P4固有の事情も、省略せず範囲を区切って説明する。xv6が使う[Sv39ページング](https://pdos.csail.mit.edu/6.1810/2025/xv6/book-riscv-rev5.pdf)のモデルを、そのままP4のプロセス分離に適用できるとはしない。P4の[データシート](https://documentation.espressif.com/esp32-p4_datasheet_en.html)にあるM/Uモード、実際に使うPMP・割り込み機構、Flash/PSRAMのマッピングを区別する。「MMUがある／ない」という一語でまとめず、仮想アドレス変換と外部メモリのマッピングの違いを説明したい。使用するチップrevisionに合う資料の固定が必要になる。

## 目次案

初版の編集上の目安は本文240〜300ページ程度、12〜16章。以下は学習順の候補であり、実装済みの機能一覧ではない。未実装部分の本文を先に埋めることはしない。

| 部 | 章の候補 | 読者が得る成果 |
| --- | --- | --- |
| 入口 | 動く端末からOSを考える／実験環境と最初の画面／ZigとC ABI | 起動経路と依存関係を説明し、表示を小さく変えられる |
| CPUとメモリ | 有限のメモリ／RISC-Vの例外とコンテキスト／時刻と割り込み／タスクとスケジューリング | スタック切替、待ち、プリエンプションを区別して追える |
| 端末を支えるI/O | キャッシュとDMA／画面と入力／音声と期限／保存と電源断 | データの所有者と寿命を定義し、遅延や破損を調べられる |
| システムを育てる | SMPとメッセージ／資源とアプリ境界／性能を測る／拡張と最初の貢献 | 2コア化の損益を判断し、ひとつの拡張を他人が再現できる形にする |

ページテーブル、fork、TCP/IP、SQLite、Quake、WASMをすべて主線に詰め込まない。ページングはxv6との比較、SQLiteはストレージの発展課題、Quakeは将来の負荷測定というように、学習目的と実装状況に応じて別冊・補足に逃がせる。特にQuake 60 FPSは現在の実績ではなく性能目標である。

入口ではESP-IDFによる起動を明示し、その後でnihosが引き受ける責任を増やしていく。ROMから全てを自作すると受け取れる題名や説明は避ける。native移行の章では、移行前後で誰がタイマ、割り込み、スタック、スケジューラを持つかを具体的に比較する。

## 各章で繰り返す学び方

1. 画面の乱れ、待ち時間、メモリ不足など、観察できる問いを置く。
2. 動く前に結果を予想し、資源の所有者と守る条件を図や表にする。
3. その判断に必要な最小限のコードを読み、実行経路を追う。
4. 指定したバージョンで実験し、結果と条件を記録する。
5. 容量、負荷、優先度など一つの条件を変え、予想との差を説明する。
6. 他の方式との比較と、nihosに持ち帰れる小さな拡張で終える。

説明の単位をソースファイル順にしない。各章には「なぜ必要か」「変更してはいけない条件」「壊れたときの調べ方」「別の方式を選ぶ条件」を持たせる。演習には所要時間の実測、期待される観察、詰まりやすい点、ヒント、解答例を後から付ける。答えが環境に依存する性能問題は、数値の一致より測定条件と説明を評価する。

| 実験の候補 | 学ぶ原理 | 現段階での扱い |
| --- | --- | --- |
| arenaを枯渇させ、失敗時の状態を調べる | 有限資源、境界検査、失敗の原子性 | 今回の試読章で実施可能 |
| 周期tickの回数と経過時間を比較する | 時刻、割り込み遅延、時間管理 | hostとESP-EMUの既存記録から教材化可能 |
| キュー容量を変えて待ちとスループットを測る | 所有権、バックプレッシャー、SMP | hostとESP-IDF実機の基礎記録あり。nativeの待機は別課題 |
| 全画面と部分更新を比較する | 帯域、コピー、フレームの期限 | 既存scanoutを土台に実験設計が必要 |
| 保存を中断し、再起動後の状態を調べる | 永続性、atomic replace、復旧 | ファイルシステム実装と安全な試験手順が必要 |

## 現在のnihosと執筆できる範囲

2026年10月25日の[architecture](../architecture.md)、[ADR](../adr/)、[測定記録](../measurements/)を基準にする。開発が進んだら、この表の更新と章の再検証をセットで行う。

| 領域 | 既存の根拠 | 書籍で守る区別 |
| --- | --- | --- |
| Zig、C ABI、arena、scheduler policy | hostテスト、RV32コンパイル確認 | hostでの正しさと実機の挙動 |
| メモリ、DMA、scanout、touch初期化 | ESP-IDF-hostedなTab5測定 | 描画leaseの操作とnativeドライバ。idle pollと実際の押下操作 |
| CPU0/CPU1リング通信 | ESP-IDF-hostedな実機で10万往復の検査 | throughputとwakeup latency。FreeRTOSの配置とnative SMP |
| コンテキスト切替 | ESP-EMUとTab5の限定した同期切替 | 制御した往復と常時動くnative scheduler |
| native timerとpreemption | ESP-EMUで限定区間の非同期割り込みと2タスク実行 | エミュレータ実行と物理Tab5のpreemption |
| ストレージ、音声、アプリ隔離、native SMP | 設計・今後の実装 | 将来の章候補と読者が再現できる機能 |

現段階では「完成したOSを一冊で作る」本の刊行を約束するには早い。一方、境界・有限メモリ・ABI・実験方法の章は今から育てられる。ADRは設計理由、測定記録は観測条件、本文は読者の理解という役割に分け、同じ文章を三重に維持しない。

## エコシステムへつなぐ仕組み

書籍の読者をカーネル作者だけに限定しない。最初はhostの演習・誤記報告から入り、Tab5での再現、サンプル改良、周辺機器、アプリ、他ボードへの移植へ進める道を用意する。アプリABIやローダが安定するまでは、ファームウェアに組み込む小さなデモを入口にできる。

| 段階 | 読者の成果 | プロジェクト側で必要になるもの |
| --- | --- | --- |
| 読む | 他OSにも通じる概念を理解する | 無料で参照できるWeb本文、用語、図、誤記への恒久リンク |
| 再現する | 同じ入力と条件で結果を説明する | 固定された実習版、host/エミュレータ/実機の手順、既知の問題 |
| 変える | 表示や割当方針を一つ変更する | 小さな演習、ヒント、期待される動作、戻れるチェックポイント |
| 作る | 他人が使えるデモやドライバを作る | 境界が明示されたAPI、雛形、実機互換表、必要なライセンス情報 |
| 返す | 再現報告、測定、修正、翻訳を提供する | issue/PRの雛形、貢献ガイド、難度と必要機材を示した課題 |

上記は導入案であり、公開サイトやSDK、issueラベルはまだ作成していない。成否はダウンロード数だけで判断せず、初回実験の完了率、詰まった箇所、外部の再現報告、初めてのPR、継続的に保守される拡張を観察する。取得するなら本人が任意で報告する方法から始められる。

## monbanの組版から取り入れること

参考にしたのは `~/repo/monban/docs/book/ja` の設定とCSS、章前処理、および演習の分離である。A5、Markdown、techbookテーマ、章順を一箇所で管理する方式、章番号を本文に固定しない運用を取り入れた。コードとCSSはnihos用に独立して記述し、monbanの本文・図・生成物は取り込んでいない。

今回の土台は以下に絞る。

- 日本語のMarkdown原稿と、固定版Vivliostyle CLI・techbookテーマ。
- PDF、Web Publication、プレビューを同じ本文から生成するコマンド。
- 章順から目次と章番号を生成し、未知の参照で停止する前処理。
- 実ソースからの抜粋と、抜粋元のコミット・作業変更の有無を記録する仕組み。
- 企画案と将来の章を、現在読める試読本文から分離する構成。

monbanの索引、Mermaid生成、日英同期、DOCX生成などは、本文が増えて必要になった段階で検討する。英語版は安定した実習単位から段階的に用意する案とし、今回の時点では翻訳一式を作らない。紙面幅で読めるコード量と図の大きさは、実際のPDFで確認する。

## 実装と執筆を同時に進める手順

最初に全目次の空原稿を作ると、未検証の説明が増えやすい。まず三章程度を読み切れる試読版として整え、少人数に実験してもらいたい。今回の試読章は、境界の説明、既存hostテストの再現、arenaの読み解きである。

次の実装区間では、native timerと物理preemptionを優先し、実行経路と復帰条件を記録する。その後、画面・入力・音・保存の小さな一連の操作が成立するたびに、実験と章を完成させる。教材のためだけに汎用QEMU `virt` 用OSを並行開発せず、共通部分はhost、P4のCPU経路はESP-EMU、周辺I/OはTab5で確かめる。

実習版は、将来 `book/v0.x` のようなタグに固定する案とする。各公開版に、ソースのコミット、toolchain、ボードrevision、対応する実験、既知の問題、正誤表を添える。現時点ではタグ作成も公開も行っていない。開発版の仕様変更を、過去の書籍の読者へ無条件に押し付けない。

初版に進む判断は、nativeでの常時タスク実行、入出力、復旧を含む保存、第三者による実習再現が揃ってから行う。執筆を設計の理解を確かめる機会として使い、書きやすさのためにOSの責任境界を曖昧にしない。

## 次に決めたいこと

中心読者をOS自作の初学者とするか、既存教材を終えた読者とするかで、CPUの説明量と実験の深さが変わる。どちらでも実機と設計判断という主軸は保てる。次に、試読版のarena実験と画面を変える実験を読者に試してもらい、どちらが「次も読みたい」につながるかを確かめるのがよい。
