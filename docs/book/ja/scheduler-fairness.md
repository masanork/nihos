# スケジューラは公平か

三つのタスクを順番に選ぶテストは通った。では、優先度の高い仕事がときどき割り込んでも、その順番は保たれるだろうか。

{{ch:task-lifetime}}では、実行を保存する仕組みと、次のタスクを選ぶ方針を分けた。この章では方針に絞り、nihosで実際に見つかった飢餓を追う。飢餓とは、実行できる仕事があるのに、いつまでも順番が来ないことである。小さなモデルによる検証を、手元のOSにも使ってみよう。

## 一回の選択が正しくても

タスクHは高優先度で、短い仕事を終えるとブロックする。タスクAとBは同じ低優先度で、どちらも実行可能なままとする。Hが眠っている間には、AかBを選ぶ機会が必ずある。

旧実装は「最後に選んだスロット」を一つだけ覚えていた。その次のスロットから候補を探すので、同じ優先度のタスクだけなら順番が回る。しかしHも同じ記録を書き換える。スロットをH、A、Bの順に置くと、次の循環ができる。

| 操作 | 最後に選んだタスク | 次に起きること |
| --- | --- | --- |
| Hがブロック中に選択 | A | Aを実行 |
| Hを`wake`して選択 | H | 優先度に従ってHを実行 |
| Hが再びブロック | Hのまま | 探索をHの次から始める |
| 低優先度を選択 | A | Bを飛ばしたまま同じ循環へ戻る |

どの一回を取り出しても、より高い優先度の候補を無視していない。同時に二つを`running`にもしていない。それでもBは選ばれない。高優先度の仕事がCPUを使い切るからではなく、低優先度へ渡せる機会を毎回Aが受け取るからである。

## 守りたい性質を二つに分ける

「同時に二つを`running`にしない」は、どの状態でも破ってはいけない条件である。このような安全性に対し、「実行可能な低優先度タスクにも繰り返し順番が来る」は、状態がどう続くかについての活性の条件になる。

この区別は、テストの書き方にも効く。最初の数回だけを眺めても、後で同じ循環に閉じ込められるかもしれない。逆に、有限回の観測でBが動かなかっただけでは、永遠に動かないとは言えない。そこで、状態と遷移を小さなモデルにして、繰り返される循環を調べる。

nihosの[TLA+モデル](git:d9afd649d8628aedc484bab0d50496942ffdcb5e:formal/scheduler/SchedulerFairness.tla)は、タスクの状態、選択位置、現在のタスクと、Hを起こす・選ぶ・ブロックする操作を表す。レジスタやタイマーは持ち込まない。スケジューラのAPI呼び出しを、一つずつ完了する操作として扱う。

守りたい進捗は「各低優先度タスクが、何度でも再び選ばれる」である。環境の操作自体が止まらないことは仮定するが、タスクを公平に選ぶことを仮定に入れてはいけない。それが、これから調べる性質だからだ。

また、この要求はHが繰り返しブロックする環境に対するものだ。Hが常に実行可能な場合にも低優先度へ時間を配る、という別の方針へ変えたわけではない。

## 修正をモデルと実装へ戻す

修正は、選択位置を優先度ごとに分けることだった。Hを選んでも、AとBの順番を覚えた位置は変わらない。次の低優先度の機会には、Aの次から探してBへ渡せる。

{{figure:priority-cursors}}

図のcursorはqueueの要素ではなく、「前にどこを選んだか」を記憶する情報である。Hを選ぶ操作で低優先度のcursorまで動かしてしまうと、AからBへ進めるはずの記憶が失われる。この例ではHが再びblockし、低優先度を選べる機会が来ることを前提にしている。

モデル検査器TLCで、タスク数を3、4、5に固定して調べた。[実験記録](git:d9afd649d8628aedc484bab0d50496942ffdcb5e:docs/measurements/2026-10-26-formal-scheduler-mvp.md)では、旧方式はすべての条件で飢餓の循環を持ち、優先度別の方式は同じ環境と要求を満たした。状態数を有限にしたことで、各条件の到達可能な状態と循環を調べきれる。

ただし、モデルの成功だけでは、Zigの実装が同じ動きをするか分からない。TLCが出した状態と操作列を取り出し、実際のスケジューラ APIへ順に与える。各操作の後で、選ばれたタスク、全タスクの状態、選択位置を照合する。[対応表と再生の説明](git:d9afd649d8628aedc484bab0d50496942ffdcb5e:formal/scheduler/README.md)には、モデルの番号とZigのスロットの対応も記載している。

さらに、意図的に旧方式へ戻した実装を、修正後のモデルと照合した。これは間違ったタスクを選んだところで拒否される。検証の道具をつないだだけで安心せず、その接続が誤りを見つけられることも確かめる。

## 小さな回帰テストに残す

反例が分かれば、日常の開発で回すテストにも残せる。修正後の実装に加えた検査を見よう。

{{snippet:fairness-regression}}

`lows`に並ぶ三つのタスクを順番に選ぶたびに、Hを起こして実行し、再びブロックしている。単に同じ優先度のタスクを続けて選ぶテストとの差は、この割込み方にある。

モデルは見落としていた循環を探す役に立ち、短い回帰テストはその具体例を日々守る役に立つ。どちらも持つことで、モデルの記述を毎回読まなくても、修正の理由がコードに残る。

## PC上で反例と修正を確かめる

リポジトリのルートから、未使用の名前で別の作業用コピーを作る。元の作業中のファイルはそのままにする。

```sh
git worktree add --detach ../nihos-book-fairness \
  d9afd649d8628aedc484bab0d50496942ffdcb5e
cd ../nihos-book-fairness
sh tools/bootstrap-zig.sh
.tools/zig-0.17.0/zig test src/kernel/scheduler.zig
python3 tools/run-formal-mvp.py
```

モデル検査にはPython 3、Java、curlを使う。既存の実験ではJava 21を用いた。初回は固定版のTLCを取得し、ハッシュを検査する。

最後のコマンドは、旧モデルが期待した活性違反を出すこと、修正モデルが通ること、各実装の再生が一致すること、誤った実装を拒否することまで確認する。途中の`violation`という単語だけで、実験全体の失敗と判断しない。最後の終了状態と`summary.json`を対応づけよう。

まずタスク数3の結果で、Aだけを選び続ける循環を紙に描く。次に回帰テストでHを起こす行を外し、旧方式でも通り得る理由を考える。演習で変更するのは、この作業用コピーだけにする。

## 何を小さくしたかを振り返る

タスク数と環境の順序を固定したので、生成・終了や割込みは含めていない。Zigの全入力列の証明でもない。それでも、実装の誤りを見つけ、再現して修正を確かめられた。待機や通知、保護を加えるときも、原子的とみなす操作と、要求する進捗を決めるところから始めよう。次の{{ch:process-isolation}}では、誰を選ぶかという方針を保ったまま、再開するタスクの権限を変える。公平な選択だけでは、不正なメモリアクセスを防げないことも確かめる。
