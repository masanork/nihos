# CPUとメモリ、機器の仕事を追う

画面のボタンを押すと、数字が一つ増える。その小さな変化にも、入力を知る、数字を計算する、画面用のデータを作る、表示回路へ渡すという仕事がある。どの仕事をCPUが行い、どの仕事を別の回路へ任せるのだろうか。

本書の実験機であるM5Stack Tab5は、CPU、メモリ、画面、入力装置を備えた小さな端末である。これからOSのコードを読む前に、それらのつながりを押さえよう。この章は、特定のTab5の配線や設定値を再現する手順ではない。入力の到着を知り、画面を更新する簡単な機械を模型にして考える。

まずバイトと番地、次にCPUと実行状態、メモリと機器の接続、割込みによる通知、DMAによる転送へ進む。最後に、CPUと転送回路が同じメモリを使うときの注意を調べる。実機は不要で、表に値を書き込むだけでも取り組める。

## バイトを並べ、置き場所に番号を付ける

コンピュータは、情報を0と1の組合せで扱う。一つの0または1がビットであり、本書の機械では8ビットを1バイトとする。8個のビットには256通りの組合せがあるため、符号なしの整数として読めば0から255までを表せる。同じビット列を文字や色として読むこともでき、どう解釈するかはプログラムの約束になる。

メモリを、一列に並ぶバイトの置き場所として考えよう。それぞれの場所に付けた番号が、メモリアドレス、つまり番地である。以下の番地は説明用の架空の値であり、Tab5の実際の配置ではない。

| 番地 | 入っている値（十進数） |
| --- | ---: |
| `0x1000` | 10 |
| `0x1001` | 20 |
| `0x1002` | 0 |
| `0x1003` | 0 |

`0x`から始まる数は16進数である。普段の十進数が0から9を使うのに対し、16進数は0から9とAからFを使う。Aは十進数の10、Fは15に当たり、その次が`0x10`、十進数では16になる。小文字のaからfで書く場合も同じ値を表す。

表の`0x1000`は場所の番号であり、そこに入っている10とは別の数である。「番地`0x1000`を読む」と、値10が得られる。「番地`0x1000`へ11を書く」と、同じ場所の中身が11へ変わる。番地そのものが11へ変わるわけではない。

隣のバイトの番地は1ずつ増える。`0x1000`から、上端`0x1004`を含めない範囲なら、四つのバイトを使える。長さは上端と下端の差で求められる。メモリの「どこから」と「何バイト」を、別々の情報として持つ理由がここにある。

Cなどのポインタも、プログラムが対象を参照するためのアドレスを保持する。ただし、番号を計算できることだけでは、その場所を読んでよいか、必要な長さがあるか、まだ有効かは分からない。これらの条件は後のメモリ管理や保護の章で調べる。

## CPUは命令を読み、値を操作する

CPUは、プログラムの命令を実行する回路である。メモリから値を読む、二つの数を足す、条件によって別の命令へ進む、といった操作を組み合わせて仕事を進める。CPUが実行できる命令と、その動作の規則を命令セットと呼ぶ。本書で使うRISC-Vは、その規則の一つである。

CPUの中には、計算途中の値を置くレジスタがある。先ほどのメモリとは別の置き場所で、命令が計算に使う値や、あるメモリを指すアドレスを保持する。たとえば表示する数字を一つ増やす処理を、次のように追える。この図では、番地`0x1000`の1バイトだけを読み書きする。

{{figure:cpu-memory-steps}}

最初はメモリの値が10である。読出し後はCPUのレジスタにも10が入る。CPUがそのレジスタへ1を足しても、その時点ではメモリはまだ10のままだ。最後の書込みでメモリが11になる。レジスタの中の値と、メモリの中の値を分けて追おう。

メモリからレジスタへ値を取り込む操作をロード、逆にレジスタの値をメモリへ書く操作をストアと呼ぶ。ここでは、命令の細かい記法より、この二つの向きを押さえればよい。

CPUは、どの命令を実行しているかも持つ。RISC-Vのプログラムカウンタ`pc`は、現在の命令のアドレスを表す。普通に次へ進むほか、分岐や関数呼出しによって別の位置へ移る。命令は常に同じ長さとは限らないので、「次へ進む」ときに何バイト増やすかも命令の規則による。

本書で使うRV32では、基本の整数レジスタの幅は32ビット、4バイトである。これはメモリの全容量が32バイトという意味ではない。一つのレジスタの幅、アドレスで表せる範囲、実際に載っているメモリ量は区別する。[RISC-VのRV32Iの説明](https://docs.riscv.org/reference/isa/unpriv/rv32.html)では、レジスタ、`pc`、ロードとストアの規則を読める。

## 関数から戻るための場所を残す

ボタンの入力を処理する関数から、数字を描く関数を呼んだとしよう。描く関数が終わったら、呼出し元のどこへ戻ればよいかを残す必要がある。途中の計算や局所変数にも、呼出しをまたいで残したいものがある。

その保存場所の一つが、メモリ上のスタックである。関数の呼出しに合わせて作業場所を使い、内側の関数が戻ると、その分を戻していく。戻り先や局所変数を実際にどこへ置くかは、コンパイラと関数呼出しの約束による。すべてが必ずスタックに置かれるわけではなく、レジスタで保持できる値もある。

スタックの使用位置を示すレジスタを、スタックポインタ`sp`と呼ぶ。nihosが最初のZigの関数を呼ぶときも、その関数が使える場所を用意してから`sp`を設定する。詳しい配置は後の{{ch:native-entry}}で読む。[RISC-Vの呼出し規約](https://riscv-non-isa.github.io/riscv-elf-psabi-doc/#_integer_register_convention)にも、`sp`や戻り先を扱うレジスタの役割がある。

OSがある仕事を一時停止して別の仕事を進めるなら、最初の仕事のスタックは、その仕事が戻るまで残さなければならない。CPUのレジスタだけを覚えていても、スタックの中身を別の仕事が上書きしたら、同じ場所から計算を続けられない。後のタスク切り替えは、この「途中の状態を残す」という問いを広げたものである。

## 一つの値が、複数のバイトを使う

レジスタの32ビット値をメモリへ残すなら、4バイト分の置き場所が要る。たとえば値`0x12345678`を、下位のバイトから順に置く方式では、次のようになる。

| 番地 | バイトの値（16進数） |
| --- | --- |
| `0x1000` | `0x78` |
| `0x1001` | `0x56` |
| `0x1002` | `0x34` |
| `0x1003` | `0x12` |

このバイトの順序をリトルエンディアンと呼ぶ。値が4バイトを使うことと、どちらのバイトを先に置くかは別の約束である。ここから後の表は、それぞれの例の最初の状態へ戻して読む。

置き始める番地にも条件がある場合がある。4バイト境界なら、番地が4の倍数になる位置を使う。このように位置を指定した境界へ揃えることを整列、またはアラインメントと呼ぶ。使える区画の長さだけでなく、開始位置も確認する理由になる。実際に必要な整列は、命令や転送回路の条件によって違う。

## 番地の先には、RAM以外もある

作業中の値を読み書きするメモリがRAMである。Tab5では、チップ内部のSRAMと、外部に接続したPSRAMを使う。どちらも作業用の記憶で、電源を失った後の保存には使えない。電源を切ってもプログラムやデータを残すためには、Flashなど別の記憶を使う。Flashは、通常のRAMへのストアと同じ方法で自由に書き換えられるものではない。

CPUを初期状態から起動し直すリセットは、電源を断つこととは違う。RAMの内容が残る構成もあるため、起動時に使う変数を初期化する仕事が必要になる。後の起動の章では、その担当も調べる。

さらに、ある番地は機器の状態や制御につながっている。たとえば、ある値を読むと入力が届いたか分かり、別の値を書くと表示の転送を始められる。このように、周辺回路の操作をメモリの読書きと同じアドレス指定で扱う方法を、メモリマップドI/O、略してMMIOと呼ぶ。I/Oは入力と出力を意味する。

CPUやプログラムが使うアドレスの全体を、アドレス空間と呼ぶ。その中のどの番地を何へ割り当てるかの表が、メモリマップである。説明用の機械なら、たとえば次のように割り当てられる。

| 番地の例 | つながるもの | 操作の意味 |
| --- | --- | --- |
| `0x1000`からの領域 | RAM | 作業中の値を残す |
| `0x2000`からの領域 | Flashの読出し窓 | 保存された命令やデータを読む |
| `0x3000` | 入力状態レジスタ | 入力が届いたか調べる |
| `0x3010` | 表示制御レジスタ | 転送の開始などを指示する |

周辺回路にも、状態や制御を扱う「レジスタ」がある。CPU内部の汎用レジスタとは別の回路であり、MMIOの場合は対応する番地へアクセスして使う。機器によっては、別の通信回路を介してレジスタを読み書きする場合もある。

RAMの値は、普通は読んだだけでは消えない。一方、機器のレジスタは、読むと状態が変わったり、書いた値が動作の開始として解釈されたりすることがある。書込みに使える幅も決まっている。読み返せば同じ値が必ず戻る、好きな番地へ好きな幅で書ける、とは考えない。[RISC-Vのメモリの説明](https://docs.riscv.org/reference/isa/v20240411/unpriv/intro.html)も、記憶領域とI/O領域、アクセス時の作用を区別している。

存在しない番地や、許可されていない番地もある。Cのポインタを作れたことと、その先が有効なRAMであることは別だ。具体的なTab5のメモリマップは、後の起動とメモリの章で扱う。

## 入力が届いたことを、どう知るか

ここからは、入力状態を読める架空の機器を考える。CPUが入力状態を繰り返し読み、「新しい入力あり」になるのを調べる方法が、ポーリングである。

単純な方法だが、確認にもCPUの時間を使う。間隔を長くすれば気付くのが遅れ、短くすれば確認の回数が増える。入力を待つ間にほかの仕事を進められるかは、確認の間へどの処理を置くかにもよる。

別の方法として、機器がCPUへ「処理してほしい」と要求を知らせられる構成がある。この割込み要求をIRQ、Interrupt Requestと呼ぶ。要求を受けたCPUが実行中の処理をいったん中断し、設定された入口へ制御を移す仕組みが割込みである。

{{figure:interrupt-request-path}}

図は一つのCPUで、通常の処理と割込み処理を順番に実行する模式図である。入力機器の要求は割込みコントローラを通り、CPUへ届く。コントローラは、どの要求を通すか、どれを優先するかなどを管理する回路だ。Tab5の実際の入力経路や割込み設定は後の章で確かめる。

割込みを受けたときに動く処理を、割込みハンドラ、またはISR（Interrupt Service Routine）と呼ぶ。CPUが原因や復帰位置などを記録しても、作業中のすべてのレジスタが自動的に保存されるとは限らない。nihosでは、入口のコードが必要なレジスタを保存し、処理後に復元して再開する。

この例では元の処理へ戻るが、OSは次に別の仕事を選ぶこともできる。その仕組みは後の{{ch:task-lifetime}}で扱う。ここでは、機器からの要求、割込みを受ける判断、ハンドラの実行、元の仕事の再開を分けて押さえよう。

## 要求が来ることと、すぐ処理することは違う

CPUは準備中や短い管理操作の間、通常の割込みを受け付けない設定にすることがある。これを割込みのマスクと呼ぶ。CPUで割込みをマスクしても、入力装置や転送回路が停止するわけではない。

要求を保留できるか、複数回の発生を数えられるかは、機器やコントローラの仕組みによる。割込みを長く止めても、後ですべての出来事を一回ずつ処理できるとは限らない。ハンドラの実行回数と、実際の入力や転送の回数も分けて調べる。

機器からの割込みとは別に、プログラムがOSを呼ぶ命令を実行したときなど、実行中の命令をきっかけに制御が移る同期例外もある。RISC-Vでは、このような同期例外と、外部要因による割込みを合わせてトラップと呼ぶ。通常の割込みのマスクと、同期例外への対応は別の問題だ。後の{{ch:native-entry}}では、自分で位置を選べる`ecall`という命令を使って、入口と復帰を調べる。

[ESP-IDFの割込みの説明](https://docs.espressif.com/projects/esp-idf/en/v5.4.4/esp32p4/api-reference/system/intr_alloc.html)では、ESP32-P4で要求を接続し、処理を登録する仕組みを読める。nihosのネイティブ経路は、このSDKのAPIをそのまま使う構成ではない。共通する要求と処理の関係を理解してから、機種ごとの接続を見るとよい。

## 画面のデータを、誰が運ぶか

入力を知り、数字を一つ増やせたら、その数字を画面の絵にする。画面を構成する小さな点が画素である。その色を並べたメモリ上の領域をフレームバッファと呼ぶ。バッファは、処理の間でデータを置くための領域を指す。

画素を用意することと、そのデータを表示回路へ運ぶことは別の仕事だ。CPUが一つずつ読み書きして運ぶ方法もある。もう一つ、転送を専用の回路へ任せる方法が、DMA（Direct Memory Access）である。

DMAを使う場合も、CPUの仕事がなくなるわけではない。CPUは使うメモリ、長さ、転送先などを設定し、開始を指示する。転送中はDMA回路がメモリへアクセスするので、その領域を別の用途へ返したり、読出し中の内容を勝手に書き換えたりしてはいけない。

{{figure:dma-control-and-data}}

図では、CPUが開始を指示する矢印と、画素データを運ぶ矢印を分けている。点線は転送完了を割込みで知らせる構成の例だ。転送はDMAの仕事、CPUへ処理を求めるのはIRQの役割であり、同じ仕組みではない。完了をポーリングで調べる構成もある。

また、DMAの読出しが終わっても、後段の表示回路にはデータが残っているかもしれない。転送の完了、領域を再利用できること、画面の最後の画素が見えたことは、それぞれ確認する条件がある。後の{{ch:io-lifetime}}と{{ch:display-handoff}}で、どの段階まで終わったかを追う。

## CPUが書いた値を、DMAも読めるだろうか

CPUとメモリの間には、アクセスを速くするためにデータのコピーを保持するキャッシュがある。CPUがキャッシュを使って書いた値が、メモリ側へまだ反映されていない場合を考えよう。ここでは、DMAはCPUのキャッシュを通らずにメモリを読むものとする。

| 時点 | CPU側のキャッシュ | メモリ側 | この時点でDMAが読む値 |
| --- | ---: | ---: | ---: |
| 両方に同じ値がある | 10 | 10 | 10 |
| CPUがキャッシュ側を更新 | 11 | 10 | 10 |
| メモリ側へ書き戻した後 | 11 | 11 | 11 |

CPUから見ると新しい値なのに、DMAは古い値を読める。キャッシュの変更をメモリへ反映する操作が書戻しである。逆にDMAがメモリへ新しい値を書いた場合、CPUが古いコピーを使い続けないため、キャッシュを無効化する操作が必要になる場合もある。

実際の要否や操作の順序は、使うメモリと回路、キャッシュの仕組みによる。ESP32-P4の[メモリ同期の説明](https://docs.espressif.com/projects/esp-idf/en/v5.4.4/esp32p4/api-reference/system/mm_sync.html)も、CPUとDMAが違う経路を通るときの書戻しや無効化を扱っている。後の{{ch:psram-and-evidence}}では、nihosがどの経路を確認したかを読む。

キャッシュを揃えることと、同時に変更してよい相手を決めることも別である。書き戻した直後に別の仕事が内容を変えれば、転送中のデータは安定しない。必要な順序で値を反映し、使い終わるまで誰がその領域を持つかも決める。

## 一回の操作へ戻る

最初の「ボタンを押すと数字が増える」へ戻ろう。入力状態をポーリングまたは割込みで知り、CPUが数字を計算する。画素をメモリへ作り、必要なキャッシュの操作を済ませ、DMAなどで表示回路へ渡す。それぞれの段階は、異なる回路とプログラムが担当する。

数字が増えなかったら、どの段階で止まったかを調べる。CPUの計算が合っていても、機器へ渡した番地が違うかもしれない。DMAが動いていても、古い値を運んでいるかもしれない。OSの実装を読むときも、このように「誰が、どの値を、どこからどこへ動かすか」を追っていこう。

## 紙の上で確かめる

1. 最初の表で、`0x1000`へ11を書いた後、`0x1001`を読むと何が得られるだろうか。
2. CPUが値10をロードし、レジスタだけを11にした。まだストアしていないとき、メモリ側はいくつだろうか。
3. CPUで通常の割込みをマスクした。DMAが使っている領域を、直ちにほかへ貸してよいだろうか。
4. キャッシュの表の二行目でDMAを開始したら、11が転送されると期待してよいだろうか。

答えを確かめよう。1は20で、別の番地の内容は変えていない。2は10で、レジスタの更新とメモリへの書込みは別である。3は貸してはいけない。CPUが要求を受けない設定と、DMAの停止確認は違う。4は、この表の条件では10が読まれるので、11の転送を期待できない。
