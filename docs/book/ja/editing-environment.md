# 文字を描くところから、編集する環境へ

文字を描けるようになったら、次は文章を直したくなる。だが、キーを受けて画素を書き換えるだけでは、変換中の読み、取り消した編集、保存前の文章を扱えない。画面にあるものと、文書として保持するものを分ける必要がある。

この章は、一行のASCII編集の実験から、文書、組版、日本語入力を分けたXYの共通コアへ進み、Tab5とMacの共通描画へつなぐ。{{ch:japanese-fonts}}で扱ったFreeTypeとHarfBuzzの実験に加え、後から着地した独自のフォント読取りと描画の実装を扱う。初期の参照版`980f522`と、後の統合版`9208c4e`を分け、それぞれの到達点と予算を保ったまま比べよう。

## 一行だけなら、何を確かめられるか

最初の実験は80バイトまでの印字可能ASCII一行である。左右移動、挿入、Backspaceを受け、変更した行を描き直す。固定した操作列を作れば、編集後の文字列と画面を予測できる。

[HID入力の実験](git:980f522a3575c3922b956bf97f46a228b557070d:docs/measurements/2026-10-29-editor-hid-fixture.md)では、キーの押下と解放を表す疑似データを、モデル化したI2C経由でTab5のキーボードドライバへ渡した。ドライバ、HIDの解釈、行の編集、コンソール描画までをRV32上で動かし、三つのフォントの最終画面を独立した画素の参照値と比べた。物理I2Cや実キーボードを試した結果ではない。

次に、ブラウザのキーをデバッガの受付領域からRV32へ渡す対話実験を作った。各入力でゲストを止めて再開し、そのフレームバッファを読む。[七つの途中画面の検査](git:980f522a3575c3922b956bf97f46a228b557070d:docs/measurements/2026-10-29-editor-live.md)では、操作ごとに画素と領域末尾のguardを照合した。部分描画と全描画の比較に加え、別に定めた参照値とも比べる。両方の描画が同じ誤りを持つ場合に備えるためである。

ホストのファイルを開く機能では、改行、ASCII以外、80バイトを超える入力を現在の行を変える前に拒否する。ブラウザの保存先選択を使える場合はそこへ書き、使えなければコピーをダウンロードする。後者では、文書を保存済みにしない。コピーの出力と、編集中の文書を対応するファイルへ保存したことを分ける。

これは操作と描画を観察する小さな実験である。デバッガ経由の遅延を端末の応答性能として扱わず、ホストのファイル保存をTab5のSD保存としない。手順と制限は[シミュレータの説明](git:980f522a3575c3922b956bf97f46a228b557070d:docs/development-simulator.md)にある。

## バイト、文字、画面の一文字は一致しない

ASCIIでは一バイトずつ動かしても困りにくい。UTF-8では「か」だけで三バイトある。その途中にカーソルを置けば、文字として読めない列に分断する。

さらに、「か」と結合濁点を組み合わせた「が」は二つのUnicode符号位置、六バイトだが、一まとまりとして消したい。「葛」に異体字セレクタU+E0100を付けた列は七バイトで、字形の指定まで一緒に保持したい。利用者が一まとまりと感じる文字の境界を、書記素クラスタの境界と呼ぶ。

[XYの文書実装](git:980f522a3575c3922b956bf97f46a228b557070d:src/xy/document.zig)は、UTF-8の正本を持ち、カーソル移動と削除を、このようなまとまりに合わせる。異体字セレクタ、結合濁点、ZWJという連結用符号に対応する限定した規則であり、Unicodeのすべての書記素境界規則へ適合したと主張するものではない。

| 対象 | 保持する単位 | 例 |
| --- | --- | --- |
| 保存・通信 | バイト列 | UTF-8の七バイト |
| 文字の識別 | Unicode符号位置 | 葛と異体字セレクタ |
| 編集の移動・削除 | 対応範囲の書記素クラスタ | 二つを一緒に扱う |
| 字形選択 | フォント内のglyph番号 | 指定に対応する異体字 |
| 描画 | 画素と位置 | maskと配置座標 |

見えている一文字から、この表を逆に一意にたどれるとは限らない。文書の位置を画面の列数で保存せず、編集する列の境界と照合する。

## 変換中の読みを、本文へ混ぜない

日本語入力では、読みを打ち、候補を選び、確定するまでに画面が何度も変わる。候補を眺めただけで本文へ書き込むと、取消しやUndoのたびに中間の文章を戻す仕事が増える。

XYは変換中の文字列をPreeditOverlayとして保持する。preeditは未確定入力のことで、本文の上に重ねて表示し、確定時に文書を編集する。SKKは読みの入力と候補の選択を操作で切り替える日本語入力方式で、この実装はローマ字からかなへの変換、送り仮名、候補列、取消しを扱う。

{{figure:editor-document-flow}}

候補の取得口を外へ分けると、異体字、漢字の構成、辞書などを同じ入力欄から問い合わせられる。共通コアは候補列を受け取り、ホスト側がDBを検索する。コールバックという、呼出し元が渡した関数の入口を使い、文書自身へSQLやOSのファイル処理を埋め込まない。

実装にはSKKの学習通知もあるが、通知が出たことと学習結果が媒体へ保存されたことは別である。単体テストの候補提供関数と、実DBの問い合わせ、Tab5の保存サービスへの接続を区別しよう。

## 文書と配置を分ける

編集の正本は文書として保持し、画面へ出す範囲から配置を作る。{{ch:text-layout}}で追った書記素、行分割、ルビとDisplay Listは、文書を直接画素に塗らずに組み直すための仕組みである。幅や方向が変われば配置を再計算しても、元の文書は変えない。固定長の出力領域には上限があり、全文書を一度に無制限に展開しない。

## 大きいフォントを、必要な部分から読む

独自の[フォント実装](git:980f522a3575c3922b956bf97f46a228b557070d:src/graphics/ttf.zig)は、オフセットと長さを指定して読む入口を持つ。ファイル全体をRAMへ載せず、文字からglyphを選ぶ表や、そのglyphの輪郭を必要に応じて読む。メモリ上のテスト用フォントと、ホストのファイル読取りを同じ入口に接続できる。

複数のフォント層があるときは、まず全層から異体字セレクタ付きの対応を探し、見つからなければ基底文字を探す。本体側で「葛」が見つかっただけで探索を終えると、拡張層にある指定字形を見落とすからだ。

輪郭を保持するcacheと、サイズ・向きに合わせた画素を保持するcacheも分ける。輪郭が残っていれば、文字サイズを変えても同じ輪郭を媒体から読み直さずに画素化できる。ただし、cacheから追い出された字形まで読取りゼロになる保証ではない。

この実装はTrueTypeの輪郭や深さ一段の限定した複合glyphを扱い、対応しない変換にはエラーを返す。FreeTypeやHarfBuzzの広い機能を置き換えたと判断せず、読める形式、字形選択、組版、hintingの有無と出力を揃えて比較する。前章のライブラリ実験のstackや割当量も、独自実装の測定値には流用しない。

## ヒープを使わなくても、領域は必要になる

[設計文書](git:980f522a3575c3922b956bf97f46a228b557070d:docs/planning/xy-architecture.md)は二段cacheを512 KiBの枠で考えている。一方、[初期のC ABIホスト構成](git:980f522a3575c3922b956bf97f46a228b557070d:src/xy/c_abi_host.zig)は、bitmapを256枠、一枠96×96バイトで確保する。画素配列だけで2,359,296バイト、2.25 MiBである。さらに256枠の輪郭、管理情報、文書、Undo、作業領域がある。

これはホスト用の固定構成であり、Tab5の実測resident量ではない。動的なヒープ割当てがなくても、静的領域とstackを消費する。設計目標、型が予約する量、実行時に使った量を揃えずに「512 KiBで動く」と書くことはできない。

## S式で、編集の操作を呼ぶ

S式は、括弧で囲んだリストとして式を表す記法である。XYには、例えば次のように、編集操作や表示設定を呼ぶための評価器がある。

```scheme
(buffer/insert! "が")
(view/set! #:size 28 #:direction 'vertical)
(buffer/undo!)
```

これは初期の`scheme_bridge.zig`で対応する操作を示す例であり、シェルへそのまま貼る実習ではない。評価器はScheme風の限られた式と操作を実装している。一般的なScheme処理系の全機能や規格への適合、任意の式を安全に実行する隔離環境が完成した意味ではない。

関連する複数の変更をUndoの一単位へまとめ、設定には世代付きの履歴を持つ。一つ前へ戻す操作はあるが、この版の設定履歴はメモリ内である。DBへ永続化するトランザクションや、再起動後の復旧と同一視しない。SQL問い合わせも外部hookとの接続口を備え、単体テストには模擬の結果を使う。

後の統合版には、定義とクロージャを保持する別の`scheme_runtime.zig`がある。クロージャは、関数と、その関数が参照する周囲の変数を結び付けた値である。関数を一回呼んで終わる操作から、後で何度も呼べる編集コマンドへ進む。対応する式や上限、保存方法は{{ch:live-editing}}で扱う。初期の表示操作用の式が、別の評価器でもそのまま使えるとは考えない。

## 同じ文書から、同じ画素を作る

共通コアには文書、入力、組版、描画のホストテストがあり、C ABIの入口とmacOSのCocoaホストも着地した。C ABIは{{ch:c-library}}でも扱う、言語の間で関数やデータの渡し方を合わせる契約である。Cocoaホストはフォントをファイルから読み、ホストのSQLiteで辞書DBを読み取り専用に開く実装を持つ。

[後の描画統合](git:9208c4edad1c78eb3e2f5942a530fb67979fa675:docs/measurements/2026-10-31-xy-native-pixel-landing.md)では、Macとnativeで文書、拡張されたSchemeの実行系、表示設定、描画セッションを共通にした。MacでもOS標準の文字描画へ渡さず、同じ字形選択、組版、ラスタライズ、RGB565合成を通す。MacのRGBA画像は、完成したRGB565から展開する。nativeで回転した画像とMacの論理座標の画像を同じ向きに揃え、全画素を比較する。

これで、文書が合っているのに片方だけルビや背景色が違う、といった接続の誤りを検査できる。共通の描画器に同じ誤りがあれば一致するので、全画素一致だけで字形や組版の正しさを決めない。既存の独立した参照値のテストも残す。

英数字にはSource Code Pro Mediumから作った「Nihos Code」という小さいフォントを使う。元のフォントとライセンス、再生成手順を保持し、ASCIIの印字可能な95文字を複数サイズ・両方向で比較した。収録データは10,184バイトで、25px時の送り幅は15pxである。日本語は両ターゲットとも同じ復旧用のBunsen字形を使う。大きい外部フォント一式と、実機に載る限定した字形群を同じ収録範囲だと扱わない。

ホストのウィンドウはCocoaを使う。この記録の時点ではGPUI実行の証拠ではない。後には別のGPUIホスト実装も追加されたが、同じ実機候補を検証したという意味ではない。また、この記録の表示範囲はカーソルに追従する240 glyphの窓であり、文書のバイト上限とは別の制約である。

## ASCIIは通るのに、日本語が入らない

[RAM文書の起動試験](git:9208c4edad1c78eb3e2f5942a530fb67979fa675:docs/measurements/2026-10-31-xy-ram-startup.md)では、ASCIIの入力は通ったが、異体字セレクタを含む入力は文書へ入らなかった。七バイトを受信したというカウンタだけが進んだ。

C側の入力関数は、バイトのほかに「入力なし」やエラーも整数で返す。バイトを通す入口と、符号付きの戻り値を区別する必要がある。失敗した候補の機械語を調べると、上位ビットが立つUTF-8を受ける分岐が残っていなかった。修正版は整数が0〜255の範囲かを検査し、ビット列を保ってバイトへ変換する。

ホストでは全256値と範囲外の整数を調べ、実機ではIVSの挿入と一まとまりの削除を確認した。この候補で観察したコード生成の問題を、処理系全体の一般的な不具合へ広げない。「受信した」「文書へ入った」「表示された」の三つを別に記録したことが、調べる境界を絞る助けになった。

## 呼び出すスタックも、実行状態に含まれる

日本語の描画を実機へつなぐと、別の問題も現れた。[初期の実機統合](git:9208c4edad1c78eb3e2f5942a530fb67979fa675:docs/measurements/2026-10-31-xy-native-render.md)では、PSRAMの描画用スタックでタイマー割込みを受けたとき、保存先の範囲検査で停止した。SPだけを切り替え、スケジューラが記録するbootstrapのスタック範囲を変えていなかったためである。

修正版は、SPと実行イメージの範囲を短い割込み禁止区間で揃え、描画中は割込みを再開する。戻るときも元の範囲とSPを揃える。次の候補でSchemeの再帰制限試験がスタックのガードへ達した問題は、大きい値の複製を減らして修正した。深さの上限を決めても、各段の使用量を測らなければ、スタックの収まりは分からない。

最終統合のtrace候補では、日本語、縦横、文字色と背景色、サイズ変更を実機で動かし、描画スタックの最大観測は131,072バイト中77,936バイト、ガードは保持された。最大観測値を最悪時の必要量へ置き換えない。主SRAMヒープの予約区間も49,216バイトで、既存の49,152バイト基準に対する余裕は64バイトしかなかった。

シリアル入力による編集やScheme操作は実機で確認し、利用者から英語と日本語が読めるとの目視確認も得た。実キーボード、全収録文字、冷電源投入、SDへの文書保存は別の確認である。描画の途中を見せない変更と、その資源の費用は{{ch:display-handoff}}へ戻って読むとよい。

## 本を読み、編集へ戻る

後の[Tab5読書画面](git:87b957ac4e6bdf3d62739d10542e0d54c3b14898:docs/measurements/2026-10-31-xy-tab5-reader.md)は、本棚から本と章を選び、文字サイズや縦横を変えながら読む。実機で本文表示とタッチによる本の選択が利用者に確認された。変更後は現在のページ先頭のUTF-8位置から組み直す。読書画面は閲覧専用で、編集中の文書とUndoを別に保持する。

この試験では設定や読書位置の再起動後の永続化、実機でのSVG図の表示を確認していない。本を開けたことから、保存、すべての書籍や字形、あらゆるタッチ操作の完成までは導けない。

## PC上で、一行から確かめる

```sh
git worktree add --detach ../nihos-book-editor \
  980f522a3575c3922b956bf97f46a228b557070d
cd ../nihos-book-editor
sh tools/bootstrap-zig.sh
.tools/zig-0.17.0/zig test src/xy/document.zig
```

最初は文書だけのテストで、異体字セレクタと結合濁点を途中で分けない例、古い版の編集要求を拒否する例を読む。模擬入力を含む共通コア全体は`zig build test`で試せる。

一行の対話実験には`sh tools/nihos-dev.sh canvas-live`、固定操作の再生には`sh tools/nihos-dev.sh editor-live-check`を使う。こちらはESP-EMUとRISC-V GDBなどを要する。ブラウザへ読み込む文章が実験ログや画像に残る場合があるため、試験用の文章を用意しよう。

演習では「葛＋異体字セレクタ」と「か＋結合濁点」を並べ、バイト境界と削除単位を紙に書く。次に、変換中に取消す場合、確定してからUndoする場合、保存後に再起動する場合に、戻すべき状態と保持する場所をそれぞれ挙げる。最後の保存を実機へ結ぶための条件は、{{ch:sqlite-persistence}}で扱う。
