# ICカード端末としてつなぐ

カードを置き、本体で操作し、結果を画面に出して、最後に消す。この短い操作の裏では、USB、カードへのコマンド、入力、文字、画像、メモリの回収がつながっている。

この章では、これまでの仕組みを一つの端末の事例として読み直す。実機で四情報と顔写真を表示し、消去まで確認したマイナンバーカードの経路を中心にする。実習では実カードやPINを使わず、ホストの状態遷移と架空データのテストを読む。

## 最初に、どこまで届いたかを分ける

端末はUSBでカードリーダーと話し、リーダーは近くに置かれたカードと話す。USBの接続が見えたことは、カードの応答やカード内のデータを読めたこととは別の段階である。各段階で相手と成功条件を確かめる。

USB機器が列挙できても、カードが読めるとは限らない。readerと話すための形式がCCID、その先のカードへ送るコマンドがAPDUである。カードが応答しても、欲しいアプリケーションへ入れるとは限らない。読めたデータが正しく表示されても、その発行者の署名を確認したことにはならない。

| 段階 | 確かめる対象 |
| --- | --- |
| USB列挙 | descriptor、interface、endpoint |
| CCID | readerとの要求・応答、slotの状態 |
| カードの起動 | ATRなど、カード側の応答 |
| APDU | 選択したアプリケーションの要求と結果 |
| データの解釈 | 長さ、tag、文字、画像の形式 |
| 端末の完了 | 表示、通信の終了、秘密と画素の消去 |

[最初のUSB実機試験](git:a25ad6a0405733136be7e83efedee899e8d34a04:docs/measurements/2026-10-26-tab5-native-usb-ccid.md)では、PaSoRiを列挙し、CCIDのslot状態を三回問い合わせた。返事はカード不在だった。そこでの成功はreaderとの通信までで、カード起動やAPDUの結果ではない。

後の[PINなしの読取り](git:a25ad6a0405733136be7e83efedee899e8d34a04:docs/measurements/2026-10-26-tab5-native-jpki-pinfree.md)では、カードを起動し、許可したAPDUだけを使って証明書の先頭を読んだ。PINの残り回数も前後で照合した。証明書の一部が読めたことは、署名、証明書チェーン、有効期間を検証したこととは異なる。

## USBの成功を、次の層の成功にしない

USB転送では、controllerが読めるdescriptorとbufferを用意し、endpointの状態を進める。CCIDでは、messageの長さとsequenceを照合する。その先のカードは、APDUの末尾のstatus wordで結果を返す。

途中のどこかが失敗したら、先へ進めない。USBが送信を終えたことを、VERIFYが受理されたことへ変換してはいけない。逆にUSBの応答が失われても、カード側では処理済みかもしれない。この不確かさが再送方針へ影響する。

最初のnative USB実装は、通常のタスクを動かす前の限定したprobeだった。readerの列挙と停止が動いても、長時間使うUSBサービス、hub、任意機器の切断回復を全部実装したことにはならない。上位の利用場面を増やすたびに、必要な寿命と失敗経路も増える。

## 入力を受け取る画面と、送る権限

画面から数字が届いたら、そのままカードへ送る設計は単純だ。しかし画面が切り替わった後の入力や、前のカードで表示した確認ボタンが、次のsessionへ作用してはいけない。

[カードサービス](git:a25ad6a0405733136be7e83efedee899e8d34a04:src/card/service.zig)は、sessionと要求tokenを照合する。送信前に残り回数を再確認し、変化や不明な応答があれば、保留中のPINを捨てる。入力画面の状態だけで、カードへ送る許可を決めない。

同じ確認ボタンを押したつもりでも、古いsessionのtokenなら拒否する。これは{{ch:task-lifetime}}の世代番号や、{{ch:io-lifetime}}の古い完了を拒む仕組みと同じ問題である。

## 返事がないとき、同じ要求を送ってよいか

通信の再試行は便利だが、すべての要求へ同じ方針を使えない。PINを含むVERIFYは、相手に届けば試行回数へ影響し得る。応答が失われたときに、送信失敗と決め付けて同じ要求を再送してはいけない。

[送信側のpolicy](git:a25ad6a0405733136be7e83efedee899e8d34a04:src/card/wire_policy.zig)は、許可するコマンドの形と、認証要求の一回分の予算を管理する。予算は送信を試す前に消費する。上位の状態機械が誤って再び要求しても、同じsessionで二回目を通さない。

応答が失われた、形式が壊れた、結果を決められないという場合は、結果不明として終了へ進む。残り回数を以前の値のまま表示し続けることも避ける。{{ch:durable-storage}}でsyncのエラーをrollback済みと断定できなかったように、返事がないことから相手の処理結果は決められない。

取消しが送信前なら、保持中のPINを消して送信しない。送信中なら、画面を閉じる操作だけで転送bufferを解放せず、transportが手を離すまで待つ。この境界は、前章までのI/Oの寿命をそのまま使う。

## 読めた値を、いつ表示するか

複数の項目を読む場合、先に読めた項目を直ちに公開すると、後で失敗したときに利用者から見える状態が増える。service内部で保持する値と、表示へ出してよい値を分けたい。

この実装では、読取り後にカードへの電源停止や明示的な電源切断を確かめ、秘密のbufferを消してから結果を公開する。cleanupの失敗を、読取り成功の陰へ隠さない。

顔写真の解釈だけが失敗した場合はどうするか。既に検証した四情報を、正常なcleanup後にだけ表示する経路はある。一方、cleanupに失敗した場合や切断で状態が不明な場合は、その部分結果も出さない。途中まで読めたことと、途中まで公開してよいことは違う。

## 画像の移植は、割当器の試験にもなる

顔写真は圧縮されたまま画面へ置けない。JPEG 2000のdecoderに入力を渡し、RGB565へ変換する。このときCライブラリの作業領域、出力buffer、スタックが必要になる。

{{ch:c-library}}の所有者と割当上限を、別のCライブラリでも使う。画像の寸法、入力長、出力範囲を検査し、容量を超える要求を拒否する。合成した画像でreferenceと画素を比べ、不正な入力、前後のguard、容量不足も試す。

[顔写真表示の記録](git:a25ad6a0405733136be7e83efedee899e8d34a04:docs/measurements/2026-10-27-native-card-overview.md)には、領域を存在しない所有者へ割り当てようとして止まった初期候補がある。呼出し元のidentityは、形だけ合う値を作ればよいものではない。動作中の所有者の寿命へ結び付け直してから、decoderの自己試験へ進めた。

## カードの問題に見えた、画面の問題

同じ試験では、本体での確認操作後に表示DMAのエラーも起きた。古いログにはカードの処理段階が足りず、その時点で認証要求が送られたかを決められなかった。残り回数が変わっていないという後の観測だけでも、過去に一度も送らなかった証拠にはならない。

修正ではdescriptorのcacheとaliasの扱いを見直し、認証要求を一切出さずに、入力数だけを変える合成画面を480フレーム以上動かす検査を先に置いた。通信と表示のどちらで壊れたかを分けるためである。

さらにデータ形式の解釈にも不具合が見つかり、合成応答で再現した。各段階の成功・失敗だけを残し、PIN、APDU本文、個人の属性や写真をログへ出さずに、失敗した場所を識別できる記録へ変えた。

観測を増やすときにも、何でも記録すればよいわけではない。必要なのは、次の判断を変えられる情報である。

## 表示した後も、完了ではない

修正後の同じ候補で、四情報と写真の読取り、decode、正常な通信終了が通り、利用者が組み合わせた表示を確認した。その後のDONE記録では、画面と写真の作業領域の消去も確認した。

ここでは、ソフトウェアが結果を渡した記録、人が読める表示を見た観測、終了後に領域を消した記録がそれぞれ必要だった。表示が出た瞬間に採取を終えると、最後の回収を確かめられない。

後続の自動readerでは、カードの挿入・抜去の案内を変えるたびにpanel全体を再初期化し、画面が一瞬暗くなる問題もあった。[案内画面の修正](git:a25ad6a0405733136be7e83efedee899e8d34a04:docs/measurements/2026-10-27-native-card-notices.md)は、非表示側のbankを作り、frame境界で参照を切り替える方式にした。この修正候補はホストとビルドまでの記録で、実機のちらつき解消を確認した結果としては扱わない。既存の光学的な成功を、後から作った候補へ移さないためである。

## 読取りと、発行者の検証

[免許証対応の後続実装](git:a25ad6a0405733136be7e83efedee899e8d34a04:docs/measurements/2026-10-27-native-licence-v2.md)では、従来のIC免許証とマイナ免許証のprofile、変更履歴、外部鍵による署名検査を分けた。しかし既定の発行者鍵bundleは空で、合成署名の検査と実カードの発行者署名の検証は別の段階にある。

署名検査が実装されていても、何が署名対象か、どの鍵を信頼するか、変更履歴がその範囲に入るかを確認しなければならない。本章の実機表示は、発行者の信頼性まで確認した端末の実証ではない。表示に載せる状態の言葉も、確認した範囲へ合わせる。

## PC上で、遅い応答を次のカードへ渡さない

```sh
git worktree add --detach ../nihos-book-card \
  a25ad6a0405733136be7e83efedee899e8d34a04
cd ../nihos-book-card
sh tools/bootstrap-zig.sh
.tools/zig-0.17.0/zig test --dep ccid \
  -Mroot=src/root.zig -Mccid=src/usb/ccid.zig \
  --test-filter 'lost, malformed or indeterminate' \
  --test-filter 'late completions and old UI' \
  --test-filter 'photo parsing failure'
```

この版では`ccid`が独立したmoduleなので、単独の`zig test`にも依存の指定が必要になる。全体を試す場合は`.tools/zig-0.17.0/zig build test`がこの設定を行う。

[サービスのテスト](git:a25ad6a0405733136be7e83efedee899e8d34a04:src/card/service_test.zig)は架空の値と模擬transportを使う。最初に、認証結果が不明な場合に次のVERIFYを出さないことを読む。次に、古いUI入力と遅い完了を新しいsessionへ渡し、何を照合して拒否するかを追おう。

演習では、写真の解析に失敗した後、cleanupが成功する場合と失敗する場合について、四情報、PIN buffer、表示許可の状態を表にする。利用者が途中でカードを外した場合も一行加えてみよう。

一つの端末を作ると、CPU、メモリ、通信、入力、保存、表示を別々に理解するだけでは足りなくなる。どこを完了と呼ぶか、何を次へ渡し、何を消すかを決めることが、OS全体の設計になる。
