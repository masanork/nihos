# 通信相手は、別の計算機

画面にIPアドレスが出た。ところが、しばらくして相手の無線チップだけが再起動した。画面のアドレスをそのまま残してよいだろうか。再接続を待つ間、キー入力や表示は止まってしまうのだろうか。

{{ch:messages-and-waits}}では、同じP4の別CPUへ仕事を渡した。この章では、独立して起動するESP32-C6との通信を考える。接続を始めることに加え、返事を待ち、古い結果を捨て、やり直せる状態へ戻ることがOSの仕事になる。

## 二つのチップで、どこまで分担するか

Tab5では、P4が画面とアプリケーションを担当し、C6が無線を担当する。本章で読む実装は、C6に工場出荷時のESP-Hosted 1.4.1を残し、P4側からSDIOで制御する。P4の二つのCPUとは異なり、両チップが同じメモリを共有しているわけではない。

```text
P4の通信サービス
  ├─ 設定と接続状態、DHCP、IPv6
  ├─ Wi-Fiの制御要求とEthernetフレーム
  └─ BLEのHCIコマンドとイベント
                 ↓ SDIO
C6の既存ファームウェアと無線回路
```

分担には選択肢がある。C6へTCP/IPやBluetoothの上位処理まで任せれば、P4の担当を減らせる。一方、相手のファームウェアに必要な機能とAPIがあることが前提になる。本章の構成では、DHCPや限定したIPv6処理をP4に置く。Wi-Fiの接続とBluetoothの探索が動くことから、ソケット、TCP、TLS、GATTまで使えるとは判断しない。

[接続方式の判断](git:94c03aae4198a4a32f03601e362fa10ea86f39b3:docs/adr/0043-c6-network-offload.md)と実装を比べると、目標と、その時点で相手に任せられた仕事の違いも読める。

## 一回の呼出しで、接続完了まで待たない

無線チップの起動、SDIOの準備、制御要求への応答、APへの接続、DHCPによる取得は、それぞれ待ち時間を持つ。これを一つの関数の中で最後まで待つと、相手が黙ったときに呼出し元まで動けなくなる。

[通信サービス](git:94c03aae4198a4a32f03601e362fa10ea86f39b3:src/platform/native/network_service.zig)は、開始と反復する処理を分ける。呼び出す側は通常の実行文脈から`poll`を繰り返し、通信側は進行状態と期限を保持する。送れなかった出力も次回へ残す。これは一回ごとの仕事を分ける設計であり、実機上の処理時間が常に一定という保証ではない。

送信枠が空いていなければ、今は送らずに戻る。要求を送ったら、対応する応答か期限を待つ。無関係なイベントが届いたことを、その要求の成功として扱ってはいけない。UIDやメッセージ番号を照合し、状態を進める根拠を一つずつ決める。

通信が進む間にも、表示と両CPUのタイマーが進むかを観測する。「通信が成功した」と「ほかの仕事を妨げずに成功した」は、異なる問いである。

## レジスタは、書いた値を覚えているとは限らない

実機で最初に止まったのは、C6へ準備完了を知らせるdoorbellだった。CMD52の書込みにエラーはなかったが、読み返した値は0だった。実装は書いた1が戻ることを要求していた。

設定値を保持するレジスタと、書込みを契機に動作して自動的に消える通知用レジスタでは、確かめるべきことが違う。修正では、通常の設定用書込みの厳密な照合を残し、doorbellだけは転送エラーを検査してC6からのINITを待つ形にした。[実機記録](git:94c03aae4198a4a32f03601e362fa10ea86f39b3:docs/measurements/2026-10-27-c6-hosted-device.md)には、修正前の停止も残っている。

読返しが一致しないとき、検査を丸ごと外す前に、そのレジスタの意味を考えよう。転送が受理されたこと、状態が保持されたこと、相手が処理したことを、別の観測で確かめる必要がある。

## アドレスには寿命がある

DHCPでは、Offerを受け取っただけでアドレスを確定しない。自分のtransaction ID、MACアドレス、選択したサーバー、要求した値に対応するACKを受けて初めて取得済みにする。

取得後も仕事は続く。T1で更新を始め、T2では再バインドへ進み、有効期間が尽きたらアドレスを使う権利を失う。切断やNAKの後に、以前のアドレスを使った送信だけがキューに残ることも避けたい。

| 出来事 | 状態として必要な判断 |
| --- | --- |
| 適合するACK | アドレスと期限を採用する |
| 別のtransactionへのACK | 現在の要求を完了させない |
| 更新待ち | 期限内の状態と再試行を管理する |
| 失効・NAK・切断 | アドレスと保留出力を失効させる |
| C6の再起動 | 古い通信の状態を捨てて取得をやり直す |

[実機の更新・復旧試験](git:94c03aae4198a4a32f03601e362fa10ea86f39b3:docs/measurements/2026-10-27-network-lease-device.md)では、診断用に早めた更新要求へ本物のDHCPサーバーがACKを返した。その後C6だけをリセットし、アドレスの失効と再取得を確認した。200秒の採取中、P4の起動は一回で、画面と両CPUのタイマーは進み続けた。

これは自然なT1まで待った長時間試験ではない。更新のタイマー判断はホスト、実サーバーとのACKと制御した再起動は実機、というように観測を組み合わせる。通信相手が戻ってこない場合も、P4が動き続ける設計にしたい。

IPv6では、link-localの重複検査が終わった状態と、ルーターからの通知によって外部へ通信できる状態も分ける。[link-localの実機試験](git:94c03aae4198a4a32f03601e362fa10ea86f39b3:docs/measurements/2026-10-27-native-ipv6.md)では準備完了後のEchoが5回とも応答したが、APからRAを受けなかったため、グローバルIPv6の実証には進んでいない。

## Bluetoothも、要求と完了を対応づける

BLEでは、ホストとコントローラーの接続口であるHCIを通して初期化し、受動的な広告探索を行う。コマンドを無制限に送らず、相手が示す発行可能数、creditを使う。送信した時点の小さい処理を見よう。

{{snippet:ble-command-sent}}

この処理は一つのcreditを消費し、待機中であることと期限を記録する。対応する完了イベントが来なければ、次の状態へ進まない。探索時間を過ぎたときも、停止コマンドを書くだけで終わりにせず、停止の応答を待つ。

実機では、工場出荷版にはBluetoothを有効にする新しいRPCが存在せず、既に起動時に有効だった。また、C6から受け取るHCIの種別はpayload内、C6へ送る種別はHostedのheader内に置かれていた。送受信を同じ形式だと考えた実装では探索が進まなかった。

[後続の記録](git:94c03aae4198a4a32f03601e362fa10ea86f39b3:docs/measurements/2026-10-27-default-connectivity-devices.md)では、Wi-Fiとともに広告88件を受信し、探索停止の応答まで確認した。この数は異なる機器の台数ではない。資格情報がない構成でもBLE探索は動き、Wi-Fiは未設定のままだった。ドライバがあること、設定済みであること、接続済みであることを区別すると、状態表示も正確になる。

## コラム　時計が返事をしても、時刻は正しいか

通信の期限には経過を測る時計が必要で、利用者に日時を示すにはカレンダーが必要になる。両者を一つにすると、日時の補正が待機期限へ影響する設計になりかねない。

Tab5のRTC、RX8130CEはI2Cへ返事をし、秒も進んでいた。しかし曜日レジスタの値`0x14`には二つのbitが立っていた。このRTCの曜日は一つのbitで表すため、その読み値を有効な日時としては採用しなかった。

[RTC実装](git:94c03aae4198a4a32f03601e362fa10ea86f39b3:src/board/tab5/rtc.zig)は、BCD、日付の範囲、曜日、低電圧と停止の状態を検査する。読めたことと、日時として使えることを分ける。起動時に勝手にビルド日時を書けば、問題を隠し、別の電源やバックアップの方針まで変更しかねない。

カレンダーの設定には明示的なAPIがあり、途中の失敗では停止状態を残すよう試みる。停止の書込み自体に失敗した場合もエラーを返す。実機での時刻設定、保持、バックアップやwake-upは、この読取り試験とは別である。

## PC上で応答の順序を変える

本章の参照版を、独立した作業用コピーで開く。

```sh
git worktree add --detach ../nihos-book-network \
  94c03aae4198a4a32f03601e362fa10ea86f39b3
cd ../nihos-book-network
sh tools/bootstrap-zig.sh
.tools/zig-0.17.0/zig test src/root.zig \
  --test-filter 'DHCP' --test-filter 'BLE'
.tools/zig-0.17.0/zig test src/board/tab5/rtc.zig
```

[Hostedのテスト](git:94c03aae4198a4a32f03601e362fa10ea86f39b3:src/net/hosted_test.zig)で`DHCP T1 unicast, T2 broadcast and ACK restart the lease clock with a new transaction`を読む。時刻を進める前に、次の送信先とアドレスの状態を予想しよう。別のtransactionの応答や不正なT1/T2を渡した場合、何が維持されるだろうか。

次に[BLEのテスト](git:94c03aae4198a4a32f03601e362fa10ea86f39b3:src/net/ble_hci.zig)で、creditが0の場合、違うコマンドの完了が来た場合、期限を過ぎた場合を比べる。演習では、作業用コピーの探索停止の成功応答を失敗応答へ変え、最終状態が`idle`にならないことを確かめよう。送信した記録だけで完了と判断すると、どの検査がすり抜けるだろうか。

最後にRTCの不正な曜日と日付の試験を読む。値を補正して採用する方式と、無効として利用者へ知らせる方式を、時刻の利用目的から比べてみよう。次の{{ch:io-lifetime}}では、待っている仕事を取り消すとき、資源をいつ返せるかを考える。
