# 既存のCライブラリを迎える

小さなOSから`SELECT 6*7`を実行できたら、何が揃ったと言えるだろうか。関数を呼べたことに加え、その関数が使ったメモリや、失敗した後の状態にも目を向けたい。

{{ch:floating-and-abi}}ではZigとCの呼び出しの約束を調べた。この章ではSQLiteを迎え、既存ライブラリが暗黙に受け取っている実行環境を洗い出す。対象はメモリ上のDBである。保存の仕組みは、次の独立した課題として残す。

## 関数の外にある依存を探す

SQLiteの本体をコンパイルするだけでは、nihosの上で動く実行環境はできない。どの処理を提供し、どれを使わせないかを決める必要がある。

| 境界 | この実験で用意するもの |
| --- | --- |
| メモリ | タスク所有の固定容量プールと割当器コールバック |
| ライブラリの寿命 | 一つの所有者による初期化、接続、文、終了 |
| OSとの接続 | ファイルを開かない試験用VFSと、限定した時刻などの実装 |
| 実行する場所 | Flash上のコード配置、内部SRAMの可変データとスタック |
| 失敗 | メモリ不足の注入、解放、再試行の検査 |

この構成ではloadable extensionやWALなどを無効にしている。不要な依存を減らすことも移植の一部である。一方、テスト用の時刻や乱数を用意したことは、時計や乱数源の品質を確かめたことにはならない。

## メモリの使い道をOSへ戻す

{{ch:reusable-memory}}のバディヒープの上へ、小さい要求を扱うサイズクラスのプールを置く。C側には、次の明示的なAPIを公開する。

{{snippet:c-allocator-api}}

要求は8〜4096バイトのクラスへ丸め、返すアドレスは8バイト整列とする。クラスごとに上限があり、足りないときに別のヒープへ逃がさない。この実験の制約であり、任意のCプログラム向けの`malloc`を用意したわけではない。

SQLiteには、このAPIを使う`sqlite3_mem_methods`を渡す。ライブラリの内部で生じた確保も、OS側の予算へ帰ってくる。アプリケーションが先に取ったバッファだけを数えて、ライブラリ内部の増加を見落とすことを避けられる。

`realloc`の約束にも注意しよう。正の大きさへの変更が失敗したら、古い領域と内容は残す。`capacity`で使える長さを知らせたなら、移動時にもその範囲の内容を保存する。最初に要求された長さだけをコピーすると、呼び出し側が正当に書いた末尾を失う。

また、生のポインタには世代番号が付いていない。同じアドレスが再利用された後で、古いポインタと新しいポインタを区別することはできない。プールの所有者を検査することと、C側のすべての寿命違反を防ぐことは、別の仕事である。

## ライブラリにも所有者がいる

本章のSQLiteは`THREADSAFE=0`で構築する。[セッションの実装](git:edbdd6cdbc4ff19d5d1a46f20510abd6d6789608:src/services/sqlite_session.c)は、接続だけでなくライブラリの初期化と終了も一つの所有者へ集める。別のタスクから呼ばれたときは、SQLiteの内部へ入る前に拒否する。

終了では、実行文と接続を閉じ、ライブラリの終了処理を済ませた後に割当器を閉じる。順序を逆にしてプールだけを回収すると、SQLiteのグローバルな状態がすでに無効なメモリを参照するかもしれない。

タスクを強制終了して領域をまとめて取り戻せることも、ライブラリが再利用可能な状態に戻ることとは違う。PC上の試験には、所有者を失った後の古いグローバル状態を、新しいタスクの世代番号から使わせない検査がある。どこまで通常終了を要求し、どこからシステムの再初期化が必要になるかを、APIの契約へ含める。

中断も、別タスクから同時にSQLiteへ入る方法にはしない。PC上のセッション試験では、別タスクは取消トークンを公開し、実行中の所有者が進捗コールバックで受け取る。これはPC上で確かめた接続であり、ネイティブSMPのSQLサービスを検証したものではない。

## 成功する入力から、失敗の途中へ

最初にPC上で動かす処理列は、計算、表の作成、トランザクション、行の追加、集計を行う。[割当器の記録](git:960bb1056252aaf6193d8d66350a27e63259d26d:docs/measurements/2026-10-26-native-c-allocator.md)では、通常実行で308回の確保・再確保があった。その一回ずつに失敗を注入し、文と接続を閉じた後に全領域が戻るか、もう一度同じ処理を成功させられるかを調べた。

メモリ不足は、初期化が半分終わった場所でも起きる。結果をNOMEMで返すだけでなく、誰が途中の資源を片づけるかが問われる。セッションを加えた[後続の実験](git:edbdd6cdbc4ff19d5d1a46f20510abd6d6789608:docs/measurements/2026-10-26-sqlite-owner-session.md)では321箇所を別に検査している。二つは処理列が異なるので、数を混ぜない。

予算も総量だけでは決まらなかった。元のPC上の処理列の使用量の最大値は約27 KiBだったが、全クラスへ同じ個数を予約する方式では512 KiBの親領域が必要だった。小さいクラスに合わせて個数を増やすと、大きいクラスまで過剰に予約されるからだ。要求の分布を見てクラス別の上限へ変えると、後続の固定処理列は64 KiBの親領域で動いた。

必要な予算は処理列と実行環境によって変わる。RV32のネイティブ実行では、32・64バイトクラスの不足が追加で見つかった。[実行コードの配置と割当の記録](git:960bb1056252aaf6193d8d66350a27e63259d26d:docs/measurements/2026-10-26-native-sqlite.md)から、その失敗と調整を追える。

## 実機で動いた範囲を読む

PSRAM修正後のTab5では、同じイメージの3起動で、各2セッション・26文が実行され、終了後の外部ヒープの空き容量が戻った。コードは監査したFlash上にあり、実行中の命令位置もその関数内にあることを確認している。

このSQLはCPU0の起動処理上で、スケジューラのタイマーを止めた後に実行した。並行して要求を受けるサービスではない。スタックの変更パターンから6,472バイトを観測したが、任意のSQLの最大使用量を保証する値でもない。問い合わせの制限と、実行環境ごとの測定が必要になる。

また、VFSという名前の接続口があっても、保存ができるとは限らない。ここでは`:memory:`を使い、試験用VFSはファイルを開く要求を拒否する。電源を切った後にもデータを残すには、ブロック入出力、ファイル操作、同期、障害時の回復を別に設計し、試験することになる。後の{{ch:sqlite-persistence}}では、この段階の所有者と割当器の考え方を、ホストの永続DBへつなぐ。

## PC上で不足と回復を確かめる

リポジトリのルートから、専用の作業用コピーを作る。

```sh
git worktree add --detach ../nihos-book-library \
  edbdd6cdbc4ff19d5d1a46f20510abd6d6789608
cd ../nihos-book-library
sh tools/run-c-allocator-probe.sh
sh tools/run-sqlite-memory-probe.sh
build/sqlite/memory-probe profile
```

初回は固定版のZigとSQLiteのソースを取得し、ハッシュを確認する。SQLiteのコンパイルを含むので、小さいZig単体テストより時間がかかる。いずれもPC上で動き、Tab5や利用者のDBへアクセスしない。

通常実行と失敗注入のログを分け、終了後の使用中のブロックと親領域の回復を探そう。次に、クラス別の上限を定義する箇所を読み、一つのクラスだけ減らした場合にどこが先に失敗するか予想する。変更するなら作業用コピーで行い、失敗後の再試行まで観察する。

ライブラリを移植することは、欠けた関数名を埋めることにとどまらない。メモリ、寿命、失敗、実行場所の約束を、OSとライブラリの間で結び直す仕事である。
