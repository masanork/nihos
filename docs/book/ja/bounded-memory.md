# 有限のメモリを誰が持つか

「メモリを確保する」とき、私たちは何を受け取っているのだろうか。新しい物理メモリを作ることはできない。すでに存在する領域のうち、使ってよい範囲を受け取り、その寿命を守っている。

この章では、nihosの小さなアリーナを使い、領域の割当、整列、容量不足の意味を調べる。確保に失敗しても状態を壊さないことを、コードと実験の両方から確認する。

## 普段の確保の、その下へ降りる

アプリケーションで`malloc`などを呼ぶと、メモリがどこから来たかを毎回考えずに済む。しかし、ライブラリが空き領域から区画を選ぶ仕事と、OSがその元になるメモリを提供する仕事は、分けて考えられる。本章では最初から使えるバイト列を一つ渡し、その中をどう分けるかだけに注目する。

たとえば、検索結果を一回表示する間だけ使う作業領域なら、処理が終わるとまとめて返せる。編集中の文書のように次の検索後も残したいものは、同じ寿命にまとめにくい。確保方法を選ぶ前に、データをいつまで持つかを考えると、小さなアリーナを使える場面が見えてくる。

アリーナに渡す領域の準備は{{ch:psram-and-evidence}}で、個別に解放する方式は{{ch:reusable-memory}}で扱う。ここでは、用意された領域をどう分けるかという計算に集中しよう。

## 先に領域を受け取る

アリーナは、あるメモリ領域から順に区画を切り出す仕組みである。本章の実装は `memory: []u8` と `cursor: usize` を持つ。`[]u8` は開始位置と長さを持つバイト列、`usize` は対象のアドレス幅に対応する符号なし整数を表す。

`Arena.init` は与えられた領域を保持し、カーソルを0から始める。確保に応じてカーソルが前へ進み、個別の解放は行わない。`reset` はカーソルを0に戻し、全体を再利用する。

| 状態 | 呼び出し側が守ること |
| --- | --- |
| 初期化 | 渡した領域が有効であり、書き込み権限がある |
| 割当済み | 同じバイトを別の所有者が勝手に再利用しない |
| リセット | 以前に取り出した領域を誰も使わない |
| 複数の実行主体から利用 | 排他や単一所有者の規則を別途用意する |

Zigのスライスは範囲を表すが、借用の寿命や別のCPUとの排他を自動的に証明してはくれない。アリーナの呼び出し側にも責任が残る。

## 確保の計算を追う

実際の割当関数を読む。

{{snippet:arena-alloc}}

戻り値の `?[]u8` は、バイト列を返すか、失敗を表す `null` を返す。`*Arena` はアリーナ自身を書き換えるためのポインタである。

最初の行で整列が0、または2の累乗でない場合を拒否する。2の累乗なら、1を引いた値をマスクとして使い、アドレスを次の整列位置へ切り上げられる。整列はカーソルという相対位置ではなく、実際の開始アドレスに対して計算する。

たとえば開始アドレスを仮に `0x1003`、カーソルを0、整列を16とすると、次の整列位置は `0x1010` になる。最初の13バイトはパディングになり、長さ16の領域を取るとカーソルは29へ進む。確保できる量には、このパディングも影響する。

## 加算する前に確かめる

メモリ確保では、配列の末尾だけでなく整数の末尾にも注意する。大きすぎる値を加えると、整数の表現範囲を超える。実装は `base + cursor` と整列の切上げを行う前に、それぞれ加算が可能か調べる。

範囲の検査では `start + length > memory.len` と書く代わりに、まずstartが範囲内か調べ、残りの長さとlengthを比べる。これにより、検査のための加算そのものがあふれる問題を避ける。

カーソルを書き換えるのは、すべての検査に通ったあとだけである。容量不足や無効な整列指定で失敗したとき、次の要求に使える領域は変化しない。この性質は、呼び出し側が別の方針でやり直す助けになる。

## 手を動かす

まず、既存テストの中でどの要求が成功し、どれが失敗するか予想しよう。次に実行する。

```sh
.tools/zig-0.17.0/zig test src/kernel/arena.zig
```

既存テストは整列や容量不足を検査する。次の演習では、そのテストに「失敗した要求で残量が変わらない」という確認を追加する。実験前のソースを記録し、自分の変更をほかの作業と区別できるようにする。

1. 容量を超える要求の直前に `arena.remaining()` を保存する。
2. その要求が `null` を返したあと、残量が保存値と同じか検査する。
3. 無効な整列指定を指定した場合も、同じ性質を検査する。
4. DebugとReleaseSafeで実行し、結果と変更内容を記録する。

ヒントは、既存テストで使っている `std.testing.expectEqual` である。実装が最後にしかカーソルを変更しないことと、観察した結果を結びつけて説明しよう。

## アリーナだけでは解けない問題

アリーナが返すのはアドレスと長さである。その領域が内部RAMかPSRAMか、DMAに適しているか、キャッシュの同期が必要かは、別の契約になる。アリーナを通して確保したという事実から、デバイスへ安全に渡せるとは判断できない。

また、リセットしても古いスライスの値そのものは消えない。利用者が残っていれば、新しい割当と同じメモリを指すことになる。割当器の実装だけでなく、どの時点で誰も使わなくなるかをシステム側で決める必要がある。

## 設計を選ぶ

アリーナは、同じ時期にまとめて寿命が終わるデータに向く。領域と残量が見えやすく、個別解放の管理も要らない。独立した寿命のオブジェクトが増えるなら、固定サイズのプールや、解放可能な割当器を検討する。その場合は断片化、管理情報、最悪時の所要時間という別の費用が生じる。

別の割当方式が必要になったら、まず寿命の規則のどこが合わなくなったかを考えよう。守りたい条件から方式を選ぶと、複雑さを増やす理由も説明できる。
