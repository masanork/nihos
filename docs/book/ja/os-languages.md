# OSを何で書くか

同じメモリ確保の処理でも、Cで書くか、Rustで書くか、Zigで書くかによって、間違いの見つけ方は変わる。関数から失敗を返す方法も、返した領域をいつまで使えるかという約束の表し方も違う。

nihosはZigを主な記述言語に選んでいる。この章では、その選択をOSの歴史の中へ置いてみる。言語の機能、実行に必要な支え、コンパイラやライブラリの条件を分け、Zigによって説明しやすくなることと、設計者に残る責任を考える。

## OSの、どの部分を書くのか

OSは一つの言語だけでできているとは限らない。起動直後の入口、カーネルのデータ構造、デバイスの操作、利用者がプログラムを書く環境では、必要な道具が違う。{{ch:boundaries}}で分けた責任の境界を、ここでは記述言語から眺める。

| 記述する部分 | 言語を選ぶときの問い |
| --- | --- |
| 起動、例外の入口、実行状態の切り替え | 命令、レジスタ、スタックの状態を指定できるか |
| カーネルやドライバの通常の処理 | データの寿命、共有、失敗をどう表すか |
| 処理系、エディタ、利用者の道具 | どこまで動作中に調べ、変更できるか |

言語の仕様だけで実行できるわけでもない。生成コードが必要とする補助関数、スタック、初期値、例外処理やGCなどを、誰かが用意する必要がある。OSのない環境で動くfreestandingなプログラムを作るときには、その前提を一つずつ確認する。必要な支えの範囲は、言語だけでなく、使う機能とコンパイラの設定によっても変わる。

## アセンブリから高水準言語へ

初期のOSでは、機械の命令を直接扱えるアセンブリが大きな役割を担った。ただし、「Unix以前はすべてアセンブリだった」とまとめると、それ以前の試みを見失う。

[Multics開発者たちのPL/Iに関する回想](https://multicians.org/pl1.html)によれば、先行するCTSSのsupervisorはほぼアセンブリだったが、スケジューラには方針の実験をしやすくするためMADが使われた。同じ資料は、BurroughsがB5000のOSをALGOLの方言で記述していた先例にも触れている。変更したい方針を高水準の記述へ移す発想は、早い時期からあった。

Multicsが選んだのはPL/Iだった。選択に関わったDoug McIlroyは、文字列とビット列、分割コンパイル、アドレスやデータ構造を扱う要求を挙げている。一方、当時のPL/Iには、十分に使えるコンパイラをどう用意するかという難しさがあった。必要な機能を持つ言語の仕様と、そのOSを作れる処理系が手元にあることは、同じではない。

この区別はnihosにも残る。型が便利でも、対象CPUへ必要な命令を生成できなければ使えない。機種ごとの呼び出し規約やリンカとの接続まで含めて、記述の道具を評価する必要がある。

## CとUnixが結びつけたもの

Unixも最初はアセンブリで書かれていた。[Dennis RitchieによるCの成立史](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html)は、BCPL、Bを経てCが形になり、構造体などの機能が整った後、1973年にPDP-11のカーネルをCで書き直した経緯を説明している。高水準言語でOSを書く先例を受け、機械に近いデータ表現と、ソースを別の機械へ持ち出す可能性が結びついた。

Cはアドレスやビット列を扱いながら、関数、構造体、制御構造で処理をまとめられる。ただし、Cへ書き換えれば機種依存性が消えるわけではない。レジスタの配置、割込み、キャッシュの扱いは残り、型の大きさや整列、呼び出し規約も確認する必要がある。nihosで起動コードと通常のZigコードを分けることにも、同じ問いがある。

現在の[Linuxの言語に関する説明](https://docs.kernel.org/process/programming-language.html)も、Cを主な記述言語とし、GNUの拡張を使うことを明示している。「Cで書かれている」という説明の中にも、標準言語、コンパイラの拡張、ビルド環境という層がある。

C++もOS記述の選択肢に入る。たとえばAppleの[XNUの説明](https://github.com/apple-oss-distributions/xnu)には、ドライバ用のC++ APIであるIOKitが登場する。関数やデータをまとめる方法が増える一方、利用する言語機能と実行時の支えを選ぶ仕事は残る。OS全体を一つの言語名で分類するより、どこで何を使うかを見る方が実装へ近づける。

## Lisp Machineでは、言語が作業場になる

OSを記述する言語は、機械を扱うためだけの道具とも限らない。Lisp Machineでは、OSとプログラムを作る環境が、Lispを中心として密接につながっていた。

MITの1977年の[LISP Machine Progress Report](https://dspace.mit.edu/entities/publication/c6d82ef4-939b-43d6-afb4-ba562a28417a)は、システム言語としてのLisp、入出力、データ表現、記憶管理、GC、エディタを一つの報告で扱っている。[Symbolicsの技術史](https://www.symbolics.biz/history.html)にも、Lispで記述されたOS、コンパイラ、ウィンドウ、Zmacsというエディタ、デバッガを備えた環境が記されている。動作中のシステムを調べ、変更することまでが、言語の使い方に含まれる。

この構成を考えるには、処理系や、それを支える機械にも目を向ける必要がある。Lispの式を評価できることと、電源投入後にその評価器を使える状態へ持っていくことは別の仕事である。記憶管理やGCを含め、利用者には見えにくい下支えをどこへ置くかが問われる。

将来、nihosのZigカーネルの上へScheme処理系を載せ、編集や拡張に使う構成も考えられる。その場合も、式から呼べる機能、止められる処理、失敗時に残すデータを決める必要がある。言語をどの層へ置くかによって、設計する境界も変わる。

## MesaとOberonでは、部品の境界も設計する

言語とOSの関係を考える系譜には、MesaやOberonもある。[開発者たちによるPilotの論文](https://www.mcjones.org/paul/pilot/pilot.html)は、Mesaで記述された個人用計算機のOSを説明し、実装の部品への分け方と、部品同士の動的な関係を扱っている。機械の操作に加え、大きなソフトウェアの部品をどうつなぐかが関心になる。

[Niklaus Wirthの開発史](https://people.inf.ethz.ch/wirth/projects.html)では、Modula-2とLilith、続くOberonで、言語、コンパイラ、OS、編集の道具を一緒に設計した様子を読める。Oberonでは、全体を理解し説明できる大きさに保つことが目標に置かれ、システムの拡張に必要な型の機能も言語の設計へ戻された。

小さな端末の上で、読むこと、書くこと、動かすことをつなぎたいnihosにとって、これは比較する価値のある先例である。CPUを切り替えられるだけで利用者の作業場ができるわけではない。逆に、便利なエディタを作るために、カーネルのすべてを同じ言語へ揃える必要があるとも限らない。どの境界で何を共通にするかを選べる。

## 言語で保護するという試み

メモリの誤った操作を、言語や検証器によって防ぐ方向もある。Microsoft Researchの[Singularity](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/osr2007_rethinkingsoftwarestack.pdf)は、C#を拡張したSing#を使い、プロセスの分離やメッセージの受け渡しを、言語の規則と組み合わせて設計した研究OSである。

マイクロソフト在籍時代、私はSource DepotでSingularityのソースを日々同期し、自分でビルドして動かしていた。特に印象に残ったのは、形式検証との統合だった。当時のWindowsにも、Cで書かれたドライバがカーネルAPIの利用規則を守るか調べる[Static Driver Verifier](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/eurosys2006-1.pdf)があった。Singularityでは、検証を言語とOSの設計へ、さらに深く組み込もうとしていると感じた。

Singularityでは、プロセス間で渡すデータの所有権や、メッセージを送受信する順序を検査する。カーネルとプロセスが同じアドレス空間・特権レベルで動く構成なら、保護のための切り替えの費用を省ける。実行状態の保存・復元は残るが、言語で守れる規則を使うことで、OSが毎回行う仕事も変わる。

同じころのWindowsには、Nexusというカーネルで保護された実行環境を作る[NGSCBの構想](https://download.microsoft.com/download/3/8/1/38198a72-294d-46c3-93ba-faee5cf85d00/ARC341.ppt)もあった。私は実際には動かしていないが、「カーネルは起動できても、その内部をデバッグできない」という話を伝え聞いていた。保護された場所を作ることと、その中を調べながら開発できることは、別の設計課題である。

OSを何で書くかを考えると、どの誤りを言語で防ぎ、何を実行時に調べ、どの道具で問題を追うかという問いにも行き着く。これはnihosでも考え続けたいことだ。

## Rustで表す所有権と保護

[Rustの所有権の説明](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)は、GCを必須にせず、所有権の規則をコンパイラで検査する方式を示している。借用の規則と合わせ、safeなコードから起こせるメモリ操作の誤りを制限する。ただし、機械のアドレスや外部のコードへ接続する部分などでは、その規則を支える実装が必要になる。[unsafeの説明](https://doc.rust-lang.org/book/ch20-01-unsafe-rust.html)も、その内部で参照の検査がすべて無効になるわけではなく、特定の操作にプログラマが責任を持つことを明示している。

[LinuxのRustに関する説明](https://docs.kernel.org/rust/general-information.html)は、CのAPIへの直接の接続を、検査された抽象の内部へ閉じ込める方針を示している。そこで公開するAPIの安全性は、内部の実装と`unsafe`の契約が正しいことを前提にする。また、通常のアプリ用の`std`ではなく、`no_std`の環境で使う。言語を採用する仕事には、そのOSで使える部品を整えることも含まれる。

Rustで設計された組込みOSの[Tock](https://www.tockos.org/documentation/getting-started/)は、カーネルとドライバの間などにRustの性質を使い、アプリケーション間などの分離にはMPUというハードウェア機能を使う。言語による制限と、機械による保護を組み合わせる例である。

メモリ安全性が得られても、仕事が期限までに終わるか、通知の順序が正しいか、電源断で保存内容を失わないかという問いは残る。言語が防ぐ誤りの範囲と、OS全体で守る性質を区別して読みたい。

## Zigで明示しやすくなること

こうした歴史の中で、nihosではZigを使う。[Zigの設計概要](https://ziglang.org/learn/overview/)は、暗黙のメモリ確保を避けること、手動の記憶管理、コンパイル時の処理、Cとの接続を特徴としている。nihosでは、これらを資源と実行条件が見える実装へ結びつけられる。

たとえば、[アリーナ](repo:src/kernel/arena.zig)の`alloc`は`?[]u8`を返す。`[]u8`は開始位置と長さを持つバイト列で、先頭の`?`は値がない場合もあることを表す。この関数では、容量不足や無効な要求を`null`で返している。呼び出し側は成功時のデータと失敗の分岐を一緒に読むことになる。失敗の理由を区別したければ、error unionなど別の型を選ぶ余地もある。

## Zigでも設計者に残る責任

Zigのスライスは長さを持つが、その領域の寿命を保証するものではない。[0.17.0の言語仕様のLifetime and Ownership](https://ziglang.org/documentation/0.17.0/#Lifetime-and-Ownership)も、利用できなくなったメモリを指すポインタへアクセスしない責任をプログラマに置いている。アリーナをリセットした後、古いスライスを使ってよいかは、その長さだけでは判断できない。

範囲外アクセスなどを検出する実行時検査にも、適用範囲がある。[同仕様のビルドモードの説明](https://ziglang.org/documentation/0.17.0/#Build-Mode)では、DebugとReleaseSafeで安全性の検査が有効になり、ReleaseFastとReleaseSmallでは既定で無効になる。検査を有効にしても、すべての寿命の誤りや、CPU間のデータ競合を検出できるわけではない。

検査に失敗してpanicすることと、通常の容量不足を戻り値で扱うことも違う。カーネルの実行時検査を使うなら、どの情報を残し、どこまで止めるかを考える必要がある。入力が大きすぎるときに処理を断れることと、すでに内部の約束が壊れていることを、同じ失敗へ押し込めない。

DMAが読んでいるバッファを書き換えないこと、別CPUへの公開順序、割込みを止める長さも、言語名だけでは決まらない。Zigで操作を明示できることを、操作が正しいという保証へ読み替えてはいけない。手動の記憶管理やGCを必須としない構成でも、最悪時の実行時間が自動的に決まるわけではない。

## 使える処理系を選び続ける費用

本書のコードはZig 0.17.0を基準にする。読者は[bootstrapスクリプト](repo:tools/bootstrap-zig.sh)で版を揃える。別の版へ移るときは、言語、標準ライブラリ、ビルドAPIの差分を確かめ、生成物と実験も更新する必要がある。これは言語の新しさを楽しむ側面と、教材を維持する負担の両方を持つ。

対象CPUへコンパイルできても、必要なABI、デバッグ方法、ベンダーSDKとの接続が揃うとは限らない。Cの既存ライブラリを使う場合も、必要なOS機能や割当器を用意し、使わない機能を切り分ける仕事がある。nihosのZigとCの接続を、そのまま任意のCプログラムを動かせる環境とは扱わない。

言語の性能や保守の費用を比べるときは、機能、入力、最適化、エラー処理の条件を揃える。nihosでは、Zigで資源の使い方と失敗を追いやすくすることを重視した。

## 誰に何を任せるかを比べる

次の表は、言語だけですべてが決まるという分類ではない。Cにも検査の道具があり、Rustにも`unsafe`や外部実装があり、Zigの検査には設定と範囲がある。通常のコードを記述するときの出発点として読む。

| 見る点 | C | Rust | Zig |
| --- | --- | --- | --- |
| ポインタの寿命 | APIの約束と実装で管理 | safeな参照には所有権・借用の検査。外部との境界に契約が必要 | APIの約束と実装で管理。スライスも寿命の保証ではない |
| 記憶の確保と回収 | ライブラリや用途で方式を選ぶ | 所有権、Drop、割当器などを組み合わせる | 確保元と失敗を明示し、回収の時点は実装で決める |
| 機械との接続 | コンパイラ拡張やアセンブリも使う | `unsafe`などを内部へ閉じ込めてAPIを作る | ポインタ、配置、アセンブリを明示してAPIを作る |

同じ仕事を別の言語へ移すとき、文法の置換だけでは済まない。たとえば受け渡したバッファの所有権を型へ入れるなら、APIの形も変わる。既存のC APIをそのまま公開する案と、寿命を制限した新しいAPIへ包む案では、呼び出し側が守る約束が違う。

## 手元のコードで、一つ確かめる

ここでは環境を増やさず、nihosの配置の検査を観察する。Zigの準備は{{ch:first-experiment}}を参照できる。リポジトリのルートで実行する。

```sh
.tools/zig-0.17.0/zig test src/arch/riscv32/context.zig
```

次に、作業用コピーで`IntegerContext`に32ビットのフィールドを一つ増やしたらどうなるか予想する。サイズの契約を変えずに追加し、同じコマンドを実行する。実行時にテストが失敗するのか、それ以前にコンパイラが止めるのかを、診断とともに記録しよう。終わったら自分が追加したフィールドだけを戻す。

サイズの検査を通すために定数だけを変えると、アセンブリが参照する配置も正しくなるだろうか。続くオフセットの検査と、実際の保存・復元命令を読む必要がある。コンパイル時の検査を一つ入れたことと、両側の約束がすべて合っていることは別だと分かる。

検索結果をエディタへ渡す場面を考えよう。領域を誰が返し、いつまで表示できるか。中断時には誰が片づけるか。C、Rust、Zigを比べ、型、実行時の検査、文書やテストのそれぞれに、どの約束を表せるか整理してみよう。
