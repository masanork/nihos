# 別のCPUへ仕事を渡して待つ

CPU0が仕事をキューへ置いた。CPU1はキューが空だと判断し、眠ろうとしている。二つの操作がすれ違ったら、仕事はいつ処理されるだろうか。

この章では、値の受け渡しと、受取り側を起こす通知を分ける。固定容量のキューからイベント待ち、IPI、WFIへ進み、通知が待機直前に届く場合を調べる。必須実験はPC上のリングと待機モデルで行う。

## 共有するものと、渡すものを選ぶ

同じデータを使う方法には、共有の表をロックで守る案も、所有者へ要求を送る案もある。小さな要求をコピーするか、大きな画像の置き場所をハンドルで渡すかでも、費用と寿命の管理が変わる。どちらでも、受取り側が使い終わるまで元のデータを有効にしておく約束が必要になる。

nihosのサービス案では、状態を変更する役割を所有者へ集め、他の仕事から要求を送る。この構成は、サービスの内部を理解する範囲を小さくする助けになる。一方、キューの容量、待ち、取消、応答前に依頼元が終了した場合など、受け渡しそのものの設計が必要になる。

[MINIX 3](https://www.minix3.org/)は、保護されたプロセスへOSの役割を分ける例である。本章のM-modeワーカー同士のメッセージ交換と比べると、メッセージという形式と、アクセスを制限する機構を分けて考えられる。本章ではまず、小さな値を渡す場合の順序と待機を調べる。

{{ch:process-isolation}}の保護タスクは別の契約を持つ。共有ringのポインタを知らせるだけでは、PMPの許可は増えない。`wake`や`notify`を使う既存のワーカー間通信を、制限されたU-modeのABIからそのまま呼べるわけでもない。コピーするデータの検査、共有を許す範囲、通知相手への権限を決める仕事は別に残る。

## キューのスロットを誰が使ってよいか

SPSCはsingle producer, single consumerの略である。一つの送信側だけが書き、一つの受信側だけが読む。この条件に限定することで、すべての操作を一つの共有ミューテックスで囲まずに、スロットの所有を渡せる。

nihosの[リング](repo:src/kernel/spsc_ring.zig)は、まだ読んでいない値を上書きしない。満杯なら`tryPush`はfalse、空なら`tryPop`はnullを返す。満杯を無制限のメモリ確保で解決しないので、呼び出し側は待つ、失敗を返す、仕事をまとめるといった方針を選ぶ必要がある。

送信側の処理を読もう。

{{snippet:ring-push}}

スロットへ値を書いた後で、書き込み済みカウンタを`release`で公開する。受信側は、その公開を`acquire`で観測してからスロットを読む。逆方向にも、読み取り済みカウンタを公開してスロットの再利用を許す約束がある。

{{figure:spsc-ownership}}

図は一つのslotを繰り返し使う循環を示す。書込みの公開だけでなく、読取りの終了も相手へ公開する。まだ受信側が読んでいるslotへ、送信側が次の値を書き始めてはいけない。

これは、どのメモリにも自動的な一貫性を与える指定ではない。CPU間で共有可能なメモリに置くこと、DMAや外部メモリに必要なキャッシュ操作を満たすことは別の条件である。`volatile`だけで、この公開順序の代わりにはならない。

カウンタの整数範囲も有限である。本章の実装は、公開するカウンタと所有者だけが使うスロット位置を分けている。容量3のリングでカウンタが桁あふれするとき、単純な`counter % capacity`が同じ順序を表し続けるとは限らないからだ。

## 通知は仕事そのものではない

キューへ値を置くだけでは、眠っている受信側を起こせない。そこで「読めるものがある」というイベントを通知する。重要なのは、通知の回数と値の個数を同じものにしないことである。

通知は合流したり、読んだ後まで残ったりする。起こされた受信側は、必ずキューを確認し直す。キューが真実を持ち、通知は確認のきっかけになる。

[チャネル](repo:src/kernel/spsc_channel.zig)は、公開してから通知する順序を明示している。

{{snippet:channel-send}}

ここには、`published_unnotified`という結果がある。値はすでにキューの所有になったが、通知に失敗した状態だ。これを単純な「送信失敗」として同じ値を再送すると、二重投入になる。途中まで進んだ操作を結果の型で表すことは、サービスAPIでも役に立つ。

受取り側は、キューが空ならイベントを待つ。確認と待機の間に届いた通知を捨てないよう、スケジューラのイベントは保留ビットとして保持される。待機に入るとき、すでに一致するビットがあればその場で受け取る。

{{figure:event-before-wait}}

通知がwaitより前に着いた場合を、図の順で追おう。kernelはeventの確認と待機登録を直列に扱い、既着なら眠らず返す。wait登録後に着いた場合は、通知で`waiting`から`ready`へ戻す。どちらの順でも、再開したtaskがqueueを調べ直す点は同じである。

## 別CPUのスケジューラを直接書き換えない

ネイティブ経路では、送信元が相手CPUのスケジューラの状態を直接操作しない。要求を相手の受信箱へ公開し、ソフトウェア割込みであるIPIを立てる。相手CPUが自分の割込み処理で受信箱を読み、自分の選択方針へ通知する。

{{figure:cpu-ipi-delivery}}

一回の割込みで処理する件数には上限がある。残りがあれば再通知する。キューがあるからといって、割込み中に無制限の仕事を処理すれば、描画や他の期限を守れなくなる。

一つのリングには送信者と受信者を一つずつ割り当てる。複数の送信者を接続したり、タスクをCPU間で移したりするなら、この所有規則から見直す必要がある。[設計判断](repo:docs/adr/0020-native-ipi-and-interrupt-wait.md)では、受信箱の容量と一回に処理する量を追える。

## 待つ仕組みを読み比べる

別の仕事が終わるまで待つ問題は、CPU間の通信に限らない。条件変数も、共有された条件を調べ、満たされるまで待ち、通知をきっかけに再び調べる仕組みである。[OSTEPの条件変数の章](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-cv.pdf)では、この問題をロックと待機の組合せから説明している。

nihosの保留ビットと条件変数は、同じAPIや通知の保持規則を持つわけではない。読み比べるときは、待ちたい条件をどこへ記録するか、確認と待機への登録をどうつなぐかを見る。ここでは、まずタスクがイベントを待ち、その結果として動かす仕事がなくなったCPUがWFIへ進む、二つの待機を分けよう。

## 眠る直前が難しい

仕事がなければ、CPUはWFIという待機命令を使える。しかし「終了していないか調べる」「待機する」の間に条件が変わる場合を考える必要がある。

nihosの小さな待機部品は次の形である。

{{snippet:park-once}}

このP4の経路では、割込みの処理をマスクしたまま条件を確認し、WFIを実行する。ローカルに許可された割込みが保留状態になれば待機から戻り、その後で元の割込み状態を復元する。待機から戻る条件と、割込み処理を実行してよい条件を分けている。

この前提はCPUと割込み設定に依存する。他のCPUへ移すときに、同じ数行だけをコピーしてはいけない。また、WFIから戻ったことは、そのまま仕事の完了を意味しない。呼び出し側は保持された状態をもう一度調べる。

## PCで取りこぼしの条件を調べる

リポジトリのルートで実行する。

```sh
.tools/zig-0.17.0/zig test src/kernel/spsc_ring.zig
.tools/zig-0.17.0/zig test src/kernel/park.zig
.tools/zig-0.17.0/zig test src/kernel/scheduler.zig
```

リングのテストでは容量3と64の二つの条件で、PC上の別スレッド間に10万個の値を渡す。これは順序を検査する実験であり、P4のスループット測定ではない。

`park`のテストは、実際のWFIではなく割込み操作のモデルを使う。マスクした瞬間とwaitの直前で条件を変え、待機の有無と元の状態への復帰を調べる。モデルが何を仮定しているかも読むことが、この実験の一部である。

条件変更の演習では、作業用コピーのリングテストに容量5を追加する。カウンタの桁あふれ付近から始める設定を保ち、順序と満杯判定が崩れないかを確かめる。さらに、待機モデルが保留状態を保持しなかったら何が起こるか、時系列図で説明しよう。

もう一つ、音を作る仕事から再生サービスへデータを渡す場面を考えてみよう。短い値ならコピーできても、一まとまりの音声ではバッファの寿命が問題になる。要求の投入、受取り、再生終了、バッファの返却を並べ、どの時点で送信側が同じ領域を書き換えてよいかを決める。これはAPIの設計演習であり、音声サービスの実装済み機能を使う実習ではない。

## タイマーに救済されていないか

[ネイティブIPIの検証記録](repo:docs/measurements/2026-10-25-native-ipi-idle.md)では、周期タイマーのアラームを止めてから64往復を行っている。両CPUで、待機する前にIPIを保留状態にする条件も意図的に作った。IPI区間のタイマー割込み数が開始時と終了時で同じことが、周期ティックで偶然起きたのではない根拠になる。

ESP-EMUに加え、実機でも64交換の基本経路を観測した。ここで確かめているのは通知と起床の接続である。省電力効果を知るには消費電力を、負荷時の応答を知るには要求から処理までの時間を、別に測る必要がある。

追加実験の`sh tools/run-native-smoke.sh integer 0`では、キューの送受信、通知と起床、WFIへの出入り、タイマー数を組にして読む。満杯のネイティブ受信箱を連続的に処理する負荷試験は、この64往復の記録とは別の課題である。

## 読み終えたら確かめること

値を公開する前に通知してはいけない理由、通知に失敗しても再送できない場合、WFIの前に割込み処理をマスクする理由を説明しよう。{{ch:psram-and-evidence}}では、そのような仕事が使う外部メモリを、実機で利用可能にするまでを考える。
