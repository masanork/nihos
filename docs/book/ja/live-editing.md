# 編集する道具を、その場で育てる

同じ挨拶を何度も書くなら、文字列を挿入するコマンドを作りたくなる。次には、その挨拶を編集画面で書き直し、アプリを閉じずに使いたくなる。さらに、次の起動でも定義が残っていてほしい。

{{ch:editing-environment}}で分けた文書、入力、描画に、編集操作を定義する小さな言語と、定義を保存する仕組みを加える。{{ch:sqlite-persistence}}までに学んだ保存の順序は、ここでは「保存済みの定義と、動作中の定義をどう対応させるか」という問いになる。

本章は[XYのMacワークスペース](git:9208c4edad1c78eb3e2f5942a530fb67979fa675:docs/measurements/2026-10-31-xy-mac-workspace.md)と[後続の共通描画統合](git:9208c4edad1c78eb3e2f5942a530fb67979fa675:docs/measurements/2026-10-31-xy-native-pixel-landing.md)を使う。保存を実行したのはMacのシステムSQLiteであり、Tab5のSDへこの定義を保存する機能は未接続である。

## 一回の操作から、名前を持つ操作へ

挿入したい文字列を関数にする。Schemeの`define`は名前を定義し、この例では引数を取らない`stamp`という関数を作る。

```scheme
(define (stamp)
  (buffer/insert! "xy live edit"))
```

`buffer/insert!`はXYが用意する文書操作で、現在のカーソルへUTF-8を挿入する。関数の中に書いた挿入は、定義した時点では行わず、後で`stamp`を呼んだときに行う。言語の評価器が画素や文書の配置を直接書き換えるのではなく、既存の文書APIを呼ぶ。

後の共通実行系は、定義した関数とクロージャを、次の要求まで保持する。コマンドの名前から関数を引ける登録表も持つ。登録した名前はソース文字列へ連結せず、そのまま名前として検索する。

ここで編集できるのは、用意された操作を組み合わせるSchemeの定義である。Zigの描画エンジンやカーネルを、入力した場で再コンパイルする機能ではない。それでも、アプリの振る舞いの一部を、利用者が読む・直す・試す対象にできる。

## 失敗する式を、どこで止めるか

式を読めるだけでは、対話環境には足りない。終わらない再帰、長すぎる文字列、たくさんのリストが、編集の入口を使い切るかもしれない。共通の[限定Scheme実行系](git:9208c4edad1c78eb3e2f5942a530fb67979fa675:src/xy/scheme_runtime.zig)は、呼出し元が渡す固定長のセル配列を使う。セルは整数、文字列、リストなどの値を保持する単位である。

| 資源 | この実行系の上限 |
| --- | ---: |
| 値を保持するセル | 256 |
| 一つの文字列・名前 | UTF-8で64バイト |
| 読取り・評価の深さ | 24 |
| 一要求の読取り・評価tick | 1,024 |
| 登録コマンド | 初期定義を含め16 |
| ソース | 4,096バイト、別にセル上限も適用 |

tickは処理を数える内部の単位であり、一tickが何マイクロ秒という期限の測定ではない。セルとstepの制限は、任意の外部呼出しまで一定時間で終える証拠にもならない。実行する操作を限定したことと、機械の権限で隔離したことも別で、Mac版は通常のアプリ権限で動く。

要求と要求の間では、参照されなくなったセルをGCで回収する。残すべきものは、大域変数だけではない。クロージャが参照する環境と、コマンド表から参照する関数も回収から守る。関数を定義した要求が終わっても、その関数が必要とする値の寿命は続く。

これは整数と限られた式の実装であり、R7RSというScheme規格全体への適合を主張しない。マクロ、継続、完全な数値体系やproper tail callは備えていない。まずは、上限を超えた要求をエラーとして終え、その後も編集を続けられる範囲を作る。

## 動作中の環境へ、いきなり読み込まない

Sourceバッファで`stamp`を直して保存するとしよう。新しい定義の途中に構文エラーがあるかもしれない。現在の環境を直接変更しながら読むと、一部だけ新しくなり、残りは古い状態になりうる。

そこで、現在のVMとは別に候補のVMを組み立てる。VMは式を評価する状態で、定義、値、登録表を含む。候補全体を新しい環境へ読むため、削除した古い定義が残ることも避けられる。再反映時には、変数やクロージャが持つ実行中の状態も初期化される。

候補の構築中は、文書編集やシステム操作を拒否する。先の挿入は関数本体なので定義できるが、読み込みの最上位で直ちに文書を編集する式は通さない。まだ採用していない候補が、現在の文書を変えないためである。

この段階で通るのは構築時の検査であり、定義した関数のすべての入力に対する正しさではない。呼出し時に起きるエラーには、別の処理が要る。

## ディスクとRAMの変更を、順序でつなぐ

候補VMができたら、保存先を変更する。ソースの原文は、コメントや改行も含むUTF-8で保存し、セル配列そのものは保存しない。次回起動時は、保存済みの原文から実行環境を作り直す。

{{figure:workspace-apply-order}}

図のDBとRAMは、同じトランザクションに参加していない。SQLiteの中でソース世代と有効世代を更新し、COMMIT成功を受けてから、準備済みの候補へ切り替える。切替えまでイベント処理へ戻らず、採用する処理は追加の構築を要しないようにしている。

| 止まる・失敗する位置 | 動作中の環境と、次回起動 |
| --- | --- |
| 候補の読取りや構築で失敗 | 現環境を保ち、候補を保存しない |
| 世代競合やDB busyで保存できない | 候補を捨て、現環境を保つ |
| COMMIT成功後、RAM切替え前にプロセス終了 | 次回は保存済みの新ソースから構築 |
| 切替え完了 | 新しい定義をその場で利用 |

保存の成功と動作の変更の間に、短くても隙間がある。その隙間を「一つの原子的操作だった」と呼ぶ代わりに、再起動で何を正本として読むかを決める。前章までのストアのrootと成功通知の議論が、アプリケーションの設定にも現れる。

これはMac上のプロセス再起動や保存失敗を試す構成である。あらゆるI/O故障や電源断の後に同じ回復ができるという資格試験ではなく、Tab5の保存基盤へつなぐ際には、下位の同期と故障の契約を改めて満たす必要がある。

## 世代があれば、他の編集も見つけられる

同じDBを開くAとBが、ともに世代7を読んだとしよう。Aが保存して世代8になった後、Bが古い定義で保存すると、Aの変更を見ないまま有効版を上書きしてしまう。

保存APIは、呼出し元が期待する有効世代も受け取る。`BEGIN IMMEDIATE`で更新するトランザクションを始め、DBの有効世代が期待値と一致するかを確かめる。Bの期待値7と現在の8が違えば保存せず、再読込みを求める。これを、先に読んだ状態がまだ有効かを確認する楽観的な競合検出と呼ぶ。

履歴を戻す場合も、過去のソースを書き換えない。有効世代が指す先を変更する。履歴から戻した版をさらに直せば、新しい世代として追加される。取り消せることと、過去を消すことを分ける設計である。

## 三種類の「戻す」を分ける

文書のUndo、評価失敗からの復元、保存世代の復元は、それぞれ対象が違う。

| 操作 | 戻すもの | 今回の実装 |
| --- | --- | --- |
| 文書のUndo | ひとまとまりの編集 | 共通Documentの履歴 |
| 対話評価・コマンドのエラー | 評価前のVMと文書 | Macのlive workspaceが有界な複製から復元 |
| Historyでの世代選択 | 次に構築する定義の原文 | DBの有効世代を変更して採用 |

この違いは実装を再利用するときにも残す。nativeの小さいSchemeフロントエンドは、途中の効果が残ってUndoできる方式だった。Macのlive workspaceは、評価前のVMと文書を退避して復元する。共通評価器を使うだけで、すべてのフロントエンドに同じ巻戻し契約が付くわけではない。

保存済みの定義が読み込めなくても、内蔵の定義で起動し、DBの原文と履歴は残す。`--safe`では正常なユーザー定義も実行せず、修復の入口を確保する。未反映の草稿を持つときの終了や履歴復元では、草稿の扱いも利用者へ示す。読み込めない定義を黙って消すと、修復する材料まで失う。

## Macで、反映と再起動を試す

独立した作業用コピーを作る。CocoaとシステムSQLiteを使うため、この実習はmacOS向けである。

```sh
git worktree add --detach ../nihos-book-live-edit \
  9208c4edad1c78eb3e2f5942a530fb67979fa675
cd ../nihos-book-live-edit
sh tools/bootstrap-zig.sh
tools/build-xy-mac.sh
open build/xy-mac/xy.app
```

Source（⌘E）を開き、最初の`stamp`の定義を入力する。Apply & Save（⌘S）で保存し、文書へ戻ってRun Command（⌘R）から`stamp`を呼ぶ。挿入された文字列を確認したらアプリを閉じ、再起動して同じコマンドを呼ぶ。次に文字列を変えて保存し、History（⌘B）で前の世代へ戻して動作を比べる。

初期版のMac手順にあった外部フォント依存や512 glyphの描画上限は、後の統合では同梱の復旧用字形と240 glyphの表示窓へ変わっている。全文書や全字形が表示できるという意味ではない。また、ここでDB保存の対象になるのは単一の`user/init.scm`の定義で、通常の文章はRAMだけにある。

実際のMac実行ファイルと一時DBを使う結合試験は、次で動かせる。作業中のDBを消す試験ではない。

```sh
python3 tools/xy_workspace_test.py -v
```

保存された原文の復元、別プロセスの再起動、履歴からの分岐、競合、保存エラー、壊れた定義からの起動、VMと文書の復元を調べる。後続統合の記録では描画を含む16件が成功した。GUIでソースを書き換えた観察、結合試験、Tab5の描画試験は、それぞれ別の経路として記録されている。

## 境界を一つ変える演習

世代7を読んだAとBについて、Aの保存、Bの保存、Bの再読込みの順に、期待世代とDBの有効世代を書こう。Bを競合として拒否する位置はどこか。ソースが文法として正しいことだけを検査しても、この問題を見つけられない理由を説明する。

次に、COMMITの直前と直後でプロセスが終わる時間線を描き、次の起動で読む原文を予想しよう。Macの保存アダプタをTab5の`sqld`要求へ置き換えるなら、期待世代、保存完了、読み直し、失敗時に残す原文の契約を列挙する。これは接続の設計課題であり、未実装のSD保存を動かす演習ではない。
