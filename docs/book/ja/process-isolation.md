# タスクの実行と、壊せる範囲を分ける

二つの仕事を交互に実行できても、一方の誤った書込みで、もう一方の保存状態が壊れたらどうなるだろう。実行する順番を管理することと、触れてよいメモリを制限することは、それぞれ必要な仕事である。

{{ch:task-lifetime}}では再開に必要な状態を保存し、{{ch:task-queues}}では実行可能なタスクを選んだ。本章では、その復帰先に「どの権限で、どの領域を使わせるか」を加える。例は、CPU0上の保護タスクがカーネルのメモリを読もうとしても、そのタスクだけを終了させ、カーネルを続ける実験である。

本章の実装は、PR #76を取り込んだ版を対象にする。CPUの物理メモリアクセスを制限するPMP（Physical Memory Protection）を、タスクの復帰権限と組み合わせる。[実装の契約](repo:docs/native-user-pmp.md)と[実機証跡](repo:docs/measurements/2026-10-30-pmp-synchronous-faults/receipt.json)を対応づけて読む。通常の表示・カード・通信・SQLiteワーカーは引き続きM-modeで動く。保護タスクの登録は既定では拒否され、明示したCPU0の診断用構成だけが許可する。すべてのアプリケーションを隔離した製品になった、という更新ではない。

## 実行する単位と、守る単位

タスクには、実行位置、レジスタ、スタック、待ち状態が必要である。スケジューラは、その情報を使ってCPUを配る。一方、メモリを誰と共有し、どこへアクセスできるかは、別に決めなければならない。

[OSTEPのスレッドの説明](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-intro.pdf)では、プロセスのアドレス空間を複数の実行の流れが共有し、各スレッドがレジスタとスタックを持つ。一般的なプロセスの説明では、アドレス空間や資源を持つ単位に、その中で動く一つ以上のスレッドを対応づける。本書では、名前だけをnihosへ当てはめず、実装が持つものを分けて見る。

| 問い | nihosの今回の実装 |
| --- | --- |
| 次に誰を動かすか | スケジューラのタスク記録と状態遷移 |
| どこから計算を再開するか | 保存フレームと復帰状態 |
| CPUで何へアクセスできるか | タスクの保護範囲と、そのCPUのPMP設定 |
| 終了後に何を返すか | タスクが持つ領域を記録する資源台帳、回収、世代番号 |
| アプリをどう読み込み、資源を共有させるか | 汎用ローダや複数スレッドの保護領域共有は未実装 |

この段階では、一つの保護タスクに一つのコード範囲と専用のデータ範囲を結び付ける。独立したprocess管理オブジェクトを追加したわけではない。実行中のプロセスを複製する`fork`、実行するプログラムを入れ替える`exec`、開いたファイルの番号（FD）を管理するプロセス別の表も、この変更には含まれない。アドレスをタスク別に変換する仮想ページ表も追加していない。実行単位に保護情報を加えたことが、プロセスモデルを考えるための新しい足場になる。

## 同じアドレスでも、使える権限は違う

ESP32-P4には、カーネルが使うM-modeと、権限を制限するU-modeがある。MはMachine、UはUserを表す。保護タスクだけをU-modeで再開し、カーネルやデバイス制御はM-modeに残す。

ここではタスクごとにアドレスを変換し直していない。CPUから見た同じアドレス範囲に対して、読出し、書込み、命令の実行を許すかを制限する。PMPはこのアクセス権の検査を行う。外部FlashやPSRAMを窓へ対応付けるMMUとも、プロセスごとの仮想記憶とも役割が違う。

Rは読出し、Wは書込み、Xは命令の実行を表す。

{{figure:protected-addresses}}

図の範囲は役割を示す模式図で、アドレス順ではない。コードはRX、専用アリーナはRWとし、アリーナの一部をスタックに使う。それ以外のカーネル、ROM、周辺回路は保護タスクに許可しない。M-modeのカーネルがROMの関数や周辺回路を使うことまで、禁止する設定ではない。

保護情報は小さい。

{{snippet:task-protection}}

各範囲は下端を含み、上端を含まない。実装は128バイトの境界に揃え、空の範囲、重なり、桁あふれなどを拒否する。この128バイトは対象チップのPMPの粒度であり、Cの型の整列や、スタックの16バイト整列とは別の条件である。

PMPのTOR（Top of Range）は、下端と上端で範囲を表す方式である。今回の二範囲は、それぞれ二つ、合計四つのPMPエントリを使う。カーネルは自分の管理情報を使って設定し、利用者の要求した任意の範囲をそのまま許可しない。

## 切り替えるのはレジスタだけではない

整数レジスタの保存フレームは従来と同じ128バイトである。そこへ特権状態を混ぜてABIを変える代わりに、`ReturnState`が`mstatus`と`mcause`を別に持ち、選んだ実行イメージが`Protection`を参照する。

`mstatus.MPP`は、例外から戻るときの特権モードを指定するフィールドである。保存状態をU-modeにしても、保護情報がなければ再開してはいけない。逆に、保護タスクをM-modeへ戻したら、PMPで制限する意図を失う。登録、捕捉、選択で対応を検査する。

`mcause`は例外や割込みの原因を表すレジスタである。このチップでは割込みからの復帰状態にも関係するため、選んだタスクの権限と、今処理しているトラップの原因を分けて用意する。

{{snippet:privilege-contract}}

{{figure:protected-return}}

スケジューラは従来どおりタスクを選び、その後の機種側の経路が保護設定を反映する。利用者へ戻る直前に、そのCPUのPMPへコードとアリーナの許可を入れる。カーネルタスクを選んだ場合は、その許可を取り除く。割込み中に利用者の設定を変更させないよう、MIEというマシン割込みの許可は復帰準備の間クリアしたままである。

図のU-modeへ戻る経路は、正常なECALLやタイマー処理の後などに使う。故障した元のタスクへ戻る経路ではない。故障の場合は、後の回収の図で追う。

PMPはタスクごとの表が自動で切り替わる機構ではなく、CPUごとの設定である。今回U-modeを実行するのはCPU0だけであり、CPU1へ移動させるには、移動先の設定と所有権の契約も必要になる。

復帰時の`mcause`にも注意がある。選んだタスクの以前の例外原因を戻すのではなく、今処理しているトラップのCLIC状態を使う。

{{snippet:active-trap-return}}

CLICはこのチップの割込みコントローラである。P4では`mcause`の一部が`mstatus`の特権情報と関係するため、アセンブリは`mcause`を先に、選択したタスクの`mstatus`を後に書く。同じレジスタ名を持つRISC-VのCPUでも、機種固有の復帰条件まで同じとは限らない。

## 関数呼出し、権限の切替、タスクの切替

`ecall`を使っただけで、保護境界ができるわけではない。M-modeのタスクも同じ命令でカーネル処理を要求できる。何が変わったかを三つに分けよう。

| 操作 | 実行するタスク | 権限 |
| --- | --- | --- |
| M-modeで通常の関数を呼ぶ | 同じ | M-modeのまま |
| M-modeのタスクからECALLし、同じタスクへ戻る | 同じ | M-modeのまま例外処理を行う |
| U-modeからECALLし、同じタスクへ戻る | 同じ | U→M→U |
| タイマーでAを中断し、Bを選ぶ | 変わる | AとBの種類に応じて変わる |

権限の切替と、実行コンテキストの切替は別の操作である。U-modeのタスクからのECALLは原因8、M-modeからのECALLは原因11として届く。保護タスクは整数の番号とスカラ値を渡し、利用者ポインタを引数としてカーネルに読み書きさせない。

世代付きハンドルが正しいことと、その操作を許してよいことも別である。保護タスクから他タスクを指定する`wake`や`notify`は許可しない。これはプロセス間通信の能力を完成させたAPIではなく、他者へ作用する操作を狭めた入口である。既存のSPSCやコピー型RPCを、そのままU-mode向けの通信路として使えるわけではない。

## 不正なアクセスから、どこへ戻るか

保護タスクがカーネルのRAMをロードすると、読出しのアクセス例外が起きる。失敗した命令を再実行し続けたり、カーネル全体を停止したりする代わりに、そのタスクを終了させる。

例外入口では、まずカーネルが用意した割込み用スタックへ退避する。利用者のSPがアリーナ内に収まることを検査してから、通常の保存フレームを作る。SPが0などの不正値なら、カーネル側の故障用フレームへ切り替える。例外を受けた後の保存処理が、不正なポインタへ書いてしまわないためである。

{{figure:protected-fault-cleanup}}

U-modeの不正アクセスや特権命令などを、保護タスクの故障として処理する。実行基盤は終了値`-70`を残し、資源台帳を閉じ、回収を進める。資源が片づくまでは`reap`しない。最後に管理slotを空け、新しい世代のタスクへ使い直す。この順序は、正しく終了するアプリでも、故障するアプリでも必要である。

台帳を閉じる処理は、選んだ別の実行イメージを公開する前に行う。重い回収はカーネルへ戻ってから進め、完了したかを検査して枠を空ける。選択が済んだことと、次のタスクの命令を実行し始めたことも、同じ時点ではない。

CPUによる不正アクセスを止めても、別のCPUやDMAが借りているバッファの寿命は終わらない。PMPはDMAを止める機構ではない。今回の保護タスク試験から、転送中の任意のアプリを安全に破棄できると結論してはいけない。借り手がいる場合の回収条件は{{ch:io-lifetime}}で扱う。

## 正しい許可表でも、例外を処理できなかった

PC上のエンコーダが許可・拒否を正しく計算しても、チップ上のアクセスが同じように終了するとは限らない。Tab5のESP32-P4 revision v1.3では、CLICの`0x20800000`をU-modeでロードするケースが停止した。PMPの範囲を変えても、そのロード後の行が出なかった。

タイムアウトだけでは、どこで止まったかは分からない。別のCPUから進行を観測し、許可されたアリーナへロード直前の印を残すと、その印までは実行され、新しい例外入口の記録がないことが分かった。後からJTAGで停止させたときは、M-modeのバスエラー状態を読めた。ただしデバッガが介入した後の値から、内部の停止機序を断定することはできない。

対象チップは、ロード・ストアのバスエラーを既定で非同期に扱う。失敗したアクセスの後まで命令が進む場合があり、通常の同期例外と同じ前提では扱えない。そこで、[v1.3の技術資料](https://documentation.espressif.com/esp32-p4-chip-revision-v1.3_technical_reference_manual_en.pdf)の同期バスエラーモードを使った。

`mhint.SBE`を設定すると、同じPMP配置のCLICロードが、利用者の`lw`命令で例外となり、カーネルへ戻れた。最終実装は保護計画を有効にするときにSBEを立て、取り除くときにクリアする。他の`mhint`ビットは保つ。`user_mhint`というログ値は、利用者自身が特権CSRを読んだ値ではなく、カーネルがそのタスクの処理中に読み返した値である。

ブートローダの設定も保護契約に含まれる。以前のROMのRX許可が残っていれば、利用者はアリーナ以外のROMも実行できる。PMPのLビットは設定をロックし、M-modeにも権限を適用するが、U-modeを自動で禁止するビットではない。実装はROMを含む拒否設定へ改め、古いローダのままなら保護タスクの登録を拒否する。ローダから例外復帰までを、一つの境界として確かめる必要があった。

## 成功の表示を、四つの観測へ分ける

[保存されたUARTログ](repo:docs/measurements/2026-10-30-pmp-synchronous-faults/probe.log)には、ケースごとに終了、復帰、回収、保護設定が記録されている。

| ケース | 何を確かめるか |
| --- | --- |
| 0 | 許可したECALL、U-mode中のタイマー割込み、正常復帰 |
| 1〜5 | 範囲外ロード、コードへの書込み、データの実行、不正SP、特権命令 |
| 6〜8 | HP周辺回路、キャッシュ制御、CLICのロード拒否 |
| 9〜11 | 有効なカーネルRAM、ROMの読出し、ROM先頭での実行拒否 |

Tab5 v1.3で、電源を切らずにUSB経由でリセットするwarm resetを三回行い、全12ケースを確認した。故障した保護タスクだけが終了し、保存したカーネル状態は`mstatus=00001880`、利用者用の許可は解除された。slot 1は世代1〜12として使い直された。ケース0はカーネル側の割込み回数だけでなく、U-modeのタスクを実際に中断したことを数えている。

ROMのケースは、どこかで故障すれば成功なのではない。命令の取得を拒否した位置が`mepc=4fc00000`であることを確かめる。ROMに入ってから別の命令で落ちた場合を、入口の拒否と取り違えないためである。

ESP-EMU v0.50.0でも12ケースの故障と復帰は確認するが、SBEの読戻しは再現しない。ログは`sbe_evidence=unmodeled`と明記する。ホストの許可表、エミュレータの制御経路、実機の例外、元のFlashの復元確認は、それぞれ別の証拠である。冷間電源投入、他のチップ版、DMAの隔離、任意のアプリのローダは、この記録では保証しない。

## 守るための費用も測る

同期モードはロード・ストアの待ち時間を増やすため、常に有効にはしない。保護計画のない通常タスクだけを動かす経路は、PMPを書き換える処理へ入らない。登録の検査をFlashへ置き、割込み時の保存・選択はSRAMに残すという配置も選んだ。

360 MHzの実機で、PMP切替の最大観測値は5,146サイクル、約14.29 µsだった。C側のディスパッチは22,224サイクル、約61.73 µsである。カウンタを読む費用と、その実行で遭遇したキャッシュの影響を含む。アセンブリの入口・出口を含む割込み禁止時間全体や、最悪時の上限ではない。正常なアプリの処理量が何倍になるかを測った値でもない。

## 手元では、許可表と記録を読む

最初の実験で使った古い版とは別に、次の作業用コピーを用意する。コマンドはリポジトリのルートから実行する。既存の同名ディレクトリは使わない。

```sh
git worktree add --detach ../nihos-pmp-book \
  d86fcf0ffda44f7a464531d318ddf6442127993b
cd ../nihos-pmp-book
sh tools/bootstrap-zig.sh
```

このコピーのルートで、PMPのホストテストを実行する。

```sh
.tools/zig-0.17.0/zig test src/arch/riscv32/pmp.zig
```

RXのコード、RWのアリーナ、その外へのアクセスについて、読出し・書込み・実行の三列の表を紙に作ろう。`grant`と`permits`のテスト結果を予想と比較する。ここで通るのは符号化と検査であり、PCがTab5のPMP例外を起こしたわけではない。

次に、実機ログのケース8と11から、故障した命令、終了値、カーネルの状態、slotと世代を拾う。一つでも欠けていたら、どの主張を保留すべきか考える。故障した直後にアリーナを返す案には、CPUやデバイスがまだ参照している場合の反例を一つ作ってみよう。

ビルドだけを調べる追加手順は、[診断構成の作り方](repo:docs/native-user-pmp.md)にある。通常の起動試験とは別のイメージであり、生成だけでは実機を書き換えない。本書では書込みを自動実行しない。

この章で増えたのは、タスクの数やスケジューリング方式ではなく、復帰させる状態へ結び付けた保護契約である。次の{{ch:bounded-memory}}では、アクセスできる領域の内側を、誰へどう配るかを考える。
