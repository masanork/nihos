# メモリを返して使い直す

文書を閉じ、検索結果を捨て、次の仕事を始める。これらの寿命が違うなら、{{ch:bounded-memory}}のアリーナを一度にリセットするだけでは困る。まだ使う文書まで無効にしてはいけないからだ。

この章では、個別に返せるヒープが何を管理するかを読む。CPUごとの所有、割当の管理情報、断片化と結合を調べ、空き容量が大きければ常に要求を満たせるという予想を検査する。PC上のバイト配列で実験でき、PSRAM実機の動作は前提にしない。

## 寿命から割当方式を選ぶ

空き領域を管理する問題は、カーネルにも、アプリケーションの割当ライブラリにも現れる。[OSTEPの空き領域管理の章](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-freespace.pdf)は、可変長の領域を分けるときの断片化と、方式ごとの時間・空間の費用を扱っている。nihosのバディヒープも、その問題に対する一つの選択である。

たとえば、文書を一つ開く間だけ必要なもの、毎回同じ大きさで届く要求、個別に閉じる複数の検索結果では、返す時点と領域の形が違う。次の表は方式を考え始めるための対応であり、用途ごとの唯一の答えではない。

| データの使い方 | 最初に検討する方式 |
| --- | --- |
| 一まとまりの処理が終わるとすべて不要になる | アリーナに集め、寿命の終わりにまとめて返す |
| 同じ大きさの要求を上限付きで繰り返す | 固定サイズのプールで空き枠を管理する |
| 異なる大きさを別々の時点で返す | 個別解放できるヒープを使い、断片化と管理情報を調べる |

いつ返すかを決める責任も分けられる。プログラムが明示的に解放する場合も、オブジェクトの寿命に合わせて解放処理を呼ぶ場合もある。GCを持つ処理系では、到達できる参照を調べる方法などで回収の時点を決める。その下でも、使える領域を分け、管理情報を持つ仕事は必要になる。本章では、個別解放を受け付ける仕組みに範囲を絞る。

## 最初に、どのCPUの領域かを決める

同じ領域を二つのCPUが同時に割り当てれば、個別の計算が正しくても重複する。nihosは、起動時の領域を二つの所有者へ分け、通常の割当を所有CPUで直列化する。

[CoreArena](repo:src/kernel/core_arena.zig)では、呼び出し元の所有者を検査してから、前に読んだアリーナへ仕事を渡す。

{{snippet:core-arena-alloc}}

領域の両端にはガード用のバイト列を置き、その部分を利用者へ渡さない。ガードは境界を越えた書き込みを後で検出する手掛かりになる。ただし、CPUのアクセスを止める保護機構ではない。所有者番号もカーネル内部の約束であり、任意のマシンモードコードに対する権限分離にはならない。

[ネイティブ側の接続](repo:src/platform/native/memory.zig)では、自CPUの割込み状態を保存して、共有される割当状態の更新を直列化する。単にCPUごとへ分けただけでは、同じCPUで割り込んだ二つのタスクの競合までは解決しない。

## 解放できるようにする費用

バディ割当器は、領域を2の累乗の大きさのブロックとして扱う。必要な大きさまで分割し、解放したときに同じ親を持つ空きブロックが揃えば結合する。

{{figure:buddy-tree}}

図は分割の例で、ヘッダやガードを含む全メモリ配置図ではない。左下の64 Bを返すと、同じ親のもう一つの64 Bも空きになり、128 Bへ戻せる。その後なら右の128 Bと結合して256 Bへ戻せる。大きさが同じ空きblockなら、どれでも結合できるわけではない。

nihosの最小ブロックは64バイトである。木の各節点は、その下で使えるブロックの大きさなどを表す。物理的な配置には、木を保存する領域、前後のガード、実際のデータ領域が必要になる。

一つの割当にもヘッダがある。本章で扱うヘッダは16バイトで、要求長、データ領域のオフセット、割当を識別する割当番号を持つ。整列のためのパディングも加わるため、要求したバイト数と消費するブロックの大きさは一致しない。

たとえば長さ32、整列 8なら、実装が見積もる必要量は`32 + 16 + 7 = 55`バイトで、64バイトブロックに収まる。長さ48なら71バイトとなり、128バイトブロックが必要になる。ここではパディングの最大量を含めて、要求を満たすブロックを選んでいる。

この方式は管理を単純にする一方、小さなオブジェクトが多い用途では無駄が増える。{{ch:c-library}}では、バディヒープの上へ小さいサイズを扱う層を重ね、SQLiteの要求へつなぐ。

## 空き総量と最大ブロックは違う

64バイトのブロックが交互に空いていても、隣の相方が使用中なら、128バイトへ結合できない。空き総量は増えていても、大きい要求に応えられない。

その条件を作る既存テストを見よう。

{{snippet:heap-fragmentation}}

最初に、全データ領域を最小ブロックの割当で埋める。偶数番だけを返すと、空きは飛び飛びになる。そこで長さ48の要求は失敗する。隣の一つも返してバディが揃うと、同じ要求が成功する。

最後にすべてを返した後、`free_bytes`が元のデータ領域容量へ戻ることを確認する。「途中で一度確保できた」だけでなく、寿命を終えた資源を再利用できる状態まで戻せることが重要である。

## 同じアドレスでも、同じ割当ではない

解放後に次の要求を行うと、同じアドレスが返ることがある。そのため、アドレスだけを識別子にして古い解放要求を受け付けると、新しい利用者のメモリを解放しかねない。

[バディヒープ](repo:src/kernel/buddy_heap.zig)の割当結果は、バイト列に加え、所有者、節点、割当番号を持つ。解放時に、所属するヒープ、ブロックの範囲、ヘッダの長さとオフセット、割当番号などを検査する。割当番号が尽きたら、古い値へwrapして再利用せず、割当を拒否する。

これは古いハンドルによる解放の検出である。古いスライスを使ってデータ領域を直接読み書きすることまで防げない。また、ヒープ全体を作り直した後まで同じ割当番号の一意性を保証する仕組みではない。タスクの世代番号と同様、どの寿命の範囲で識別するかを決める必要がある。

管理情報やガードに矛盾を見つけた場合は、ヒープを異常状態にして、その後の操作を止める。正常な要求が容量不足だった場合と、構造を信用できなくなった場合を分けている。

## PC上で断片化を観察する

リポジトリのルートで実行する。

```sh
.tools/zig-0.17.0/zig test src/kernel/core_arena.zig
.tools/zig-0.17.0/zig test src/kernel/buddy_heap_test.zig
.tools/zig-0.17.0/zig test src/kernel/buddy_heap_test.zig \
  -O ReleaseSafe
```

本章で扱うバディヒープには13個のテストがある。断片化のほか、二重解放、古い割当番号、別所有者、壊れた木、ガードの破損などを検査する。決定的な4,000操作の確保・解放の反復では、使用中の内容、領域の非重複、最終的な容量回復を確認する。

条件変更の演習では、作業用コピーで上の断片化テストの要求長48を32へ変える。偶数ブロックだけを返した時点でも成功するはずだと予想できるだろうか。期待する結果を変更し、返された割当も正しく解放する。続いて48へ戻し、失敗の理由をヘッダと整列込みで説明しよう。

演習では、失敗した要求によって空き容量や使用中の割当が変わらないことも確認する。確保できた結果と、確保できなかった結果の両方が、割当器の契約である。

設計の演習では、編集中の文書、一回の検索で作る一時データ、サービスへの固定長の要求を選び、それぞれの寿命と最大個数を仮定する。すべてを一つのヒープへ置く案と、用途ごとに領域を分ける案を比べよう。空きを融通できる範囲、容量不足の影響を閉じ込める範囲、記録すべき使用量がどう変わるかを考える。

## 操作数の上限と実時間

確保と解放では木の経路を辿る。[検証記録](repo:docs/measurements/2026-10-26-native-reusable-heaps.md)による訪問節点数の上限は`3 * levels + 2`で、ガード走査とヘッダ処理は別に行う。

実時間を知るには、命令数、キャッシュミス、割込みを止める区間、外部メモリの待ちを測る。大きなデータの塗りつぶしは割込みを戻してから行い、管理情報の更新と分ける。

ESP-EMUでは割当・解放の反復後に使用中の割当数0と容量回復を確かめた。実機の接続は{{ch:psram-and-evidence}}、タスクと割当器の関係は{{ch:c-library}}で扱う。

## 読み終えたら確かめること

アリーナとバディヒープを、使うデータの寿命で選び分けよう。空き総量、最大ブロック、利用者へ返す長さをそれぞれ説明し、ガードと割当番号が検出できる問題と、検出できないアクセスを挙げてみよう。
