# カメラを動かし続け、止める

一枚撮れるカメラを、動くプレビューへ育ててみよう。次の画像を撮り始めるとき、前の画像をCPUがまだ読んでいたらどうなるだろう。表示を閉じるキーを押した瞬間に、転送中の領域を解放してよいだろうか。

{{ch:machine-basics}}で説明したDMAとキャッシュ、{{ch:io-lifetime}}の所有権と停止の条件が、一つの機器の中で結び付く。ここでは、通常構成への統合、更新の高速化、連続転送という三段階を追う。各段階の測定は異なる候補の結果であり、後の実装へまとめて引き継がない。

## センサーから、表示用の小さい画像へ

カメラのセンサーは、光を画素の値へ変える。撮影条件はSCCBという制御用の通信で設定し、画像はCSIという別の接続で受ける。受けた画像を処理するISPと、メモリへ転送するDMAを通して、CPUから読めるようにする。

この参照版は、センサーから1280×720のRAW8、すなわち一画素一バイトの生データを受ける。転送先は921,600バイトになる。プレビューはそこから80×45のグレースケール標本を取り、320×180へ拡大する。画面へ出す標本の画素数と、DMAが受け取る画素数は違う。

{{figure:camera-data-path}}

CPUがPSRAMを読む前には、対象のキャッシュラインを無効にし、DMAが書いた値を読み直す。初期の引渡し後、CPUは撮影用の二領域へ書き込まない。表示に使う標本は別の作業領域へ写し、撮影用領域を返した後も安定したコピーから描く。

標本を二回読んで比較し、描いたフレームバッファとも比較する。ただし、これらが一致しても、被写体の色、焦点、光学的な見え方まで確かめたことにはならない。

## 単独の試作を、いつもの構成へ入れる

カメラ専用の試験で動いた機能を、ネットワーク、ストレージ、他の機器を含む通常イメージへ入れた。すると、最初は読み出し専用のFlash配置領域に収まらなかった。詳細な診断出力を診断用構成だけへ限定し、公開する通常構成の領域を守った。

次には、内部SRAMに残すヒープ領域が既存の最低値49,152バイトを22,080バイト下回った。測定用の別ELFで不足量を調べ、製品用の検査条件は保った。最低値だけを下げると、統合に成功したように見えても、後から使う機能の余地を失うからだ。

標本処理の3,800バイトの作業領域は、初回利用時にPSRAMへ確保する方式へ変えた。確保できなければ、機器を動かす前に要求を拒否する。また、通常の前景処理のうち指定した五つの入口を、既存のFlash実行領域へ移した。割込み、トラップ、キャッシュを使えない制御経路はSRAMまたはROMへ残す。どの関数でもFlashへ移せるわけではない。

[通常構成への統合記録](git:980f522a3575c3922b956bf97f46a228b557070d:docs/measurements/2026-10-30-camera-normal-profile.md)の候補では、SRAMのヒープ両端間は51,776バイトとなった。これは予約可能な区間の幅であり、実行中の空き容量を測った値ではない。

## 遅さの一部は、待ち方にあった

最初のプレビューは、一枚ずつ撮って停止する処理を繰り返していた。約130回のセンサー設定、キャッシュの準備、90回の標本行読取りを、10 msごとに進む前景処理へ細かく分散していたため、機器の転送以外にも待ち時間が積み上がった。

そこで、一度に進める仕事をまとめ、反復回数の上限と経過時間の検査を間に置いた。撮影が続く間は停止済みセンサーの設定を再利用し、500 ms使わなければセンサーとクロックを止める。必要な機器の待ち時間や転送停止の観測は残した。

| 段階 | 標本の表示間隔の平均 | 観測条件 |
| --- | ---: | --- |
| 通常構成の初期候補 | 2.366秒 | 5更新、4間隔 |
| 一枚ずつ撮る方式の改善後 | 0.209秒、0.210秒 | 同一候補の独立した二試行、各60更新 |
| 二領域による連続転送 | 58.20 ms、56.87 ms | 別の同一候補の独立した二試行、各61更新 |

上の時間は、完全なUART記録をホストが受信した時刻の差であり、初回起動を除き、ログ送信の負担を含む。異なる候補の段階比較として読む。単純な繰返し撮影の改善は、連続DMAの実装より先に成立している。[更新間隔の比較記録](git:980f522a3575c3922b956bf97f46a228b557070d:docs/measurements/2026-10-30-camera-preview-cadence.md)には、そのときのソースとイメージの識別情報がある。

高速化すると、それまで見えなかった停止時の不具合が現れた。20更新後に閉じる操作が失敗したため、シェル全体の再描画を転送の排出完了まで待たせた。また、センサー制御の応答拒否が長めの試行で現れ、短い同期書込みと読戻しの組に限ってCPU0の割込みを禁止する変更を加えた。後続の有限試験は通ったが、電気的な原因や最悪割込み遅延の上限を特定した結果ではない。

## 読んでいる画像を、次の画像で壊さない

連続転送では、センサー、CSI、ISPを動かしたままにし、DMA完了の割込みで次の転送を設定する。撮影用領域は二つだけである。CPUが完了済みの領域Aを借りている間は、DMAは領域Bを使う。Aが返らなければ、Bを繰り返し使い、その間のフレームを捨てる。

これは、すべてのフレームを保存する録画の方針とは異なる、プレビューのための選択である。表示が追いつかないときにも、借り手の画素を壊さず、無制限に領域を増やさない。処理能力が足りないときの扱いを明示することを、バックプレッシャーの設計と呼ぶ。

{{figure:camera-buffer-ownership}}

このプールはCPU0で直列化し、貸出しには世代番号を付ける。前の撮影セッションの返却が遅れて届いても、新しいセッションの貸出しを解除しない。共有するDMAの割込みでは、表示用のチャネル0の通知を消さず、カメラ用のチャネル1の完了を処理する。コントローラ全体を無条件にリセットすれば、別の機器の仕事まで壊してしまう。

## バイト数だけでなく、管理枠も足りるか

二枚目を別に確保した初期候補は、DMAを始める前に失敗した。タスクが持つ割当て記録の二枠を、撮影領域と作業領域で既に使っていたためだ。空きPSRAMを増やしても、記録枠の不足は解消しない。

最終候補は二枚分を一つの親領域にまとめた。内訳は次のようになる。

| 項目 | 量と寿命 |
| --- | --- |
| 撮影データ二枚 | 921,600バイト×2 |
| 二枚を含むbuddy予約 | 2,097,152バイト |
| 別の標本用作業領域 | 4,096バイト |
| 初回利用後に残る既知の予約 | 合計2,101,248バイト、リセットまで保持 |

一枚撮影から始めても二枚分を予約するため、従来の一枚方式より1 MiB多い。ランチャーを起動しただけでは確保しない一方、撮影を閉じても、この版では撮影領域と開始済みチャネルを一般的に回収する仕組みはない。

[連続撮影の記録](git:980f522a3575c3922b956bf97f46a228b557070d:docs/measurements/2026-10-31-camera-continuous.md)では、処理後の再利用PSRAMヒープは容量15,072,576バイト、空き12,971,328バイトだった。このヒープの範囲での値であり、基板全体の空きRAMや他のアプリケーションが使える容量には置き換えない。同じ候補のSRAMヒープ区間は50,624バイトで、前の統合候補の値とも区別する。

## 閉じる要求と、停止完了を分ける

停止要求を受けると、新しい貸出しと、次の完了後の再転送設定を止める。前景処理はセンサー停止、DMA停止の観測、ISPとCSIの停止を進め、最後にシェルを描き直す。表示が正しくても、停止済みのCSIのクロックを切った後にそのレジスタを読む候補は停止処理で失敗した。最終版はクロックの状態を確かめてから読む。

進捗が五秒途絶えた場合や、DMA、受信回路、標本比較で異常を検出した場合も再転送を止める。転送停止が不確かな領域は保持する。タイムアウトしたというだけで、DMAがもう触らないと結論してはいけない。

二つの実機試行では、60更新後に閉じる操作を送り、Escapeの認識前にもう一枚が表示された。検査器はこの一枚を許容し、排出完了の記録後には一枚も表示しないことを確認した。入力を送った時点、OSが認識した時点、転送が終わった時点を分けると、何を禁止する検査かが明確になる。停止から排出までは284.62 msと262.42 msだった。

## 実機で観察できたこと

ESP32-P4 revision 1.3のTab5で、同じ最終イメージを二回試した。各試行は連続表示、停止、一枚撮影、読込み中の停止、待機後の再撮影、メモリ表示まで進んだ。連続区間は約3.5秒で、標本の表示更新は17.18回／秒と17.58回／秒だった。全体では各63画像を提示し、標本から描いたフレームバッファとの不一致はなかった。

DMA完了と破棄のカウンタは107／45、104／43だった。表示数とDMA完了数が同じにならないこと自体が、遅い借り手を保護してフレームを捨てる方針を表している。数の対象には停止時の進行中転送もあるため、単純な引算で提示数を決めない。

同じイメージで両CPUやネットワークサービスの進捗は観察したが、Wi-Fiは未設定で、ファイル読取りは媒体エラーで拒否された。通信やSDの持続負荷との共存、物理キーとタッチ、冷電源投入、長時間撮影、カラーや全解像度の動画、パネルの光学的な見え方は別の確認になる。

## PC上で、所有権の規則を読む

```sh
git worktree add --detach ../nihos-book-camera \
  980f522a3575c3922b956bf97f46a228b557070d
cd ../nihos-book-camera
sh tools/bootstrap-zig.sh
.tools/zig-0.17.0/zig build test
```

この手順はホストテストであり、書込みや実機接続を行わない。先に測定記録のレジスタ再生試験の説明を読み、貸出し中の繰返し破棄、古い世代の返却、クロック停止後の処理という三条件を探そう。実機手順は[実習環境](practice-notes.md)の候補識別と復元の条件も伴う。

演習では、領域Aを借りたままDMAが三回完了する時間線を描く。各時点で、CPUが読める領域、DMAが書ける領域、捨てるフレームを示そう。次に、Aの返却前に閉じる要求を入れ、どの条件が満たされるまで領域を再利用できないかを考える。
