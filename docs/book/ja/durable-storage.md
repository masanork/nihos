# 保存できた、と言ってよいのはいつか

ノートを編集して保存ボタンを押した。成功の表示が出た直後に電源が切れ、再起動すると前の文章へ戻った。途中の保存を失う場合と、成功を知らせた保存を失う場合を、同じ結果として扱ってよいだろうか。

{{ch:io-lifetime}}では、I/Oが領域から手を離す時点を考えた。この章では、書いた内容を次の起動へ渡す時点を考える。まず小さい媒体モデルで公開順序を調べ、次にホストのファイルへ接続する。実機の書込み試験へ進む前にも、OSの約束を具体的な反例で確かめられる。

## 読める、書ける、残る

{{ch:c-library}}のSQLiteはメモリ上のデータベースだった。SQLが実行できることから、電源を切っても結果が残るとは言えない。同じように、ファイルへwriteしたことと、永続化を確認したことは異なる。

ここでは、書込み内容を保持する一時的なcacheと、電源断後にも残るstable imageを分けた[媒体モデル](git:8b1c3c24fae826699829488c0af2834700945a4d:src/storage/model_media.zig)を使う。成功したsyncは、その前のdirty sectorをすべて永続化する。sync前の書込みも、一部または全部が先に残る場合がある。中断時にはcacheが失われる。

これは検査の前提である。実SDやNORがこの契約を満たすか、どの命令でその状態へ到達できるかは、後で確かめる必要がある。媒体の性質が曖昧なまま、上位の同期関数の名前だけで永続性を約束してはいけない。

## 古いデータを、先に壊さない

保存先をその場で上書きすると、途中で切れたときに旧データと新データが混じる。そこで保存する本文、payloadを別の場所へ書き、最後に、その所在を示す索引の入口、rootを公開する。これが本章で使うコピーオンライト、COWの考え方である。

rootは二つ用意し、交互に更新する。各rootには世代番号、objectの所在、長さ、checksumなどを記録する。一方を更新中にも、もう一方の完全な世代を残したい。

```text
旧root ──→ 旧payload
             保存中も保持

新payloadを書込む
    ↓ payloadをsync
次のrootを書込む
    ↓ rootを含めてsync
成功を呼出し元へ知らせる
```

[最初のストアモデル](git:8b1c3c24fae826699829488c0af2834700945a4d:src/storage/cow_model.zig)は、最大8個のobjectを扱う小さい実装である。更新や削除はtransactionへ積み、commitまで現在の読取りviewへ出さない。公開部分の入口は短い。

{{snippet:store-commit}}

最初のsyncがpayloadを先に残し、`publish`の中でrootを書いてもう一度syncする。両方が通ってから、現在のviewを進める。片方でも失敗したら、そのinstanceで書込みを続けない。

## 中断した保存と、成功した保存

{{figure:cow-publication}}

上から下へ進む途中で止めた場合と、最後の成功通知を受けた後で止めた場合を分けよう。新rootが指すデータを先に残す順序と、成功通知までにrootを残す順序の、両方が必要になる。

中断した保存では、旧世代または完全な新世代が残ることを許す。成功通知の前にも新世代が媒体へ到達し得るため、必ず旧世代へ戻るとは限らない。

一方、成功通知の後は、新世代を回復できなければならない。成功したと聞いた利用者が、その後に別の仕事を進めるからだ。

| 中断する時点 | 復旧後に許す状態 |
| --- | --- |
| 更新の途中、成功通知前 | 完全な旧世代または完全な新世代 |
| commitの成功通知後 | 成功した新世代 |
| 初回rootの公開途中 | 完全な初期root、未初期化、または破損の明示 |

初回の公開では、戻れる旧世代がない。壊れた媒体を空の媒体と見なして自動formatすると、失敗の跡を消してしまう。復旧は、世代、版、範囲、重複、checksumと参照先を検査し、どの候補を採用したか説明できる処理にする。

CRCは偶発的な破損を調べる材料であり、作成者の認証を与えるものではない。また、rootだけの整合性を見ても、その先のpayloadが残っているとは限らない。

## 古い世代へ戻れれば十分か

最初の同期を外し、rootの書込みを先に永続化できると、新しいrootだけが残る場合がある。復旧処理がそのpayloadの不整合を検出して旧世代へ戻れば、表面上は旧・新のどちらかになっている。

しかし、公開手順が作った正しいchecksumのrootが、残っていないpayloadを指してよいわけではない。このモデルでは、そのような公開rootも検出する。戻れたという結果だけで、公開順序の誤りを隠さないためである。

[中断試験の記録](git:8b1c3c24fae826699829488c0af2834700945a4d:docs/measurements/2026-10-27-store-crash-model.md)では、最初のsyncを一つ外した変異版が`DanglingPublishedRoot`で失敗した。別の負例では、payloadだけを保存しrootをsyncしないbackendにより、成功を知らせた世代が再起動後に戻ることを検出した。

検査器の価値は、正しい実装を通すことだけでは決まらない。疑っている誤りを故意に入れ、その誤りの結果を検出できるかも確かめよう。compile errorやevent数の違いだけで止まった結果を、データの不整合を見つけた結果と取り違えない。

## 中断の場所を増やす

モデルは512バイトのsector単位の書込みと、sync開始、dirty sectorのflushを観測する。未同期書込みの残り方を三通り、flush順を二通り、sector内のtear位置を六通りに変える。

objectの置換・追加・削除で2,952条件、truncateなどで648条件、初回公開で612条件、合計4,212条件を検査した。成功通知後の再起動は18条件で、いずれも新世代を回復した。

これは全byte位置や全順列の網羅ではない。有限のモデルで、どの性質を、どの中断条件に対して確かめたかという結果である。試験数を増やす際にも、まだ含まれない故障を言葉にしておきたい。

## processを止めると、何が失われるか

次に[ホストfile backend](git:8b1c3c24fae826699829488c0af2834700945a4d:src/storage/file_media.zig)を接続する。容量が一致する既存の通常ファイルを開き、協調するwriter間で排他的なlockを保持する。短いwriteは残りを継続し、進捗0をエラーにする。ファイルの作成と親directoryのsyncは呼出し側の仕事にする。

[別processの試験](git:8b1c3c24fae826699829488c0af2834700945a4d:docs/measurements/2026-10-27-store-file-backend.md)では、root公開前と成功通知後に、runnerが自分で起動した子processをSIGKILLし、別processで開き直した。公開前には旧世代、成功通知後には新世代が読めた。

SIGKILLで失われるのはprocessの状態であり、OSのcacheは残る。この試験を、電源断でcacheも失う媒体モデルと併用する。二つの結果を合わせても、実SDの電源断試験をしたことにはならない。

syncの失敗も、「何も残らなかった」という意味ではない。rootを書いた後でエラーが返れば、新しい内容が見える可能性がある。新世代を成功として知らせず、復旧時には旧・新の完全な世代を扱えるようにする。保存の結果が不明なことを、成功やrollback済みへ勝手に丸めない。

## 容量が大きくても、全体をRAMへ置かない

8個のobjectの実験から大きな媒体へ進むには、所在を示すindexもページ化する。[後続のcheckpointモデル](git:8b1c3c24fae826699829488c0af2834700945a4d:docs/measurements/2026-10-27-store-checkpoint.md)では、rootが参照するleafだけを読み、mount時にpayload全体を走査しない。媒体offsetは64ビット、手元のbuffer長は`usize`とし、RV32でも4 GiBを超える位置を表せるようにした。

この方式はcommitごとにcheckpointを作る。後続logの再生はまだない。mountの読取り量に上限を置くことと、実機で何秒以内に開けるかを確かめることも別である。

読み続ける者がいるなら、その世代が参照するページは残す。[reader snapshotと回収](git:8b1c3c24fae826699829488c0af2834700945a4d:docs/measurements/2026-10-27-store-index-gc.md)では、現在のroot、もう一方の有効なdisk root、作成中のroot、pinされたreaderを保護する。旧rootをfallbackに使うつもりなら、その先のleafを先に再利用してはいけない。{{ch:io-lifetime}}の「まだ使う者がいる」という問いが、保存された世代にも現れる。

## PC上で、保存の途中を切る

```sh
git worktree add --detach ../nihos-book-store \
  8b1c3c24fae826699829488c0af2834700945a4d
cd ../nihos-book-store
sh tools/bootstrap-zig.sh
.tools/zig-0.17.0/zig test src/root.zig \
  --test-filter 'every write and sync event' \
  --test-filter 'negative control detects'
```

[テスト](git:8b1c3c24fae826699829488c0af2834700945a4d:src/storage/cow_model_test.zig)の`baseline`、`update`、`state`を読み、旧・新の各世代に存在するobjectを表にしよう。途中の状態に、どちらにも属さない組合せが現れないことを検査している。

演習では作業用コピーの最初のsyncを外し、同じ試験を実行する。実行前に、payloadとrootのどちらが残れば破綻するかを描いておこう。失敗後は原本との差分を保存し、変更を戻して再び通ることを確認する。ここで変更するのはホストのモデルで、実媒体へは書き込まない。

この章の成果は、完成したファイルシステムや永続SQLiteではなく、公開と成功通知の条件を検査する小さな実装である。次の{{ch:partial-updates}}では、その正しさを保ちながら、変更していないデータを書き直す費用を減らす。
