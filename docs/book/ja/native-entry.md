# Zigが動き始めるまで

シリアル端末に最初の一行が出た。その行を表示したZigの関数は、誰に呼ばれたのだろう。関数が使うスタックや変数は、その時点でもう使えるのだろうか。

普段のアプリケーションでは、起動の準備をOSやランタイムに任せられる。OS自身を起動するときは、どこまでが用意済みで、どこからが自分の仕事かを決める必要がある。この章では、nihosのnative側の入口を読み、Zigへ入る前の準備と、最初の例外からの復帰を追う。

手を動かす範囲は、PC上でのRV32向けコンパイルとELFの検査までである。{{ch:first-experiment}}のZig環境とPython 3を使い、Tab5への書込みは行わない。ESP-EMUでの実行は、追加の実験として後半に分ける。

## 最初に呼ばれるのはmainとは限らない

電源投入後にCPUが最初に実行する場所と、私たちが書いた関数の入口は異なる。ESP32-P4には書換えられないROMの起動処理がある。通常のFlash起動では、ROMが第2段のブートローダを読み込み、そのローダがアプリケーションのイメージを処理する。第2段のローダはESP-IDFに含まれるものを利用する。

nihosには、ESP-IDFを使って周辺機器を調べる経路と、独立したnativeアプリケーションを動かす経路がある。ここで扱うのは後者である。

```text
ROMの起動処理
    ↓
ESP-IDFの第2段ブートローダ
    ↓ イメージに記録された入口へ
nih_native_start      アセンブリ
    ↓ 最低限の実行環境を用意
nih_native_main       Zig
```

native経路では、ESP-IDFのアプリケーション初期化やFreeRTOSのタスク開始を通さず、nihosの入口へ制御を渡す。ただし、ROMも第2段のローダも残っている。「native」という言葉は、どの範囲をnihosが担当するかと一緒に使おう。[ESP-IDFの起動手順](https://docs.espressif.com/projects/esp-idf/en/v5.4.4/esp32p4/api-guides/startup.html)と、nihosの[独立起動の判断](repo:docs/adr/0018-independent-native-boot.md)を比べると、引き受けた責任が見える。

## CPUが読む入口と、リンカが作る配置

ソース上の関数名だけでは、ローダがどこへジャンプするかは決まらない。コンパイラが作ったコードをリンカが並べ、入口のアドレスを実行形式に記録する。native側の[リンカスクリプト](repo:src/platform/native/esp32p4.ld)では、`ENTRY(nih_native_start)` がその名前を指定している。

この実装は、命令、通常の定数、初期値付きの変数、ゼロ初期化する変数、スタックを内部SRAMへ置く。実験に使う範囲は `0x4ff00000` から `0x4ff20000` の直前まで、128 KiBである。これはこの起動構成が使う窓であり、チップ全体のSRAM容量を表す数字ではない。

Flash側には、ローダが読むためのアプリケーション記述子と、小さな互換用データも置いている。コードが内部SRAMで動くことと、イメージの全バイトが内部SRAM用であることは区別する。配置は、概念的には次のように読むとよい。

| 領域 | 役割 | 起動時に必要な処理 |
| --- | --- | --- |
| `.text`、`.rodata` | 命令、定数 | ローダが対応するRAMセグメントを配置する |
| `.data` | 初期値付きの書換え可能な変数 | イメージの初期値をRAMへ配置する |
| `.bss` | ゼロ初期化する変数 | nihosが確保範囲をゼロで埋める |
| スタック、起動用heap | 呼出しと割当のための予約領域 | 範囲を決め、利用する側が準備する |

ELFは、入口やセクション、シンボルを調べられる実行形式である。Flashへ書くESP形式のイメージは別に作る。ELFの検査で配置が正しく見えても、ローダが実際に起動できたことにはならない。

## Zigへ入る前の準備

CPU0の入口を、そのまま読んでみよう。

{{snippet:native-entry}}

`csrci mstatus, 8` は、この入口で通常のマシン割り込みを禁止する操作である。割り込み先やスタックを準備している途中に、タイマなどの処理へ入らないようにする。同期例外まで起こらなくなるわけではなく、あとで自分から実行する `ecall` も例外を起こせる。

`gp` と `sp` はレジスタの名前である。`gp` は静的データへの参照に使う基準、`sp` はスタックの現在位置を表す。`la` は指定したシンボルのアドレスをレジスタへ入れる疑似命令で、`__stack0_top` などの値はリンカが決める。

`gp` の前後にある `.option norelax` は、この初期化をリンカの命令短縮の対象から外すための指定である。まだ値が決まっていない `gp` を使う形へ変換されると、初期化にならない。レジスタを使ったコードが生成される前提と、そのレジスタを用意する処理の順序にも注意が要る。

Zigの関数に入れば、コンパイラは関数呼出しや局所変数のためにスタックを使えるものとしてコードを生成する。そのため `call nih_native_main` より前に `sp` を設定する。スタックは低いアドレス側へ成長するので、最初は予約範囲の上端を指す。別のCPU用には別の範囲があり、同じスタックを共有しない。

最後の `j .Lhalt` は、戻らないはずのZig側から制御が返った場合の行き先である。その先では割り込みを禁止して待ち続ける。入口の後ろに偶然並んだコードへ流れ込ませない、という失敗時の約束にもなっている。

## 変数の初期値は、誰が実現するのか

次に、二つのアドレスの間をゼロで埋めるループへ戻る。リンカ側には、対応する範囲がある。

{{snippet:native-bss}}

`.bss` の開始と終了をシンボルにし、起動側がその区間を処理する。`NOLOAD` の指定だけでRAMの内容がゼロになるわけではない。ゼロを並べた大量の初期値をイメージに持たず、実行時に用意する仕組みである。

入口のループでは、`t0` を開始、`t1` を終了として使う。`sw zero, 0(t0)` が4バイトを書き、`addi t0, t0, 4` が次の位置へ進める。`bgeu` は二つを符号なしで比べ、開始位置が終了へ達したら抜ける。`1b` は手前の番号1のラベル、`2f` は後ろの番号2のラベルを指す。

このコードは4バイト単位で処理するため、範囲の先頭と末尾もその単位に合っている必要がある。リンカ側の16バイト整列は、その条件も満たす。リンカと起動コードは別ファイルにあるが、一つの約束を分担している。

Zig側には、次のような状態が置かれる。

{{snippet:native-boot-state}}

`progress` などの配列はゼロ初期化、`initialized` は `0x4e494853` という初期値を持つ。後者は `.data` 側に配置される。ソースに初期値を書くことと、RAM上にその値を用意することの間には、ローダと起動処理の仕事がある。

CPU1の入口には、この `.bss` 全体を消すループがない。CPU0が準備し、共有状態を作ってからCPU1を起こすためである。CPU1が同じ初期化を繰り返すと、すでにCPU0が書いた進捗や準備結果まで消してしまう。初期化にも、誰が一度だけ実行するかという所有者が必要になる。

## 関数から戻ることと、例外から戻ること

`call` と `ecall` は、名前が似ていても違う経路である。`call` は通常の関数呼出しで、戻り先をレジスタに残す。一方、`ecall` は命令の実行をきっかけに同期例外を起こし、CPUに設定したtrapの入口へ入る。

trapは、同期例外と外部要因による割り込みを含めた制御移動の総称である。本章では、発生させる位置を自分で選べる同期例外を使う。タイマ割り込みとタスク切替を同時に調べる前に、行き先と戻り先を確かめられるからだ。

```text
nih_native_main
    ↓ ecall
CPUが例外の原因と発生位置を記録
    ↓ mtvecで指定した入口
nih_native_trap
    ↓ レジスタを保存してZigへ
nih_native_dispatch
    ↓ 保存した復帰位置を更新
アセンブリが状態を復元してmret
    ↓
ecallの次の命令
```

`mtvec` はtrap入口を設定するレジスタである。この実装ではESP32-P4のCLIC用の設定も加える。下位ビットの指定や割り込み制御は、一般的なRISC-Vの例をそのまま写せる部分ではない。詳細は[trapの契約](repo:docs/adr/0005-riscv-context-and-trap-contract.md)と[実際の入口](repo:src/platform/native/start.S)で追える。

例外の発生位置を記録する `mepc` は、`ecall` 自身のアドレスを指す。ここで同じ位置へ戻れば、また同じ例外を起こす。起動直後のdispatcherは、この `ecall` が4バイトの命令であることに合わせて、保存した復帰位置へ4を加える。命令の長さも、復帰の判断に必要な条件である。[RISC-V特権仕様](https://docs.riscv.org/reference/isa/v20240411/_attachments/riscv-privileged.pdf)では、ECALLで記録する位置と例外復帰の規則を確認できる。

trap入口は、Zigへ渡す前にレジスタを保存し、復帰時には選ばれた状態を戻す。通常の関数呼出しの規約だけでは、途中で止めたコードが使っていた全ての値を守れない。また、例外が起きればCPUが自動でnihosの専用スタックへ切り替えてくれる、という前提も置けない。現在の入口はレジスタを保存したあと、CPUごとの割り込み用スタックでZigを実行する。保存フレームとスタック切替は、後のタスク実行の章で詳しく扱う。

## 最初の成功表示が確かめていること

起動直後のZigは、初期値を調べてから `ecall` を実行する。

{{snippet:native-crt-check}}

`asm volatile` は、機械語命令を埋め込むZigの記法である。ここではメモリへの影響も指定し、コンパイラによるメモリ操作の並べ替えを抑える。CPU間やDMAとの同期は、別に定義する必要がある。復帰後に例外回数が1であることを確かめると、次の行を出せる。

```text
NIHOS_NATIVE_CRT_PASS bss=zero data=valid ecall=returned
```

この表示は、選んだゼロ初期値と非ゼロ初期値が期待どおりで、CPU0の起動用 `ecall` から戻れたことを表す。全変数や全レジスタの保存、非同期割り込み、CPU1、画面などを、この一行だけで証明したことにはならない。検査した変数と条件までソースへ戻って確かめよう。

## 手元でELFを作り、配置を確かめる

実行前に、まず生成物の構造を調べる。以下はリポジトリのルートで行う。最初のコマンドでZigの固定版を確認し、専用の出力先へintegerモードをビルドする。

```sh
sh tools/bootstrap-zig.sh
sh tools/build-native-elf.sh emulator \
  build/book-native-study integer
python3 tools/check-native-image.py \
  build/book-native-study/nihos-native.elf \
  --elf-only \
  build/book-native-study/image-audit.json integer
```

この手順にESP-IDFのインストールは要らない。Zigの初回取得にはネットワークが必要である。Flash用イメージや第2段ローダを作る工程は、ここには含めない。

成功すると `build/book-native-study/` にELFと検査結果が残る。`image-audit.json` の `entry` は内部SRAMの範囲にあり、`sections` には先ほど読んだ領域が並ぶ。`.flash.appdesc` と `.flash.rodata` だけは、既知のFlash側の配置になる。次のコマンドで値を抜き出せる。

```sh
python3 - <<'PY'
import json
from pathlib import Path
path = Path('build/book-native-study/image-audit.json')
report = json.loads(path.read_text())
print('entry:', report['entry'])
for section in report['sections']:
    print(section['name'], section['address'],
          section['bytes'])
PY
```

検査スクリプトは入口、配置、未解決シンボル、既知のROM呼出しなどを調べる。`rtos_linked` がfalseという結果も、この構造検査の条件に基づく。`ecall` が実際に復帰したか、タイマが動いたかは、まだ実行していないのでわからない。失敗したら、コンパイラの診断と `Native image audit failed` に続く理由を分けて読み、[ビルドスクリプト](repo:tools/build-native-elf.sh)と[検査の条件](repo:tools/check-native-image.py)を確認する。

## 条件を一つ変えてみる

ソースを変更する前に、emulatorプロファイルとdeviceプロファイルで何が変わるか予想しよう。同じZig関数へ入るとして、CPUのrevisionに依存する部分はどこだろうか。

1. device側を `build/book-native-study-device` へビルドする。先ほどの `emulator` と出力先を、この二つの値へ置き換える。
2. そのELFも、別の `image-audit.json` へ検査する。Flashへの書込みは行わない。
3. 両者の入口が内部SRAMにあることと、二つのELFの `elf_sha256` を記録する。
4. `start.S` の `NIH_NATIVE_REV3` の分岐を読み、割り込みのしきい値を設定する方法の違いを説明する。

二つのELFのサイズやdigestの一致を、CPUの動作互換性の条件にはしない。プロファイルの違いをどのコードに反映したかと、生成物が構造検査に通ったことを対応づける。device向けのビルド成功も、実機での起動成功とは別の結果である。

## 実行へ進む場合

ESP-IDF v5.4.4とESP-EMUの環境を用意できる読者は、[native bootの手順](repo:docs/native-boot.md)へ進める。

```sh
sh tools/run-native-smoke.sh integer 0
```

このコマンドは既定のnative-emulator出力先を再生成する。別の開発作業と同じ出力先を同時に使わず、必要な既存ログは先に別の場所へ保存しておこう。コマンドは実機へ書き込まず、PSRAMなしのエミュレータで動かす。

ログの最初には `NIHOS_NATIVE_BOOT`、続いて先ほどのCRT検査が現れる。ただし現在のsmokeは、この章の範囲を超えて、両CPUのタスク、タイマ、IPI、待機なども検査する。終了時のmarkerだけを抜き出さず、`smoke-report.json` が生成され、検証スクリプトが全条件を満たしたことを確認する。

本章ではそのログから、起動と初期値、最初の例外復帰について説明できればよい。後半で失敗した場合は、最初の起動失敗と同じものとしてまとめず、最後に通った検査と、その次の失敗を分けて記録する。エミュレータの成功も、物理Tab5の電源、メモリのタイミング、表示が動く根拠にはならない。

## 読み終えたら確かめること

`sp` を用意する前にZigへ入ってはいけない理由、`.bss` をCPU0だけが初期化する理由、ELF検査と実行検査が違う理由を説明してみよう。最初の成功表示までの経路を追えたら、次は「割り込みが途中のどこで入っても、正しく再開できるか」という問いへ進める。
