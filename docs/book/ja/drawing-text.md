# 文字が画面に現れるまで

シリアルへ出していたログを、本体の画面でも読めるようにしたい。文字をビットマップへ変えれば済みそうだが、実際には、文字列を残す場所と、画素を更新する時点と、表示回路へ渡す手順が必要になる。

この章では、起動ログを読める診断コンソールを作る。文字には事前に用意したASCII字形を使う。文字を行と列で扱う状態から、字形、画素、表示回路へと順に下り、更新の途中で起きる不具合を調べよう。

## コンソールを描画の上へ置く

文字を行と列で置く仕組みは、起動ログには扱いやすい。一方、グラフや図形、文字の大きさが違う画面を、すべて文字セルの操作へ押し込むのは難しい。そこで、役割を次のように分けて考える。

```text
起動ログと診断の状態
        ↓
文字セルの格子とカーソル
        ↓
字形のマスクと色を画素へ合成
        ↓
フレームバッファとキャッシュの受渡し
        ↓
DMAと表示回路
```

コンソールは、描画を利用する一つの表示方法になる。将来グラフを描く場合には、文字格子を経由せず画素側へ進める。この分け方なら、診断画面を先に動かしても、その文字セルを全アプリ共通の座標系にする必要はない。

本章の画素化処理はTab5の向きと固定の画面配置に合わせて作る。別の画面サイズや描画APIへ広げるときには、文字の状態と物理的な画素配置のどちらに依存する処理かを見分けるとよい。

## 一画素の置き場所を決める

フレームバッファは、画素の型を持った二次元配列とは限らない。この実装はRGB565のバイト列を使う。赤5ビット、緑6ビット、青5ビットを一つの16ビット値へ詰め、下位バイトから格納する。

{{snippet:console-pixel}}

`stride`は次の物理行までのバイト数である。幅から求めた有効画素の長さと、常に同じとは限らない。行末にパディングがある場合にも、`y * stride`を基準にする。

この小さい関数は、渡された座標の妥当性を自分では調べていない。呼び出し側がframeの長さ、stride、描画範囲を検査してから使う。バッファを受け取る公開境界と、内部の一画素処理で、何を保証するかを分けて読む必要がある。

Tab5の物理バッファは720×1280で、RGB565なら有効画素だけで1,843,200バイトを使う。横向きの文字座標は、その物理座標へ変換する。文字の列数を、そのまま物理バッファの幅として扱ってはいけない。

## 文字を残す場所と、絵を残す場所

[文字格子](git:960bb1056252aaf6193d8d66350a27e63259d26d:src/console/ascii.zig)は、文字セル、カーソル、改行待ち、スクロールの回数を管理する。小さいフォントの構成では、16×16画素のセルを78列・43行に並べる。元の字形は8×8のビットマップである。

画面とは別に、直近のログのバイト列を残す2 KiBのログ領域と、起動の段階・成功失敗を表す状態も持つ。長いログで古いバイトが押し出されても、どの段階で止まったかは残したいからだ。

ここで、ログ領域が更新されるたびに全バイトを再解釈して画面を作り直すと、リングの先頭が動くたびに文字の配置まで変わり得る。そこで、表示中の本文の格子へ直接追記し、固定ヘッダと本文のカーソルも分ける。ログの保存と、いま表示している状態には、それぞれの寿命がある。

## 消してから描くと、消えた瞬間も見える

最初の分かりやすい方法は、背景で画面を塗り、すべての文字を描き直すことだ。しかし表示回路はCPUの描画完了を待たずにバッファを読んでいる。途中で全面を消すと、その背景だけの瞬間が表示されることがある。

[スクロールの実験記録](git:960bb1056252aaf6193d8d66350a27e63259d26d:docs/measurements/2026-10-27-native-console-scroll.md)では、この全面消去を通常更新から外した。変わったセルを描き、スクロールでは既存画素を移して、入ってきた行だけを描く。更新中に来たログは別の格子へため、固定ヘッダを本文の移動に巻き込まない。

変更領域を小さくすれば、キャッシュを表示回路へ渡す量も減らせる。ただしコピーの回数も重要である。参照版のコードは、複数段階の補間によるスクロールから、一回の移動へ整理されている。見た目を滑らかにするつもりで段階を増やしても、各段階で広い範囲をコピーすれば、次のログを表示するまでの待ちが増える。

この実験は同じ一枚のバッファへ書いている。全面消去をやめることと、表示途中の新旧画素が混ざるtearingを防ぐことは別だ。バッファを切り替える方式を選ぶなら、追加の容量と、どの時点で切り替えるかを考える必要がある。

## 描画が正しくても、受け渡しで壊れる

CPUが書いた画素をDMAが読めるよう、キャッシュの書戻しを行う。ここでも、単に「更新後に一度呼ぶ」という説明では足りなかった。

[動作中に更新するコンソールの記録](git:960bb1056252aaf6193d8d66350a27e63259d26d:docs/measurements/2026-10-27-native-console-live.md)には、メインループのキャッシュ操作にDMA割込みが入り、割込み側の記述子用キャッシュ操作が重なる不具合がある。対策は、キャッシュ操作の小区間でそのCPUの割込みをマスクし、区間の間で割込みを受けることだった。最初の全画面描画やマッピングでは1 KiBずつ、後続の表示への反映では16 KiBずつ扱う。

全画面の更新中ずっと割込みを止めると、今度は表示の継続や他の応答を妨げる。どの操作は重ねられず、どこなら割込みを受けてよいかを決める。{{ch:messages-and-waits}}の所有者と受け渡しの問題が、画面の処理にも現れる。

## 読めることと、速く更新できること

実機では初期の文字画面が読めることを確認できた。一方、スクロールの候補では、並行する起動検査の負荷を含め、一段階の更新に最大約241 msを観測した。表示回路の約60 Hzという設定から、文字の更新も60 fpsで進むとは言えない。

CPUで画素を作る時間、キャッシュの受け渡し、表示回路が読む周期、利用者が読みやすいと感じることを、別々に見る。ログの`visible=1`も、描画処理からバッファを渡せたという記録であって、人が見たという記録ではない。ソフトウェアの完了と、光として見えた結果の両方が必要になる。

## 触った結果を、画面へ返す

文字を読めるようになったら、画面を触って変えたくなる。入力を読む処理、操作を決める状態、画素を作る処理を分けると、表示と入力のどちらで止まったかを調べやすい。

[四象限の色表示](git:a25ad6a0405733136be7e83efedee899e8d34a04:src/board/tab5/touch_feedback.zig)は、720×1280の座標を中央で四つに分け、接触した場所に応じて背景色を変える。新しいsampleが接触数0を報告したら、離指として暗い背景へ戻す。数字やカードの資格情報を扱う前に、接触から可視の応答までを小さく確かめる実験である。

表示を横向きにした場合、物理座標と画面上の座標の対応を決める必要がある。描画時の回転と入力時の変換が別々の約束なら、見えているボタンの隣を押すことになる。四隅を順に押して、どこへ対応するかを予想すると、座標の向きや幅・高さの取り違えを発見しやすい。

[実機記録](git:a25ad6a0405733136be7e83efedee899e8d34a04:docs/measurements/2026-10-27-native-touch-feedback.md)では、四象限すべての接触と四回の明示的な離指を観測し、利用者が色の変化も確認した。2,190 sample中、接触ありが15、観測した最大接触数は1だった。複数指を扱うホストテストがあっても、この実機試験で複数指を確認したとは言えない。

## 新しい報告がないことと、指を離したこと

入力のpollで何も変わらなかったとき、それは接触数0の報告だろうか。それとも新しい報告がないだけだろうか。この違いを捨てると、押し続けた指を、毎回押し直した指として扱いかねない。

色表示の実験には、特定のSitronix経路で座標なしの応答が二回続いた場合に離指を推定する処理もある。しかしGoodixの古いsampleには適用しない。先の実機で観測した四回は、推定によるものではなく、接触数0の明示的な報告だった。

操作を確定するUIへ進むなら、どのedgeを採用するかを改めて決める。押下、押し続け、移動、離指を一つの「入力あり」へまとめない。PIN入力の経路では、長押し、drag、複数指、古い接触を拒否するテストを別に持っている。{{ch:card-terminal}}では、その入力を実際の要求へ結び付ける条件を読む。

## PC上で描き直しと比較する

リポジトリのルートから、参照版の作業用コピーを作る。

```sh
git worktree add --detach ../nihos-book-drawing \
  960bb1056252aaf6193d8d66350a27e63259d26d
cd ../nihos-book-drawing
sh tools/bootstrap-zig.sh
.tools/zig-0.17.0/zig build test
.tools/zig-0.17.0/zig build test -Doptimize=ReleaseSmall
```

必須実験はPC上のバッファへ描くところまでで、実機へは書き込まない。[画素化処理のテスト](git:960bb1056252aaf6193d8d66350a27e63259d26d:src/graphics/ascii_console.zig)は、部分更新とスクロールを繰り返した結果を、同じ格子から一度で描き直した結果と比較する。行末のパディング、バッファの前後のガード、固定ヘッダも保存されることを調べる。

`src/console/ascii.zig`で、右端の改行前後のカーソルを追おう。画素化処理のテストでstrideへ余白を加えると、どの範囲外書き込みを見つけられるだろうか。

タッチの追加実験は、カード端末と同じ参照版を別の作業用コピーで使う。名前にcardとあるが、ここで行うのはホストテストだけである。

```sh
git worktree add --detach ../nihos-book-touch \
  a25ad6a0405733136be7e83efedee899e8d34a04
cd ../nihos-book-touch
sh tools/bootstrap-zig.sh
.tools/zig-0.17.0/zig test --dep ccid \
  -Mroot=src/root.zig -Mccid=src/usb/ccid.zig \
  --test-filter 'four quadrants' \
  --test-filter 'only this Sitronix experiment'
```

新しい接触、未更新、離指を順に渡し、二つのcontrollerの違いを予想しよう。四象限の境界も試し、入力・状態・画素・表示のどこまで進んだかを記録する。次の{{ch:japanese-fonts}}では、日本語の字形を作る側の所有者と作業領域を考える。
