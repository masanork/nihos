# 最初の実験を再現する

ソースを読めても、変更のたびに動作を確かめられなければ、理解はすぐ曖昧になる。この章ではnihosのhostテストを動かし、その結果がどこまでの根拠になるかを整理する。Tab5やシリアル接続は使わない。

## バージョンを揃える

リポジトリのルートで、使用するソースを記録する。

```sh
git rev-parse HEAD
git status --short
cat .zigversion
```

この試読版のコード抜粋に対応するカーネル側のコミットは次の通りである。

{{source-revision}}

作業中の変更があれば、その差分も結果の条件になる。書籍の実習版を将来タグで公開するときは、その版をチェックアウトして進められるようにする。

nihosのスクリプトで、固定されたZigを用意する。現在は0.17.0を使用している。スクリプトの内容と配布元を確認してから実行する。

```sh
sh tools/bootstrap-zig.sh
.tools/zig-0.17.0/zig version
.tools/zig-0.17.0/zig build test
.tools/zig-0.17.0/zig build test -Doptimize=ReleaseSafe
```

bootstrapスクリプトは初回にtoolchainを取得する。テストが成功しても、何も表示せず終了する場合がある。終了コードが0であることを確かめよう。テスト一覧を知りたいときは、`src/` の `test` 宣言と[ビルド設定](repo:build.zig)を読む。

DebugとReleaseSafeは、検査のある構成で結果を比較するために両方実行する。速度を論じる場合には、同じ最適化条件で比較し、別途時間を測る。テストの成功だけから性能の良さは判断できない。

## 一つの検査を詳しく読む

{{ch:bounded-memory}}の準備として、arenaだけのテストを動かす。

```sh
.tools/zig-0.17.0/zig test src/kernel/arena.zig
```

このテストは、少量のメモリから領域を取り出し、アドレスの整列、容量を超える要求、無効なalignment、reset後の状態を検査する。実際のESP32-P4からPSRAMを取得しているわけではない。割当の計算という一つの責任を、hostで取り出して確かめている。

## 結果の範囲を書く

| 確認方法 | わかることの例 | 別に確かめることの例 |
| --- | --- | --- |
| hostテスト | データ構造と方針が検査した条件を満たす | RV32のコード生成、実機のキャッシュや割り込み |
| RV32向けコンパイル | 対象の型や命令がコンパイルできる | 実行と周辺機器の挙動 |
| ESP-EMUで実行 | モデル化されたP4でCPU経路が実行される | 実機のタイミング、パネル、音、電源 |
| Tab5で実行 | その機体・条件で観察した動作 | 未試験のrevision、負荷、電源断など |

さらに、ESP-IDFがスケジューリングする実機試験と、nihosが引き受けたnative区間での試験を区別する。どちらも有用だが、同じ責任を検査しているわけではない。

## 実験ノートを残す

ソースのコミット、変更、toolchain、最適化条件、実行環境、コマンド、終了状態を記録しよう。性能を測るなら、入力、回数、時間の単位、ばらつきも加える。途中で失敗した場合は、最後のエラーだけでなく、どのコマンドで失敗したかを残す。

nihosの[測定記録](repo:docs/measurements/2026-10-25-language-probe-host.md)は、結果と、その結果からは判断できない範囲を一緒に記述している。既存の数値はその条件での観測であり、読者の環境で一致することを要求しない。

## 確認問題

1. hostでarenaのテストが通ったとき、DMAがそのメモリを読めると結論してよいだろうか。
2. 同じソースでもDebugとReleaseSafeの時間を直接比較して、変更の効果を判断できるだろうか。
3. 自分の実験を別の人に再現してもらうため、どの情報がまだ足りないか、手元の記録を点検しよう。
