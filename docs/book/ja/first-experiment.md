# 最初の実験を再現する

ソースを読めても、変更のたびに動作を確かめられなければ、理解はすぐ曖昧になる。この章ではnihosのホストテストを動かし、その結果がどこまでの根拠になるかを整理する。Tab5やシリアル接続は使わない。

## 機械を小さくして考える

実物の端末では、CPU、電源、メモリ、表示、入力が一緒に動く。ホストとは、この実験を動かす手元のPCのことである。端末の動きを別のソフトウェアで模擬する実行をエミュレータと呼ぶ。画面が止まったという観察だけでは、どこを調べるか決めにくい。そこで最初は、割当の計算やタスクの選択だけを取り出し、普通のPCで実行する。観察する範囲を小さくすると、予想と結果の違いを追いやすくなる。

この順序は、実機で調べる面白さにもつながる。小さなモデルでは説明できたのに、基板では違う値が出たなら、モデルに含めなかった条件へ目を向けられる。テスト結果の記録は、そのときに戻れる足場になる。この章では、他の読者や翌日の自分が、同じ足場から始められるようにする。

## バージョンを揃える

リポジトリのルートで、使用するソースを記録する。

```sh
git rev-parse HEAD
git status --short
cat .zigversion
```

実験結果を比べるには、ソースの版を揃えることから始める。章ごとの参照版と、必要なツールの対応は[実習環境](practice-notes.md)にまとめた。

作業中の変更があれば、その差分も結果の条件になる。元のソースを残した作業用コピーで実験すると、変更前後の比較とやり直しがしやすい。

次に、リポジトリのスクリプトでZig 0.17.0を用意する。

```sh
sh tools/bootstrap-zig.sh
.tools/zig-0.17.0/zig version
.tools/zig-0.17.0/zig build test
.tools/zig-0.17.0/zig build test -Doptimize=ReleaseSafe
```

bootstrapスクリプトは初回にツールチェーンを取得する。テストが成功しても、何も表示せず終了する場合がある。終了コードが0であることを確かめよう。テスト一覧を知りたいときは、`src/` の `test` 宣言と[ビルド設定](repo:build.zig)を読む。

DebugとReleaseSafeは、検査のある構成で結果を比較するために両方実行する。速度を論じる場合には、同じ最適化条件で比較し、別途時間を測る。テストの成功だけから性能の良さは判断できない。

## 一つの検査を詳しく読む

{{ch:bounded-memory}}の準備として、アリーナだけのテストを動かす。

```sh
.tools/zig-0.17.0/zig test src/kernel/arena.zig
```

このテストは、少量のメモリから領域を取り出し、アドレスの整列、容量を超える要求、無効な整列指定、リセット後の状態を検査する。実際のESP32-P4からPSRAMを取得しているわけではない。割当の計算という一つの責任を、PCで取り出して確かめている。

## 結果の範囲を書く

| 確認方法 | わかることの例 | 別に確かめることの例 |
| --- | --- | --- |
| ホストテスト | データ構造と方針が検査した条件を満たす | RV32のコード生成、実機のキャッシュや割込み |
| RV32向けコンパイル | 対象の型や命令がコンパイルできる | 実行と周辺機器の挙動 |
| ESP-EMUで実行 | モデル化されたP4でCPU経路が実行される | 実機のタイミング、パネル、音、電源 |
| Tab5で実行 | その機体・条件で観察した動作 | 未試験のリビジョン、負荷、電源断など |

さらに、ESP-IDFがスケジューリングする実機試験と、nihosが引き受けたネイティブ区間での試験を区別する。どちらも有用だが、同じ責任を検査しているわけではない。

## 同じ画面を、四つの段階で調べる

確認方法の違いは、同じ対象を段階的に調べると見えやすい。nihosのCanvasは、呼出し側から借りたRGB565の領域へ矩形、画像、スクロールなどを描く。領域の確保、表示回路への引渡し、画面への表示は担当しない。この責任の小ささを利用して、画素の計算から実機の送出までを別々に調べた。

最初のホストテストは、スクロールと8ビット画像の拡大を、Canvasとは別に書いた一画素ずつの参照計算と比較する。次にESP-EMUで同じ320×200画面をRV32命令として実行し、PSRAMから128,000バイトを読み出した。[二つの仕事の記録](git:482ec1ef9f22bda401565727d92bd9d2da86bcc3:docs/measurements/2026-10-29-canvas-workloads.md)では、両画面が参照と一致し、故意に一bit変えた画面は拒否された。これでパネルの色や速度は分からないが、ホストだけに偶然通るコードとの差を一段減らせる。

入力まで含めた[決定的な再生](git:7e01212b27758b4a644826a7548638d750ce0aec:docs/measurements/2026-10-29-emulator-trace.md)では、同じ八つのsampleから作った九枚のframeと、押下・取消しの状態を、独立したエミュレータ起動間で比較した。エミュレータ用のmailboxを修正した候補も、修正前に保存した参照へ一致した。画面のhashだけでなく、入力と状態も同時に固定したので、違う状態が偶然同じ絵になった場合を見落としにくい。

実機では、静的な診断patternをPSRAMへ描き、表示を開始する限定したfixtureを使った。[実機記録](git:0327757e7f6d343bbe4ace9d9d89ee17b34eb04e:docs/measurements/2026-10-29-canvas-scanout-physical.md)は、候補のbyteを前後に確認し、一回のwarm resetで表示割込みが進んだことを示す。元の16 MiB Flashは復元して全体を照合した。しかし光学的な色、tearing、描画時間、通常アプリケーション、cold bootは調べていない。

同じCanvasでも、各段階の主語は異なる。ホストは画素計算、エミュレータはRV32命令とモデル化されたPSRAM、実機fixtureはその候補と表示経路を調べる。一つの「Canvasが動いた」へまとめず、次に残った境界を書けば、後続の失敗を前の成功と矛盾させずに説明できる。

## 実験ノートを残す

ソースのコミット、変更、ツールチェーン、最適化条件、実行環境、コマンド、終了状態を記録しよう。性能を測るなら、入力、回数、時間の単位、ばらつきも加える。途中で失敗した場合は、最後のエラーだけでなく、どのコマンドで失敗したかを残す。

nihosの[測定記録](repo:docs/measurements/2026-10-25-language-probe-host.md)は、結果と、その結果からは判断できない範囲を一緒に記述している。既存の数値はその条件での観測であり、読者の環境で一致することを要求しない。

## 確認問題

1. PCでアリーナのテストが通ったとき、DMAがそのメモリを読めると結論してよいだろうか。
2. 同じソースでもDebugとReleaseSafeの時間を直接比較して、変更の効果を判断できるだろうか。
3. 自分の実験を別の人に再現してもらうため、どの情報がまだ足りないか、手元の記録を点検しよう。
4. Canvasの実機fixtureで表示割込みが進んだとき、利用者が正しい色を見たと結論するには、どの観測が足りないだろうか。
