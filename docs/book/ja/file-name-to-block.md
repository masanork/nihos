# 名前から保存ブロックまで

`read`に渡したバイトが、SDカードのどこから来るのか。名前を開く操作と、開いた後の読取りを分けると道筋が見えてくる。この章の最初の例は一般的な比較モデルであり、そのすべてがnihosに実装されているという意味ではない。

## 名前と開いたもの

例えば`/books/a.txt`を開くと、名前空間をたどってディレクトリの各要素を調べ、対象のファイルを見つける。mountはパスの一部を別のファイルシステムへ結び付ける。openが成功すると、以降の操作は名前を毎回たどる代わりに、開いた対象を指す参照を使える。プロセスに見える小さな番号をFD、その先の状態をopen objectと呼ぶ設計もある。

open objectには現在位置やアクセス方法などが置かれる。`read`は現在位置から要求された長さまで読み、実際に返った長さだけ位置を進める。終端や短い読取り、エラーを区別する必要がある。二つの参照が同じopen objectを共有するか、別々の位置を持つかはAPIの設計による。

名前を消す操作と、すでに開かれた参照を閉じる操作も同一ではない。名前を消した後も開いた参照が使える方式では、最後の参照が閉じられるまで対象を保持する必要がある。実際に何を保証するかは、そのファイルシステムの契約で確かめる。

## オフセットから媒体へ

ファイル内の位置は、ファイルシステムが管理する配置情報を通して媒体のブロックに対応づけられる。例えばFATでは、ディレクトリの情報から開始クラスタを得て、必要に応じてFATの連鎖をたどる。別の設計ではinodeとextentを使って連続領域を表せる。空き領域を探す情報やファイルの長さもmetadataである。名前、開いた参照、ファイル内位置、媒体の配置はそれぞれ別の情報だ。

ファイルを書き伸ばすなら、データの置き場所だけでなく、空き管理、配置情報、長さの更新も必要になる。途中で電源が失われたときに何が残るかは、更新順序と保存の保証に依存する。{{ch:durable-storage}}では、その成功条件をさらに追う。

## nihosの範囲を確かめる

{{ch:io-lifetime}}で扱ったFatFs/VFSの実験は、読取り要求とバッファの寿命を結び付ける材料になる。[固定版のprobe資料](git:f02a1674b87fe195c71b549f6cc325661120529d:probes/fatfs-disk/README.md)と同章の説明を見て、ホストで検証した経路と実機で確かめた経路を混同しないようにしよう。一般モデルのunlinkや書込みの説明から、実験版にそれらが備わるとは結論できない。

## 操作を追う

小さなファイルを開き、先頭から3バイト、次に2バイト読む。各操作の前後で名前、開いた参照、位置、配置情報のどれが変わるかを表にしよう。2回目の読取りが1バイトしか返さなかったら位置をいくつ進めるか。次に開いたまま名前を消せる方式を仮定し、名前の消失と実データの回収が別の時点になる理由を説明しよう。
