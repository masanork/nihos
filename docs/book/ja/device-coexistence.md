# 複数のデバイスを同時に使う

マイクもスピーカーも、それぞれ単独で動いた。では同時に要求したら何が起きるだろう。機能ごとの成功を足すだけでは、共有するメモリや周辺回路を二重に使わないことは分からない。

ここで扱う通常のデバイス処理はM-modeに残る。{{ch:process-isolation}}の保護タスクへ周辺回路や共有バッファの権限を与えた実装ではない。CPUのアクセスを拒否することと、二つのサービスが同じI2SやDMA領域を同時に使わないことは、別に守る条件である。

## 所有権を先に決める

音声の送出とマイク入力では、音声データを送受信するI2Sという接続を使う。この実装は両方のためのメモリ上の作業領域を共有する。両方が同じ場所を無条件に書き換えれば、相手のDMAが読んでいるデータを壊しかねない。要求を受ける側は使用中かどうかを調べ、競合する要求を所有権を変更する前に拒否する。終了時には転送を止め、音声信号を扱うcodec（符号化・変換回路）や領域の後始末をしてから所有権を返す。

マイク、音声、再びマイクという順で要求すれば、最初の利用で作った領域を安全に再利用できるかが見える。終了したはずの装置が領域を保持し続ける不具合も、この順番で表に出る。

## 一つのイメージで観察する

[同一イメージの共存記録](git:542e6ac98d477a1c33c1b927e61136ae5ad8c68b:docs/measurements/2026-10-28-connected-devices.md)では、約88秒の実機観察中に、競合する音声・マイク要求が所有権の変更前に拒否された。マイク→音声→マイクの有限動作と後始末、UARTという直列通信回路の内部ループバック（送信を内部で受信する試験）、IMUという動きのセンサーの取得、画面と両CPUのカウンタも確認した。I2S作業領域は1,536バイトで、最後には所有者とpinがない状態に戻った。ここでのpinは端子ではなく、使用中の領域を回収できないよう保持する記録である。

通信も同時に観察された。Wi-Fi接続中、最初の時刻取得は失敗し、待機後の再試行が成功した。すでに有効だったRTC（時刻を刻み保持する時計回路）はその間も進み、有効な応答の後に時刻が適用された。失敗した最初の試行を隠さず、試行と応答の順序を記録している。

これは、その条件の共存と回復の観察である。長時間の高負荷通信、外部RS-485機器との通信、音質、冷電源断後の時計保持まで確かめたものではない。各デバイス単独の結果と、同じイメージ・同じ時間窓の共存結果を分けて扱おう。

## 数が揃っても、音になったとは限らない

後の有限音声試験では、DMAの完了数、I2Sのbit clock、FIFOへ渡したsample数、停止、codecの終了、領域の返却がすべて期待どおりに見えた。それでも、繰り返し試験で利用者には音が聞こえなかった。内部counterが揃うことと、speakerから音が出ることの間には、まだ境界がある。

最初に見つかったのは、I2S送信側でPhilips形式の一bit遅延とleft-aligned形式を同時に有効にしていたことだった。片方へ直すと、今度は記述子の自動停止によって最後のsampleが一つ足りないことが分かった。自動停止を外し、一つの所有者が有限の排出後にI2Sを止める候補へ進めた。

さらに、MCLK、BCLK、LRCK、dataのpadで信号の変化を読み、BCLKの立上りごとにdataを採取した。保持できた34個の16bit slotから33 wordを復号すると、独立に作ったPCM計画の同じ位置とすべて一致した。ここまでで、CPUが作ったsampleから出力padまでの一部は絞れた。しかしclock周波数、codecが受け取ったanalog値、mixer、amplifier enableの電圧、speaker出力は測っていない。最終候補でも可聴性は確定しなかった。

[この実機記録](git:b95033f66c2bb3260f35bf82e4123600f429885d:docs/measurements/2026-10-29-quake-audio-path-physical.json)は、各候補で排他的なserialとboard writerを保持し、元のFlashを毎回復元して照合した。同じ作業ブランチはQuake移植の準備だったが、Quakeのengineは実行していない。有限音声の基盤を試したことを、ゲーム音声が動いた証拠にしない。

| 観測点 | 分かること | まだ分からないこと |
| --- | --- | --- |
| DMA/FIFO counter | controllerの予定数 | wireのbit配置、analog出力 |
| I2S pad sample | 区間のdigital word | codec、周波数、全区間 |
| codec/mixer register | 読み返した設定値 | analog signal |
| amplifier制御 | 書いた制御値 | 出力電圧、speaker |
| 利用者の聴取 | その条件で聞こえたか | 波形品質、別個体、長時間 |

失敗の場所を絞るには、同じ「音声成功」という印を増やすのではなく、観測点を信号の進む順に置く。途中まで正しいことは、次の境界を調べる根拠になる。

## 競合を作って考える

音声の転送中にマイクを要求し、音声を終了してから再要求する操作列を書く。各時点で領域の所有者、DMAの状態、要求の結果を表にしよう。最初の要求を拒否する前に所有者を書き換えたら、後始末は誰の領域を解放するだろうか。次にネットワーク時刻の失敗を入れ、RTCの現在値と再試行中であることを別々の状態として描く。

CPUのPCM生成からspeakerまでを並べ、確認できた最後の境界へ印を付けよう。I2S padのwordが一致した後に一つだけ測るなら何を選ぶか。その結果からも言えないことを書こう。
