# 複数のデバイスを同時に使う

マイクもスピーカーも、それぞれ単独で動いた。では同時に要求したら何が起きるだろう。機能ごとの成功を足すだけでは、共有するメモリや周辺回路を二重に使わないことは分からない。

## 所有権を先に決める

音声の送出とマイク入力では、音声データを送受信するI2Sという接続を使う。この実装は両方のためのメモリ上の作業領域を共有する。両方が同じ場所を無条件に書き換えれば、相手のDMAが読んでいるデータを壊しかねない。要求を受ける側は使用中かどうかを調べ、競合する要求を所有権を変更する前に拒否する。終了時には転送を止め、音声信号を扱うcodec（符号化・変換回路）や領域の後始末をしてから所有権を返す。

マイク、音声、再びマイクという順で要求すれば、最初の利用で作った領域を安全に再利用できるかが見える。終了したはずの装置が領域を保持し続ける不具合も、この順番で表に出る。

## 一つのイメージで観察する

[同一イメージの共存記録](git:542e6ac98d477a1c33c1b927e61136ae5ad8c68b:docs/measurements/2026-10-28-connected-devices.md)では、約88秒の実機観察中に、競合する音声・マイク要求が所有権の変更前に拒否された。マイク→音声→マイクの有限動作と後始末、UARTという直列通信回路の内部ループバック（送信を内部で受信する試験）、IMUという動きのセンサーの取得、画面と両CPUのカウンタも確認した。I2S作業領域は1,536バイトで、最後には所有者とpinがない状態に戻った。ここでのpinは端子ではなく、使用中の領域を回収できないよう保持する記録である。

通信も同時に観察された。Wi-Fi接続中、最初の時刻取得は失敗し、待機後の再試行が成功した。すでに有効だったRTC（時刻を刻み保持する時計回路）はその間も進み、有効な応答の後に時刻が適用された。失敗した最初の試行を隠さず、試行と応答の順序を記録している。

これは、その条件の共存と回復の観察である。長時間の高負荷通信、外部RS-485機器との通信、音質、冷電源断後の時計保持まで確かめたものではない。各デバイス単独の結果と、同じイメージ・同じ時間窓の共存結果を分けて扱おう。

## 競合を作って考える

音声の転送中にマイクを要求し、音声を終了してから再要求する操作列を書く。各時点で領域の所有者、DMAの状態、要求の結果を表にしよう。最初の要求を拒否する前に所有者を書き換えたら、後始末は誰の領域を解放するだろうか。次にネットワーク時刻の失敗を入れ、RTCの現在値と再試行中であることを別々の状態として描く。
