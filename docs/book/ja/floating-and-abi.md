# 浮動小数点の状態と言語の境界

整数のタスク切り替えが動いたあと、計算するタスクを追加したら値が変わった。整数レジスタとスタックを保存しているのに、何が足りないのだろうか。

この章では、RV32Fの状態を誰が持つか、ZigとCの呼び出しで何を揃えるかを調べる。PC上で期待値を検査し、生成されたELFの命令とABIを確かめよう。

## 実行環境が守っている約束

アプリケーションで関数を呼ぶたびに、隣の仕事が計算用レジスタを使っていないかを確認することは少ない。OSや実行環境が、切り替えの前後で同じ状態が続くようにしているためだ。カーネル側へ降りると、どの状態を保存対象に含めるかを自分で決める必要がある。

別のCPUでは、浮動小数点のほかにベクトルなどの拡張状態も検討対象になる。必要な機能を使える便利さと、保存領域や切り替えの費用は結びついている。RV32Fという具体例から、命令セットの機能がOSの実行環境へ要求するものを読んでいこう。

言語間の呼び出しにも似た関係がある。別々に作ったコードを組み合わせるには、型の見た目に加えて、値をどこへ置き、どの状態を保つかという約束がいる。後半のC側の接続用関数は、この約束を小さく切り出して確かめる例になる。

## 計算結果以外にも状態がある

RV32Fを使うタスクには、32本の浮動小数点レジスタがある。さらに`fcsr`には丸めモードや例外フラグがある。別のタスクが丸めモードを変更したら、同じ命令でも結果が変わり得る。

nihosの[浮動小数点コンテキスト](repo:src/arch/riscv32/context.zig)は、整数フレームとは別に持つ。

{{snippet:floating-context}}

32本の32ビット値と`fcsr`で132バイトになる。この値は保存データの大きさであり、タスク全体のメモリ使用量ではない。整数だけのタスクには保存領域を割り当てず、毎回この状態をコピーする費用を避ける。

本章では、利用を明示したタスクについてトラップのたびに状態を保存・復元する`eager`な方式である。最初のFPU使用を例外で検出して遅延処理する`lazy`な方式とは異なる。選択した方式、保存回数、実際に浮動小数点命令が実行されたことを別々に調べる。

## カーネルへ命令が混ざっていないか

F拡張を有効にしてコンパイルすると、書いた式だけでなく、コンパイラの判断によって浮動小数点命令が使われる可能性がある。そこで`compiled`モードでは、タスクのコードを`.fp_app`へ分け、ELFの実行命令を検査する。

許可するのは、このタスク領域と、明示した保存・復元補助関数である。他のカーネル領域に浮動小数点命令や対応CSRへのアクセスが見つかれば、構造検査を失敗させる。実行時にも、ディスパッチャがFPUを使える状態になっていないことを調べる。

この監査はソースを検索するだけではない。RV32の16ビット圧縮命令も含め、生成物の命令を分類する。逆に、許可した命令がELFに存在するだけでは実行の根拠にならない。タイマーが記録した命令位置がタスクのコード内にあることと、計算の確認点も必要になる。

## Cと呼び合えるとは、何を確かめたことか

本章で扱う`compiled`モードはILP32Fを使う。スカラ値のf32引数と戻り値、CからZigへのコールバック、ポインタを介した構造体を検査する。型のサイズ・整列・フィールドのオフセットと、引数や戻り値を運ぶ場所は、ABIの別の側面である。

最初の直接的な構造体値渡しでは、期待した0.5に対し0.25が観測された。構造体のサイズ8バイト、4バイト整列、二番目のフィールドのオフセット4は一致していた。[当時の記録](repo:docs/measurements/2026-10-26-compiled-fp-c-abi.md)は、この試行を合格に含めていない。

そこで、構造体の値渡しはCの翻訳単位内へ閉じ、Zigとの境界にはポインタを使う小さな接続用関数を置いた。

{{snippet:c-pair-adapter}}

この接続用関数を通すと、検査した呼び出しで期待値が得られた。直接の構造体値渡しで値が変わった原因は、さらに調査が必要である。[呼び出し境界の資料](repo:probes/native_fp/README.md)には、スカラ値、コールバック、ポインタ経由の結果を分けて記載している。

また、ポインタを渡す場合にも条件がある。指す領域の長さ、整列、書き込み権限、呼び出し中の寿命を呼び出し側が守る。ここでは、同じM-modeのネイティブ空間にある小さな固定型を対象にしている。このポインタ付きC ABIと、{{ch:process-isolation}}のスカラECALLは別の入口である。現在の保護タスクは浮動小数点コンテキストを持たない整数用クラスに限り、CライブラリやFPUワーカーをU-modeへ移した結果ではない。

## 期待値を同じ計算で作らない

試験対象と同じ浮動小数点式でもう一度計算して期待値を作ると、同じ誤りを共有する可能性がある。nihosの[期待値データ](repo:src/kernel/fp_vectors.zig)は、選んだ入力に対するIEEE形式のビット列を整数側から用意する。

さらに、タスクごとにRNEとRTZという異なる丸めモードを使い、境界にある加算の結果とNXフラグを確認する。`sleep`、`yield`、イベント待ちの前後でも状態が残ることを調べる。単一の算術式が一度成功した場合よりも、保存すべき状態を具体的に検査できる。

実習では単精度の選んだ入力を使う。倍精度、可変長引数、別の構造体へ広げるときには、それぞれに期待値と呼び出し規約の検査を用意しよう。

## PC上で生成物を調べる

リポジトリのルートで実行する。出力先は他の作業と分ける。

```sh
.tools/zig-0.17.0/zig test src/kernel/fp_vectors.zig
sh tools/build-native-elf.sh emulator \
  build/book-fp-study compiled
python3 tools/check-native-image.py \
  build/book-fp-study/nihos-native.elf --elf-only \
  build/book-fp-study/image-audit.json compiled
```

対象ABIのリンクと、命令・配置を確認できる。必要なツールは{{ch:first-experiment}}で用意したものを使う。

次に、別の出力先へ`integer`モードも作り、二つのJSONのABI、FP命令の分類、各領域の大きさを比べよう。ここでは性能を測っていない。

追加実験は`sh tools/run-native-smoke.sh compiled 0`である。独立したネイティブイメージをESP-EMUで実行し、記録した命令位置、FP保存・復元、終了後の所有解除を対応づけよう。

## 読み終えたら確かめること

FPUの丸めモードを保存する理由、命令が存在することと実行されたことの違い、構造体の配置だけでは呼び出し規約を確かめられない理由を説明しよう。
