# タスクを管理する表と実行待ち

三つの仕事が実行できるとき、OSは次にどれを動かすだろう。{{ch:task-lifetime}}で見たレジスタの保存は実行を再開するための仕組みであり、選択の方針とは役割が違う。

## 表に何を置くか

例えば、A、B、Cという三つの仕事を管理するとしよう。表の一行には、一つの仕事が実行できるか、何を待っているかを書いておく。行の位置をスロットと呼ぶ。別に「今どの行を実行しているか」と「同じ優先度では前回どこを選んだか」を覚える。

| スロット | 仕事 | 状態 | 優先度 |
| --- | --- | --- | --- |
| 0 | A | 実行可能 | 1 |
| 1 | B | 実行可能 | 1 |
| 2 | C | 待機中 | 1 |

実行可能なAを選べば、Aの状態は実行中になる。Cの待ちが終われば、Cを実行可能へ変える。実行するために保存したレジスタなどと、この表の管理情報は別の役割を持つ。

[nihosのスケジューラ](git:542e6ac98d477a1c33c1b927e61136ae5ad8c68b:src/kernel/scheduler.zig)は、容量を決めた配列に状態、優先度、世代、実行時間、待ちの情報を置く。レジスタやスタックは別の実行イメージが担う。スロット番号だけを渡すと、削除後に同じ場所を使い直した際、古い参照が新しいタスクを指してしまう。そこで番号と世代を組にしたハンドルを検査する。

実行可能な行は特別な連結リストへ移されず、表の中で`ready`として見つけられる。`current_slot`は現在の行を示し、優先度ごとの`last_selected`は前回選んだ場所を覚える。ブロックや時刻待ち、イベント待ちの行は実行可能になるまで選ばれない。

## 一回の選択を追う

A、B、Cがスロット0、1、2にあり、優先度は同じ、全員が`ready`だとする。選択位置（cursor）は、最初は配列の末尾である。

| 操作 | 状態の変化 | cursor |
| --- | --- | --- |
| 選択 | 末尾の次から探し、Aが`running` | 0 |
| 次の選択 | Aを`ready`へ戻し、Bを選ぶ | 1 |
| Bがブロックして選択 | Bは候補から外れ、Cを選ぶ | 2 |
| Bを起こして選択 | Bは`ready`に戻る。Cの次から探しAを選ぶ | 0 |

選択時はまず表全体から、実行可能な中で数値の小さい優先度を探す。次にその優先度のcursorの次から一周し、最初の候補を選ぶ。誰も実行可能でなければ結果はない。優先度の高い仕事がずっと実行可能なら、低い仕事が必ず進む方針ではない。同じ優先度内の公平性で起きた実際の不具合は{{ch:scheduler-fairness}}で追う。

## 表を走査する費用

固定配列の走査は管理用の動的確保が要らず、上限も容量に比例して見積もれる。一方、空き行も調べるため容量が大きくなると選択の費用が増える。優先度別FIFOと空でない優先度を示すbitmapなら候補を早く見つけられるが、状態変更のたびに集合の整合性を保つ必要がある。期限順のheapは最も近い期限を探す目的に合うが、固定優先度の公平な巡回そのものではない。

## 手で追ってから試す

上の表でBを起こす前に、優先度の高いHを追加したら次は誰が選ばれるか。Hがブロックした後は誰が選ばれるか。状態とcursorを書いて予想し、ソース中の`higher-priority ready task preempts on the next decision`と公平性のテストを読もう。リポジトリのルートで`.tools/zig-0.17.0/zig build test`を実行すれば回帰テストを確認できる。実機の応答時間を測る試験ではない。
