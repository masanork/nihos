# 割り込まれたプログラムを再開する

二つのプログラムが、どちらも自分から制御を渡さず計算を続けている。それでも両方の進捗を増やすには、OSは何をすればよいだろうか。

{{ch:native-entry}}では、起動用のスタックを用意し、`ecall`から戻るところまでを追った。この章では、その復帰先を別のタスクへ変える。実行途中の状態を保存する仕組みと、次に誰を動かすかという方針を分け、最後にタスクの終了と資源の回収を考える。

実習では、次に動かすタスクを選ぶ方針をPC上で検査する。追加実験ではESP-EMUを使い、割込みと保存・復帰の経路を読み合わせる。

## 誰の待ち時間を短くするか

序章で見た時分割の環境には、複数の利用者が一台を使えるようにする要求があった。手元の端末でも、入力への応答、検索、音の供給などが同じCPUの時間を求める。利用者が一人でも、時間をどう配るかという問題は残る。

何をよい配り方とするかは、仕事によって違う。[Operating Systems: Three Easy Piecesのスケジューラの章](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-sched.pdf)は、仕事の到着や実行時間の仮定と、比較する指標を分けて考える。nihosでも、全仕事の完了時間、入力への最初の応答、期限からの遅れを一つの数値へまとめずに見たい。

| 端末で行う仕事の例 | 利用者から見たい性質 |
| --- | --- |
| キー入力を画面へ反映する | 次の入力をためらわずに済む応答 |
| 辞書を検索する | 最初の結果が出るまでの時間と中断への応答 |
| 音のデータを供給する | 必要な時点までに次のデータが揃うこと |

こうした利用場面を思い浮かべると、選択方針を評価する尺度も具体的になる。優先度を上げた仕事が長く走り続ければ、他の仕事の応答は変わる。切り替え間隔を短くすれば、切り替えそのものの費用にも目を向ける必要がある。

## 同じ状態を保存しても、保護の範囲は違う

プロセスとスレッドは、どちらも実行状態を持つ。区別するときには、アドレス空間や資源をどの単位で共有するかを見る。[xv6](https://pdos.csail.mit.edu/6.1810/2025/xv6/book-riscv-rev5.pdf)のようにプロセスごとのアドレス空間を扱う構成と、本書のネイティブタスクのように同じマシンモードの空間で動く構成では、誤った書き込みの及ぶ範囲が異なる。

本章の最初の目標は、途中の計算を正しく再開し、寿命を終えた実行状態を回収することである。保存フレームを読み解いた後には、その状態の置き場所を誰から保護したいかという、次の設計の問いも残る。

## 関数呼び出しでは守れないもの

通常の関数呼び出しには、呼び出し側と呼び出される側がどのレジスタを保存するかという約束がある。しかしタイマーは、プログラムがその約束に合わせて準備した場所だけで割り込むわけではない。式の途中で使っている一時値も、復帰後には元の値でなければならない。

nihosの[整数コンテキスト](repo:src/arch/riscv32/context.zig)は、復帰位置の`mepc`と、ゼロレジスタ以外の31個の整数レジスタを128バイトに保存する。レジスタの並びは、Zigの型とアセンブリで共有するABIである。型のサイズが合うだけでなく、各フィールドのオフセットも一致する必要がある。

保存した状態にはタスクごとのスタック位置も含まれる。割り込まれたタスクAのフレームを残し、タスクBのフレームを選べば、復帰処理はBのスタックと実行位置を復元できる。

{{figure:context-switch}}

図は上から下へ時間が進む。Aから割り込んだ処理が、Aへ戻るとは限らない。Bを再開する場合にも、Aのstackと保存frameは、次のAの番まで残しておく。

本章のタスクは、カーネルと同じマシンモードで動き、トラップをネストさせない。実行を再開する仕組みに加えて、利用者の誤った書き込みからカーネルを守るには、アクセスを制限する仕組みも必要になる。

## 仕組みと方針を分ける

[スケジューラ](repo:src/kernel/scheduler.zig)は、レジスタやCLICのアドレスを知らない。タスクの状態、優先度、期限、現在の選択を管理する。状態の名前を見よう。

{{snippet:task-states}}

`ready`は実行候補、`running`は現在の実行対象である。`sleeping`には時刻の期限があり、`blocked`は通知など別の条件を待つ。`exited`は終了結果を保持している状態で、まだ枠の再利用を許していない。

{{figure:task-states}}

図は実行中のタスクが待ちに入り、候補へ戻る代表的な経路である。時刻を待つ`sleeping`と、対象eventを待つ`waiting`では、戻す条件が違う。どちらも条件が満たされた後は`ready`であり、その瞬間に実行を始めるとは限らない。終了と回収は後の図で分けて追う。

状態は、どこに置かれるのだろうか。[スケジューラ](repo:src/kernel/scheduler.zig)には固定長の`tasks`配列があり、[実行基盤](repo:src/arch/riscv32/task_runtime.zig)の`images`配列が、同じslotの保存frameやstack範囲を持つ。タスクの管理情報をまとめたものは、一般にTCB、プロセスの場合はPCBと呼ばれる。nihosでは、その役割を方針側の記録と機種側の実行イメージへ分けている。

{{figure:task-records}}

実行待ちのタスクを表すために、必ず連結リストを用意する必要はない。この実装では`tasks`を走査し、`ready`の要素から選ぶ。最大N個なら選択の走査はO(N)で、待ちに入るときはstateを変えて候補から外せる。優先度別のqueueや期限順のheapへ変える場合には、選択の費用に加え、登録・取消・二重登録を防ぐ仕事も比較したい。

同じ優先度の実行候補はラウンドロビンで選び、より優先度の高い候補があればそちらを選ぶ。ただし、PC上の選択方針のテストで選択が正しくても、実機の割込みが予定どおり入るとは限らない。選択方針と、それを呼ぶタイマー・トラップ・復帰処理を別々に検査する。

また、割込みの回数と経過時間は同じではない。割込みが遅れた場合にも、自由に進むハードウェアカウンタから経過したティックを求める。[時刻管理](repo:src/kernel/tick_clock.zig)と[タイマーの判断](repo:docs/adr/0007-native-preemption-and-elapsed-time.md)では、通知の回数を単に時刻として足し続ける方式との違いを追える。

## `sleep`していた関数は、どこへ戻るか

タスク側の`ecall`は、番号と引数を整数レジスタに置く。`sleep`が受理されると、選択方針は期限を登録し、そのタスクを候補から外す。[共通実行基盤](repo:src/arch/riscv32/task_runtime.zig)は、保存した`mepc`を4バイト進め、結果を保存フレームの戻り値レジスタへ書く。

期限が来て再び選ばれると、タスクは`ecall`の次の命令から続ける。待っている間も、呼び出し途中の局所変数や戻り先はそのタスクのスタックに残る。待機中のスタックを別の仕事へ貸してはいけない理由が、ここにある。

タスク呼び出しは、[番号とスカラ値の引数](repo:src/kernel/task_control.zig)を検査する小さなABIとして用意している。利用者ポインタも受け付ける場合には、指す領域の範囲・権限・寿命を検査する契約が必要になる。

## 終了しても、まだ自分のスタックにいる

タスクが最後の関数から戻ると、終了用の経路へ入る。ここでスタックをすぐ空き領域にしたら、終了処理そのものが使っている戻り先や保存値を、新しいタスクが上書きするかもしれない。

選択方針側の終了処理は、まず終了結果を残す。

{{snippet:task-exit}}

その後、実行を離れたタスクの資源を、所有CPUの割込み用またはカーネル側のスタックから回収する。実行基盤の入口は小さい。

{{snippet:task-reap}}

この関数は終了済みかを確認し、スケジューラの枠と対応する実行イメージの参照を外す。固定スタックやFPU領域を再利用する側は、別CPUや残ったフレームがまだそれらを使っていないことも確かめる。実行を管理する情報の回収と、その置き場所の再利用を分けて読むとよい。

{{figure:task-reap}}

図の`vacant`へ戻す操作と、実際のstackやI/O bufferを再利用できる条件は、同じ一操作とは限らない。タスクを止めたあともデバイスがbufferを使う場合は、{{ch:io-lifetime}}の回収条件が加わる。

タスクのハンドルにはスロットと世代番号がある。同じスロットに次のタスクが入っても、古い世代番号への`wake`は失敗する。名前の再利用と、同じ対象であり続けることを区別する仕組みである。世代番号の上限では、そのスロットを再び古い名前として生き返らせない。

## PC上で状態遷移を確かめる

リポジトリのルートで、次を実行する。

```sh
.tools/zig-0.17.0/zig test src/kernel/scheduler.zig
.tools/zig-0.17.0/zig test src/kernel/scheduler.zig \
  -O ReleaseSafe
```

まず`same-priority tasks run round robin`と`sleepers wake at their deadline without entering the run queue early`を読み、どの呼び出しで状態が変わるかを表にしよう。

次に、作業用コピーで同じ優先度の三タスクを用意し、一つだけ`sleep`させる小さなテストを追加する。期限前後の選択順を予想し、起きるまで選ばれないことと、起きた後に再び候補へ入ることを調べる。CPU速度や実時間は、このPC上の実験では測っていない。

最後に`exit and slot reuse discard notifications and reject stale senders`を追う。古いハンドルが新しいタスクを起こせたら、どの所有権の約束が壊れるか説明しよう。

設計を考える演習として、入力、検索、音の供給が同時に仕事を持つ場面を紙に描いてみよう。それぞれについて待てる時間と処理を続ける長さを仮置きし、検索の優先度だけを上げた場合に何が変わるかを予想する。数値は設計上の仮定であり、現在のnihosの実測値とは分けて記録する。

## 実行された切り替えの根拠を読む

[独立ネイティブ実行基盤の記録](repo:docs/measurements/2026-10-25-native-task-owners.md)では、ESP-EMU上で両CPUが300ラウンド進行し、自発的に`yield`しない二つの計算を続けるタスクが、それぞれタイマーに捕捉されている。`sleep`、終了、回収、世代番号を変えた枠の再利用も検査している。

タイマーがどのタスクを中断したかは、保存フレームと捕捉位置から調べる。進捗カウンタ、終了結果、再利用した枠も対応づけると、二つの計算が進んだ理由を追える。{{ch:psram-and-evidence}}では、同じ基本経路を実機で動かした結果も読む。

ESP-EMU環境を用意した場合の追加実験は次である。

```sh
sh tools/run-native-smoke.sh integer 0
```

出力先と環境は{{ch:native-entry}}の注意に従う。この起動試験は後続のIPIやメモリ検査まで含む。最初の完了表示だけで全体の成功とせず、最後のログと検査結果を確認する。

## 読み終えたら確かめること

関数呼び出しの保存規則だけでは割込みからの復帰に足りない理由、`sleep`中にもスタックが必要な理由、`exit`と`reap`を分ける理由を説明しよう。次の{{ch:messages-and-waits}}では、別のCPUから届いた仕事で、待っているタスクを再開する。
