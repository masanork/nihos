# おわりに

画面に一行の文字が現れるまでにも、起動、メモリ、割込み、実行状態の保存、表示回路との受け渡しがある。そこへ入力、無線、保存を加え、最後にカードを読む端末までつなぐと、どの処理を完了と呼ぶかという問いが何度も現れた。

空きメモリがあっても、大きな領域を確保できない。フォントのbyte数が足りても、管理枠やstackが足りない。タスクに順番が来ない。エミュレータで通っても、実機では別の前提が見つかる。方式の選択と、それを信頼するための確かめ方を、一緒に考える必要があった。

終了したタスクの領域も、借り手が残れば返せない。保存を知らせるなら、所在の情報まで残す。SQLiteがjournalから戻す世代と、ストアが公開する世代も異なる。小さいモデル、実際のライブラリ、実機の観測を比べることで、完了という約束の境界が具体的になった。

私は、小さな端末の上で、使うことと作ることがつながる環境を育てたいと思っている。表示や入力、保存の機能を足すたびに、CPUの時間とメモリの使い方にも新しい問いが生まれる。OSの設計は、最初に一度決めて終わる仕事ではない。

AIと一緒にコードを書くときにも、何を誰が持ち、いつ返すのかという問いは役に立つ。説明を聞き、予想を立て、自分の機械で試す。次は、気になった振る舞いを一つ選んでみよう。短いテストでも、一行の観察でもよい。予想と比べられる形にすると、その小さな変更が、機械を理解する次の足場になる。
