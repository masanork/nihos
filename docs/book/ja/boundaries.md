# 動く端末からOSを考える

画面へ色を塗れたとき、そのプログラムはOSを作ったと言えるだろうか。描画には、メモリ、ディスプレイの初期化、転送、割り込み、CPUの実行が関わる。自分が書いた部分と、既存ソフトウェアが引き受けた部分を分けてみると、この問いは具体的になる。

この章では、nihosの実行経路を読み、どの層が何を担うかを説明できるようになる。機能の数より、責任の境界に注目する。

## 起動したあとに誰が動いているか

nihosのESP-IDF側の経路では、SDKに起動処理とFreeRTOSの開始を任せ、C ABIを通してZigへ入る。別のnative経路では、ROMと第2段のブートローダを利用し、その先のスタックや変数、割り込みの準備をnihosが担当する。どちらの経路で観察したかを、実験の条件に含める。

ABIとは、関数の呼出しやデータ配置について、異なる言語のコードが共有する約束である。ESP-IDF側からZigへ渡す型には、SDK内部の構造体を含めない。

ESP-IDF側の起動時に渡す情報の型を見よう。native経路の最初の入口が、この構造体を受け取るという意味ではない。

{{snippet:boot-info}}

`u32` は32ビットの符号なし整数で、`extern struct` はC ABIに従う構造体を表す。CPUの個数やメモリ量という事実を渡し、SDKの管理オブジェクトは渡していない。こうしておけば、将来SDKを呼ぶ箇所が変わっても、カーネルの判断に必要な情報を保ちやすい。

ただし、型を分けるだけで既存OSから独立するわけではない。誰がスタックを用意し、CPUへ仕事を割り当て、割り込みから戻すかを調べる必要がある。

## 責任を表にする

二つの経路を、担当する仕事で比べよう。native側は[起動の記録](repo:docs/native-boot.md)、周辺機器の比較用実装は[設計文書](repo:docs/architecture.md)を併せて読む。

| 仕事 | ESP-IDF側の経路 | 独立したnative経路 |
| --- | --- | --- |
| ROMと第2段のローダ | ベンダーの起動処理を利用 | 同じくベンダーの起動処理を利用 |
| アプリ側の初期化 | SDKが準備してZigへ入る | nihosがスタック、変数、trap入口を用意 |
| タスクと割り込み | 基盤はFreeRTOS。限定区間でnative動作を比較 | 両CPUのnative runtimeをエミュレータで検査 |
| 表示とtouch | BSPとESP-IDFで初期化し、Zigから使う | そのまま接続済みとは扱わない |
| データ構造と選択方針 | 共通のZig実装をhostでも検査 | 共通部分を利用し、native側の接続を別に検査 |

この表には、完成を待たずに学べるものがある。既存の実装を比較対象にして、一度に引き受ける責任を小さくする進め方だ。nihosでは、このESP-IDF側の実装をbring-upの比較基準として使う。

一方、ESP-IDF側での物理Tab5測定や、独立nativeイメージのエミュレータ検査から、nativeの表示や入力が実機で完成したとは判断できない。新しい経路へ責任を移すたびに、割り込み、復帰状態、待機、周辺I/Oをその経路で確かめる必要がある。{{ch:native-entry}}では、その入口となる初期化を読む。

## 一般原理と機種固有の事情

仕事の切替、資源の所有権、待ち行列は、多くのOSに現れる。ESP32-P4の割り込みコントローラや、Tab5のパネル初期化は、その実現方法の一つである。本文では両者を結びつけて説明し、別のCPUへも持ち出せる考え方を残したい。

RISC-Vという名前だけで、同じ実装が動くわけでもない。xv6のページテーブルを学ぶ環境と、P4の起動・メモリマッピング・割り込みの環境は異なる。共通の命令セット、CPUが提供する機構、ボードの配線を順に分けて読む習慣が役立つ。

## 手を動かす前の確認

1. 起動直後にZigの関数が呼ばれたとして、その前に誰が用意した資源があるか、三つ挙げよう。
2. `BootInfo` にSDK内部のポインタを入れた場合、どのような変更がカーネルへ波及するか考えよう。
3. 「表示できた」ことを、初期化、バッファへの書込み、転送、物理的な見た目に分けると、それぞれ何を観察する必要があるだろうか。
