# 一段落の日本語を組み立てる

「が、空を見た。」を小さな画面へ表示したい。最初の「が」は、かなの「か」と結合濁点を別々に保存していても、一まとまりとして扱いたい。句読点が行の先頭へ押し出されるのも避けたい。文書から画素までの途中には、文字を並べるための判断がある。

## 保存する位置と、見える一文字

UTF-8ではデータはバイト列だが、日本語の一文字は複数バイトになる。最初の「か」と結合濁点はそれぞれ3バイト、合わせて6バイトである。途中を削れば不正な文字列になる。さらに、二つの符号位置を別々に消すと、利用者が見た一文字と編集操作が合わない。

そこで対応する符号の組を、移動や削除の単位として扱う。これを書記素クラスタという。nihosの対応は結合濁点、異体字セレクタ、ZWJなどに対する限定した規則であり、Unicodeの書記素境界の完全な実装を意味しない。文書の位置は画面の行列ではなく、元のUTF-8列と対応づける。行の幅や文字サイズを変えても、同じ位置から表示を組み直すためだ。

## 文字から字形と送りを決める

フォントは文字を表示する形、glyphを持つ。同じ文字にも書体や異体字による違いがあり、一つの文字と一つのglyphが常に一対一とは限らない。字形の幅だけで次の文字の位置を決めず、次の配置へ進む距離を送り幅、advanceとして扱う。字形の見える範囲が送り幅からはみ出すこともある。

一般的なshapingは、文字列、方向、フォントの規則を使ってglyphの並びと位置を決める。{{ch:japanese-fonts}}ではHarfBuzzとFreeTypeを使った別の実験を扱う。対して本章のXYは、対応するTrueType字形と限定した組版を独自に処理する。両者が同じ言語やOpenType機能を備えるとは限らない。

## 行を分け、ルビを置く

横幅に一行の文字をすべて置けなければ、次の行へ送る。単純に幅を超えた位置で切ると、句読点の「、」が行頭へ来る場合がある。そこで行頭や行末に置けない文字を考慮し、前後の位置を調整する。これを禁則処理という。どの禁則まで扱うかは実装の規則とテストで確認する。

たとえば「空」に「そら」という読みを付けるとき、本文の文字とルビの文字を混ぜて保存する必要はない。本文の範囲と対応する読みを別に持ち、本文の配置に合わせて小さな文字を置く。一つの語にまとめてルビを付ける場合、改行位置がその範囲を横切るときの扱いも必要になる。単に小さな文字を描けるだけでは、対応と配置を含むルビ組版の証拠にはならない。

縦書きでは行の進む向きと行内の進む向きが変わる。横書きの座標を全体ごと回転すれば必ず正しいわけではない。句読点や英字の向き、送り、読みの置き場所を考える必要がある。後の読書画面では、設定を変えたとき現在のページ先頭のUTF-8位置から組み直す。対応する文字や禁則は実装と版により限りがある。

## 配置を画素へ変える

組版の結果は、どのglyphをどこに置くかという配置の列、Display Listになる。座標と送りには1/64画素を一単位とする固定小数点を使い、画素に落とす前の端数を保持する。出力先の配列にも上限があるため、全文書を一度に無制限に展開できるわけではない。

次にフォントの輪郭を読み、サイズに応じたmaskを作る。これを文字色と合成してRGB565の画素へ書く。輪郭のcacheと、サイズや向きに応じたmaskのcacheは別のものだ。どちらを保持するかで媒体の読取り、メモリ使用量、再描画の費用が変わる。

Macとnativeで同じ組版・描画を通し、向きを揃えた画素を比べた[統合試験](git:9208c4edad1c78eb3e2f5942a530fb67979fa675:docs/measurements/2026-10-31-xy-native-pixel-landing.md)がある。ただし両者に共通する誤りは一致する。画素の一致に加え、独立の期待値、禁則やルビの例、実機での見え方を別に調べる。

## 手で確かめる

冒頭の文で「か」と濁点の間をカーソルの停止位置にすると何が起きるか考えよう。次に幅を狭め、「、」が行頭に来るときの調整を紙に描く。「空」にルビを付け、表示方向と文字サイズを変えたとき、文書のどの情報を保ち、どの配置を計算し直すかを書き出す。
