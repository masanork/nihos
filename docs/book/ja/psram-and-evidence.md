# 使えるメモリになるまで

基板に32 MiBのPSRAMが載っている。PSRAMは、CPUのチップ内部ではなく外部に置かれ、作業用データを保持するメモリである。では、起動直後にそのアドレスへ配列を書いてよいだろうか。

{{ch:machine-basics}}で学んだ番地とキャッシュの見方を使い、この章では、識別、読書き、マッピング、キャッシュ、割当を分け、外部メモリがOSの資源になるまでを追う。エミュレータで通った実装を実機へ持ち込むと、何が見つかるだろうか。実習ではPC上のコントローラとキャッシュのモデルを調べる。

## メモリの表へ載る前の仕事

OSの図では、メモリが最初から一つの使える領域として描かれることがある。これは、タスクや割当方針を考えるときには便利な抽象である。実機を起動すると、その図に領域を載せてよいかを判断する仕事も現れる。

本章では、同じメモリを、コマンドによる読書き、CPUのアドレス変換、キャッシュを介したアクセスという複数の経路から調べる。一つの経路で正しかった値を、別の経路でも見られるかが問いになる。{{ch:bounded-memory}}で渡したバイト列を、基板のどこから得るのかへ戻る章でもある。

もし最初からすべてを使えると仮定すれば、その後の不具合は割当器やアプリケーションの問題に見えるかもしれない。利用を許す段階を記録しておくと、どの前提まで確かめたかを追える。小さなOSを作る面白さの一つは、普段は前提として受け取る資源の準備まで見に行けることだ。

## 容量を知ることと、利用を許すこと

PSRAMはCPU内部のSRAMと違い、外部との通信、電源、動作モード、コントローラの設定を必要とする。容量を示すレジスタが読めても、CPUのload/storeやDMAで使えることまで確認できたわけではない。

nihosの検証は次の段階に分かれている。

| 段階 | 確かめること |
| --- | --- |
| 供給と識別 | 電源の設定、待ち、モードレジスタの反復読み取り、ベンダーと容量 |
| コマンドでの読書き | 対象モード、範囲、異なるアドレスへのパターンと読み戻し |
| CPUからのマッピング | PTEの設定、仮想と物理が異なるアドレス変換、予約領域と利用領域 |
| キャッシュの受け渡し | CPUとコマンド側、CPU間で必要な書戻しと無効化 |
| 割当への登録 | 所有者、ガード、管理情報を除いた容量、再利用と完全回収 |

各段階に失敗した場合は、次の段階へ利用可能な領域を公開しない。識別値から計算した容量だけで割当器へ登録しないことが、誤ったメモリを利用者へ渡さないための条件になる。

## 終わらないコマンドから戻る

[PSRAMコントローラ](repo:src/soc/esp32p4/psram.zig)は、単一所有者がCPU1の開始前に使う。コマンドの完了を調べる回数に上限を設け、完了しなければタイムアウトを返す。

タイムアウト後には、単に同じ要求をもう一度出さない。コントローラの状態が不明になったため異常状態として扱い、ハードウェアリセットまで再利用しない。前の操作がまだ動いているのに次の設定を書けば、どちらの結果か判別できなくなるからだ。

受信用FIFOも、開始前に目印の値へ書き換える。古い値が残っただけなのに「デバイスが存在しないという応答を読めた」と誤解しない工夫である。PC上のモデルは、完了遅延、停止したコマンド、古いFIFO、変化する識別値を注入して検査する。

## 平らなRAMではマッピングを検証できない

すべてのアドレスが同じ位置のRAMへ通るモデルでは、MMU設定が無視されていても読み戻しが成功するかもしれない。nihosは、最初・中央・最後の物理ページを別の仮想窓へ置き、仮想と物理のアドレスが異なる変換を含めて確認する。

[マッピングのモデル](repo:src/soc/esp32p4/psram_mapping_test.zig)は、物理メモリとCPUキャッシュの内容も分けている。書戻しを省けばCPUが書いた値はコマンド側へ届かず、無効化を省けばコマンド側の変更をCPUが見逃す。その操作を意図的に欠落させ、検査が失敗することまで確かめる。

ここで扱うMMUは外部メモリのマッピングである。xv6の仮想プロセス空間やページ単位の保護と、同じ仕組みが実現できたという意味ではない。{{ch:process-isolation}}で追加したPMPも、アドレスの変換先を切り替えず、範囲のアクセス権を調べる。外部メモリのmapping、物理領域の配分、タスクの保護という三つの判断を重ねて考えよう。

キャッシュの操作には、公式の低水準実装が使うROM APIを境界として利用する。直接のレジスタ設定がエミュレータの読み戻し検査で失敗した経緯も、マッピングの記録に残っている。ROM関数内の待ちにはnihos側のタイムアウトがなく、コマンドのポーリング回数に上限を設けたことだけで、起動処理全体の待ち時間が制限されたとは言えない。

全容量のマッピングでは、物理ページが重複しないことも調べる。二つの仮想ページが同じ物理ページへ誤って対応していれば、片方の割当がもう片方を書き換える。[全容量マッピングの記録](repo:docs/measurements/2026-10-26-native-external-arenas.md)は、ページの対応と外部アリーナの公開を分けている。

## エミュレータで通った段階

[識別](repo:docs/measurements/2026-10-26-native-psram-discovery.md)、[コマンド読書き](repo:docs/measurements/2026-10-26-native-psram-command-data.md)、[マッピングとキャッシュ](repo:docs/measurements/2026-10-26-native-psram-mapping.md)、[再利用ヒープ](repo:docs/measurements/2026-10-26-native-reusable-heaps.md)には、それぞれ対象ソースと生成物のハッシュ、試験条件、残る検証がある。

エミュレータではPSRAMなしと4、8、16、32、64 MiBの条件を使う。compiled-FPを含む条件も分ける。これらの結果から、電圧、信号のタイミング、保持時間、実機の帯域、DMAの動作までは判断できない。

## 実機では識別で止まった

[最初の実機試験](git:378ead82fb9f1a2fe1d49d68818f4458ef1355c6:docs/measurements/2026-10-26-tab5-native-sqlite-physical.md)では、起動とタスク切り替えが進んだあと、PSRAMの識別で止まった。外部ヒープとSQLiteも組み込んだイメージだったが、そこへ制御を進める前に失敗が見つかったのである。

対象はESP32-P4リビジョン1.3のTab5で、同じ固定イメージをUSB RTSで3回リセットした。電源断起動ではない。観測を整理すると、次のようになる。

| 項目 | 3回の起動結果 |
| --- | --- |
| 独立ネイティブ起動、CRT、例外復帰 | 全回到達 |
| 両CPUのタスク・タイマー | 全回300ラウンド進行 |
| `sleep`、`exit`、回収、枠の再利用 | 両CPUの記録あり |
| IPIとWFI | 全回64交換。周期タイマーによる救済なし |
| PSRAM識別 | 全回、設定値と識別値がともに`0x8d30`。未対応と判定、容量0 |
| PSRAMマッピング、外部ヒープ、SQLite | 識別失敗により未実行 |

供給レジスタの設定と待ちを終えたことは記録されていた。しかし、実電圧が適切であることを測定したわけではない。異なるモードレジスタの組が同じ値を返すため、まずアドレス送出やモードの設定を疑うことにした。この段階のログだけでハードウェア故障と断定しなかったことが、次の切分けにつながる。

失敗した版と修正版のソース、イメージ、実行ログは、それぞれ区別して保存する。参照版の対応は[付録](practice-notes.md)に記した。

## 成功という単語を検索するだけでは足りない

実機ログには`NIHOS_NATIVE_FP_PASS floating=0`という完了表示も出る。しかしPSRAMとSQLiteの合格ではない。厳密な判定器は、識別と利用領域の公開が不完全であるとして全3回を不合格にした。

起動、スケジューラ、IPIまで通ったという情報は残しながら、試験全体は不合格にできる。途中の成功も最後の失敗も、次に調べる境界を絞るために必要である。

識別に失敗したので、外部ヒープとSQLiteの処理は実行していない。最後に出た成功表示だけでなく、各段階の結果を読む必要がある。

## 一つ直すと、次の境界が見えた

その後の[修正と実機記録](git:960bb1056252aaf6193d8d66350a27e63259d26d:docs/measurements/2026-10-26-tab5-native-psram-fix.md)は、この失敗を解消するまでを残している。最初の原因は、MSPI3で4バイトアドレスを有効にする設定の欠落だった。アドレスのビット数だけを指定しても、その送出を有効にする有効化ビットが別に必要だったのである。

この設定を加えると、識別値と容量が読め、コマンドによる読書きも通った。しかし、まだ割当器へ渡せる状態ではなかった。CPUが中間ページへ書いた値をコマンド側で読むと一致しない。識別の修正によって、今度はキャッシュの受け渡しが検査できるようになった。

キャッシュの同期対象をL2だけから、共有L1データキャッシュとL2キャッシュへ広げると、仮想と物理のアドレスが異なるマッピングの双方向検査とCPU間転送が通った。一つの設定変更ですべてを直したとまとめず、識別、コマンドによる入出力、CPUとコマンドの受け渡しを分けたことが役に立った。

| 修正の段階 | 次に進めた段階 | 残った結果 |
| --- | --- | --- |
| 最初の実装 | ネイティブ起動とCPUの基本経路 | PSRAMの識別で停止 |
| 4バイトアドレスの有効化ビットを追加 | 32 MiBの識別、コマンド読書き | CPUとコマンドの値が不一致 |
| L1データも同期する修正版 | マッピング、CPU間転送、外部ヒープ | SQLiteの実行まで到達 |

PC上のモデルが通っていても、実機の設定をすべて表せているとは限らない。有効化ビットの欠落を再び作ると失敗する回帰テストも追加した。実機で見つけた前提を、次回のPC上の検査へ持ち帰る。

## 修正版で使えるようになった範囲

修正版の同じイメージを、同じTab5で3回USB RTSによるリセットした。各起動で32 MiBの識別、コマンドによる入出力、マッピングとキャッシュ、64ラウンドのCPU間転送、外部ヒープの回収まで通った。SQLiteも各2セッション・26文を実行し、その前後の外部ヒープの空きは16,022,848バイトで一致した。

ログを判定する側にも、実機とエミュレータで異なる内部SRAM範囲を反映した。PSRAMの失敗時には処理を止める。試験の対象を正しく読む仕事も、実装の検査と組になっている。

この試験はUSB経由のリセットによる3起動である。電源断からの起動や温度・周波数を変えた動作、DMAとの接続は、それぞれ別の条件で調べる。識別からSQLまで進めた土台を使い、{{ch:c-library}}では割当器とライブラリの寿命を考える。

## PCでモデルの前提を調べる

リポジトリのルートで実行する。

```sh
.tools/zig-0.17.0/zig test src/soc/esp32p4/psram.zig
.tools/zig-0.17.0/zig test \
  src/soc/esp32p4/psram_mapping.zig
.tools/zig-0.17.0/zig test src/soc/esp32p4/psram_test.zig
.tools/zig-0.17.0/zig test \
  src/soc/esp32p4/psram_mapping_test.zig
```

コントローラのタイムアウトや不正な応答、マッピングやキャッシュ操作の欠落を、どのテストが注入するか調べよう。これらはPC上のレジスタ・状態モデルであり、実際の端子や電源を操作しない。

条件変更の演習では、作業用コピーでキャッシュ同期の失敗注入を一つ選び、失敗時にマッピングを取り消すところまでを追う。成功値を固定して通すのではなく、「どの故障がどの検査に捕まるか」を表にする。

ESP-EMU環境を用意した場合は、追加で`sh tools/run-native-smoke.sh integer 32M`を実行できる。現在のエミュレータが対応する容量と、要求した容量を検査結果で確認する。電気的な条件を調べる試験へ進むときは、別の実機手順が必要である。

## 読み終えたら確かめること

識別できた容量をすぐ割当器へ渡してはいけない理由、仮想と物理のアドレスが等しいマッピングだけでは検出しにくい誤り、キャッシュのモデルと実機測定の違いを説明しよう。最後に、自分の実験で「通った段階」「まだ実行していない段階」「次に切り分ける境界」を三行で書いてみよう。
