# 重い計算をOSサービスにする

署名を一回検証できた。では、その処理を画面や通信と同時に使えるOSのサービスへしてよいだろうか。計算結果が正しくても、入力が途中で変わり、取消した仕事のメモリを先に返し、失敗した結果に前回の成功が残れば、サービスとしては安全でない。

この章では、耐量子暗号と呼ばれる新しい方式のうち、ML-DSA-65の署名検証とML-KEM-768の鍵共有処理を使った実験を読む。暗号方式そのものを実装する章ではない。既存のC実装が必要とする長い計算、大きい作業領域、入力の寿命を、OSがどう囲うかを考える。

対象は独立ブランチ上の実験であり、製品機能ではない。固定された公開テストデータをホストとESP-EMUで実行し、通常構成へのリンクを調べた。Tab5実機、実乱数、実秘密鍵、通常UIとの共存、更新の許可や製品セキュリティは確認していない。

{{ch:process-isolation}}で導入したCPUのアクセス制限と、この章の資源の扱いは区別する。このPQCワーカーをU-modeへ移した結果ではない。また、回収できない領域を再配布せず残す「隔離」と、別タスクからのCPUアクセスを拒否する保護境界は、同じ操作ではない。両方が必要になった場合も、一方の成立から他方を推定しない。

## 計算できることと、依頼を扱えること

ML-DSAの検証は、公開鍵、署名、文脈、メッセージを受け取り、数学的に正しいかを返す。正しい署名であることは、その鍵をOSが信頼することや、署名されたファームウェアの導入を許可することと同じではない。鍵の用途、更新、失効、rollback防止は上位の方針である。

ML-KEMも、固定データで鍵生成、カプセル化、デカプセル化が通ることから、相手を認証できたとは言えない。改変した暗号文のデカプセル化がAPI上の成功を返し、元と異なる共有秘密を作る場合もある。戻り値だけで相手との鍵一致を判断せず、認証と鍵確認を別に設計する。

OSサービスの最初の問いは、暗号の名前ではなく、誰が入力と作業領域を持ち、いつ結果を公開するかである。実験では、一度に一つの仕事を受ける専用ワーカーを使った。無制限の待ち行列は作らず、満杯なら明示的に拒否する。

## 入力をワーカーの寿命へ移す

呼出し元が渡したポインタを、計算が終わるまでそのまま保持してはいけない。呼出し元が終了したり、同じ領域を書き換えたりするかもしれないからだ。実験では、公開鍵1,952バイト、署名3,309バイト、文脈最大255バイト、メッセージ最大4,096バイトを、一つの9,612バイトのスナップショットへコピーした。

コピー後に元のメッセージを変える試験では、ワーカーはコピー済みの内容を検証した。これで分かるのは、コピー後の変更から独立したことまでである。コピーの途中に別CPUが書けば、新旧のbyteが混ざる可能性が残る。

そこで別の有限実験では、協調する書き手が変更前後に世代カウンタを更新し、ワーカーがコピーの前後で値を比べた。途中で変更した決め打ちの順序では、検証を始める前に拒否できた。しかし、すべての書き手が規則へ従うこと、CPU間の公開順序、カウンタの周回、任意のタイミングを証明したものではない。実サービスでは、呼出し元が変更できない領域を渡すか、OSが所有する領域へ安全にコピーする境界が必要になる。

## 取消しても、Cの処理は止まっていない

同期的なC関数の途中で取消しを受けても、その時点でstackやarenaを解放してはならない。C側はまだそこを読んでいる。最初の契約では、取消しは「結果を捨てる」と記録し、関数が戻るまで待つ。その後で入力、作業領域、タスクの台帳を片づける。

{{figure:pqc-worker-lifecycle}}

図の`破棄待ち`は強制終了ではない。ワーカーが停止したことを確認する前に領域を返すと、別の仕事が再利用したbyteを古い計算が読む。これは{{ch:io-lifetime}}で、取消しの通知とDMA停止を分けたのと同じ問題である。

## 必要量を、同じ時点で数える

ヘッドレスのRV32エミュレータ実験では、8,192バイトの内部SRAM stackを一つ予約し、二つの処理が順番に再利用した。観測値は次の通りである。

| 処理 | 観測したstack使用 | PSRAMの主な課金 |
| --- | ---: | ---: |
| ML-DSA-65検証 | 2,896 B | arena 16,384 B |
| ML-KEM-768 | 最大4,912 B | arena 32,768 BとI/O 8,192 B |
| 入力をコピーしたML-DSA | 2,896 B | 呼出し元、snapshot、arenaの合計49,152 B |

二つの暗号処理は同時実行していないので、40,960バイトというML-KEM側の最大課金へML-DSAの値を足さない。逆に、入力コピーの試験では三つの領域が同時に存在するため、arenaだけをサービスの必要量としてはいけない。stackの観測値も、固定入力とその実行順で塗り替えられた範囲であり、最大値の保証ではない。

通常の画面、通信、デバイスを含む構成へのリンク比較では、暗号を無効にしたときのSRAM上のheap範囲が62,848バイト、二方式のAPI入口を残した試験構成が58,112バイトだった。ここへ8,192バイトのワーカーstackだけを差し引くと、既存の49,152バイト下限を768バイト上回る。しかし要求表、結果、整列、実際のワーカーコードは含まれない。この算数を「サービスが入った」と読み替えてはいけない。

## 失敗した仕事の結果を初期化する

資源不足は、計算を始める前にも起きる。実験では、直前の仕事を成功させた後、次の仕事の最初のスナップショット確保を故意に失敗させた。結果構造体を仕事の開始時に初期化する候補は、利用不能という状態とゼロの付随値を返した。

初期化だけを削った負の対照では、失敗した二件目に、一件目の`valid=1`と測定値が残った。暗号計算は実行されていない。それでも結果を受け取る側が状態と値を別々に読めば、古い成功を現在の成功と誤解し得る。

ここで重要なのは、テスト用の不変条件である。成功以外の状態では、妥当性と計測値をゼロにする。さらにjobの世代と結果を対応づけ、古いjob識別子を拒否する。エラーを返すことと、公開する結果全体がそのエラーに対応していることを分けて検査する。

## 返せなかった資源を隠さない

別の負の実験では、ワーカーがarenaを台帳へ残したまま終了し、違う所有者として解放を試みた。割当器は`WrongOwner`を返し、台帳は記録を捨てず、タスクを`faulted`へ移した。16,384バイトは空きへ戻らず、同じslotの再利用、回収、代わりのワーカー起動も拒否された。

この状態を隔離と呼ぶ。回収に失敗したのに帳簿だけを空にすると、まだ使用中かもしれない領域を再配布するからだ。ただし実験は、隔離した後に通常処理を続けられる製品機構を実装したものではない。通常の回収経路は同じ失敗でCPU0を停止する。隔離からの復旧、reset、電源断後の扱いは残っている。

## SRAMからFlashへ移せば終わりではない

二方式のコードと定数をすべてSRAMへ置くと、heap下限を満たせなかった。試験用のヘッドレス構成では、実行コードと読取り専用データをFlashへ置くことで、二つの処理を同じイメージから順に実行できた。

通常構成では、既存の二つのFlash領域へ全部を置くと容量を超えた。試験データを除き、一部の関数をSRAMへ戻した構成はリンクできたが、Flash実行領域の残りは302バイトだった。コンパイラや機能の小さな変更でも越え得る値である。

さらに、Flashの消去や書込み中は、そこから命令や定数を読めない時間がある。両CPUとDMAを止める協調機構がなければ、Flashへ移したコードを更新処理自身が実行する危険がある。配置を変える判断には、容量、実行中の利用者、cacheを無効にする順序を含める。

## 実験の層を読み分ける

[PQC実験報告](git:90d0a9e8b8c1758e31751fac39ea89634127ca80:docs/reports/2026-10-29-pqc-implementation-report.md)は、ホスト、RV32エミュレータ、通常構成のリンクを分けている。実装されたのは試験用ワーカーとfixtureであり、通常UIから呼べるサービスではない。

| 層 | この実験で確認したこと | 確認していないこと |
| --- | --- | --- |
| ホスト | 既知入力、失敗注入、サービス状態の有限モデル | RV32 stack、実機のcacheや時間 |
| ESP-EMU | RV32命令、固定入力、arena・stackの観測、負の候補 | Tab5の応答、物理PSRAM、電源 |
| 通常構成のbuild | コードと定数の配置、リンク上のSRAM範囲 | 実行中の空き、UIや通信との共存 |
| Tab5実機 | 未実施 | 動作、性能、長時間、電源断、秘密の扱い |

この区別を残したまま、ライフサイクルの小さいモデルをPCで動かす。

```sh
git worktree add --detach ../nihos-book-pqc \
  90d0a9e8b8c1758e31751fac39ea89634127ca80
cd ../nihos-book-pqc
sh tools/bootstrap-zig.sh
.tools/zig-0.17.0/zig test probes/pqc/service_model.zig
```

このモデルは、受付、取消し、完了、回収、世代の再利用を直列化して調べる。暗号の正しさ、データ競合、実際のスケジューリング、cache、物理消去を表してはいない。取消し後の完了を一つ加え、結果を公開すべきか、どの状態から領域を再利用してよいかを予想しよう。

重い計算をサービスへするとは、計算関数を別タスクから呼ぶことではない。入力を固定し、有限の資源を先に確保し、取消し後も利用者が消えるまで待ち、失敗した結果を初期化し、返せなかった資源を隔離する。その全体が成立して初めて、利用者へ一つの機能として見せられる。次の{{ch:sqlite-persistence}}では、同じ所有と失敗の問いを、計算中のメモリから保存中のデータへ広げる。
