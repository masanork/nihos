# 通読順と説明のレビュー

対象: 2026年10月28日のローカル原稿、序章・全24章・はじめに・付録。Cの関数・ポインタ・構造体を知り、OSやTab5固有の知識はこれから学ぶ読者を想定する。各章の構成と本文の主要箇所を通読順に点検した編集提案。全段落の初出を一つずつ確認した校閲ではないであり、動作検証や外部資料の事実確認の代わりではない。章や実装を増やす決定ではない。

## 判断

実装の失敗、修正、確認できた範囲を区別する材料は豊富だが、今の順序は教科書として滑らかではない。機械の全体像を持つ前に製品名や実装経路が現れ、初出の略語を後の章で説明する。初歩の概念と高度な事例を一章の中で往復するところもある。とくに最近加えた四章は短く、問いは明確だが、既存の長い章との接続と用語の導入が不足している。

修正単位は略語の展開だけではない。読者が「何をしたいか」「なぜ困るか」「どの情報を持って何をするか」を先に理解してから、名前、コード、検証記録へ進む。将来の章を予告することは構わないが、その章を既読であることを前提にしない。

## 提案する通読順

番号は仮。現在の各章を一度に分割せず、まず章の移動と冒頭の橋渡しで試す。

1. **入口**: 序章 → 動く端末からOSを考える → 最初の実験を再現する。Tab5・P4・C6・nihosを紹介し、比較の二経路と実験の種類を具体例で示す。言語の歴史は興味のある読者が選べる後半へ移す。
2. **起動と実行**: Zigで書かれたカーネルが動き始めるまで → 割り込まれたプログラムを再開する → タスクを管理する表と実行待ち → スケジューラは公平か。起動の前に必要なスタック・レジスタ・例外の最小限を短く補う。
3. **共有とメモリ**: 有限のメモリを誰が持つか → メモリを返して使い直す → 別のCPUへ仕事を渡して待つ → 使えるメモリになるまで。アリーナと個別解放を続けて学び、共有と通知を説明してから外部メモリの機種固有の経路に進む。CPUごとの所有を先取りする箇所は短く導入する。
4. **I/Oと端末**: タスクが終わっても、仕事は終わらない（一般的な要求・完了・取消の前半を先に）→ 文字が画面に現れるまで → 画面を切り替えるとき → 日本語フォント → 通信相手は、別の計算機 → 複数のデバイスを同時に使う。長いI/O章のFatFs・音声などは該当事例へ移すか後半の発展節とする。
5. **ファイルと保存**: 名前から保存ブロックまで → 保存できた、と言ってよいのはいつか → 20バイト直すために → 既存のCライブラリを迎える → SQLiteの保存を成立させる。Cライブラリ章で必要なABIの要点を先に置き、浮動小数点の詳細への依存を外す。
6. **統合と発展**: ICカード端末 → 浮動小数点の状態と言語の境界 → OSを何で書くか。言語選択やFPUは基礎経路に置かなくても価値がある。最後に読めば、それまでの具体例に戻って比較できる。

この案の利点は、一般的なI/Oとファイルの説明を個別のデバイス・SQLiteに先行させること。移動後は各章末の「次の章」も更新する。章順だけでは同期、保護、一般的なファイル配置の説明不足は解消しないので、下記の補足を併せて行う。

## 実際の書き換え例: 第1章

現行は「nihosのESP-IDF側の経路では」から始まる。比較対象の存在を、比較する理由より前に読者へ要求している。次のように、機械と二つの実行経路を先に置ける。

> 本書で使うTab5は、画面やタッチ入力を備えた小さな端末である。中心のESP32-P4というチップが、プログラムを実行し、メモリや画面を扱う。nihosは、この端末の上で仕事や資源を管理するために育てているOSである。
>
> 電源を入れた直後から、私たちのプログラムがすべてを動かすわけではない。チップに用意された起動処理が始まり、その後に別のプログラムを読み込む。nihosでは、その後の仕事を誰が担うかを二つの経路で比べる。
>
> 一つは、チップのメーカーが提供する開発基盤ESP-IDFを使う経路だ。ESP-IDFには周辺機器を扱うための部品があり、仕事の実行管理にはFreeRTOSという小さなOSを利用する。もう一つは、起動用の部品を利用した後、タスクや割込みの管理をnihos側で引き受けるネイティブ経路である。どちらも既存の部品を利用するが、担当する範囲が違う。

この後に二経路の図と比較表を置き、CとZigの境界を説明してからABIを導入する。正確な実装範囲は改稿時に固定版のソースと照合する。

## 優先順位と受入条件

1. **入口の修復**: 序章、第1章、最初の実験。Tab5の構成と二経路を説明でき、初出の略語を追えること。
2. **通読経路**: I/Oとファイルの基礎を事例より前へ移し、章末の「次章」・相互参照・目次を更新。後の章への参照は予告と分かること。
3. **四つの新章**: 一つの具体例、状態の図または表、用語導入、演習の予想と解答の要点を揃える。
4. **残る章の語彙と密度**: 各章の初出用語を確認し、実装名・一般原理・検証結果を分離。前提を複数同時に導入する段落を分割。
5. **読者検証**: OS初学者が目次順に読み、各章で「何を、誰が、いつまで持つか」を説明できるか確認。実習のコマンドと固定版の参照を実行し、PDF/Webの章番号とリンクを検査する。

とくに、教科書として不足する同期・デッドロック、アドレス空間と保護、ファイルシステムの基本構造は、章順変更だけでは埋まらない。別の基礎単元にするか既存章に組み込むかは、[シラバスの分析](syllabus-fit-gap.md)と合わせて決める。

## 2026年10月30日: 出発点とM5StackのOS環境

著者の訂正を受け、開発動機を後から技術的に正当化する構成を改めた。MeOSを面白がって拡張し、自分の好きな設計で作りたくなった出発点、作り始めた後に知ったFreeRTOSのSMPや他のOS、現在のSMP・保存の問いを分けた。

第1章の責任分担の後に「M5Stackで動くOSとアプリ環境を見渡す」を置く。カーネル、SDK、ランタイム、ランチャーを先に導入し、各プロジェクトを説明してから、起動する単位と権限の比較へ進む。MeOS/NuttX/Tactilityを中心に、Zephyr、tab5-os、MicroHydra、UIFlow、M5Launcher、Stamp-P4向けNOMMU Linux、Tab5のMacintoshエミュレータを扱う。対応機種と確認版を明記し、外部プロジェクトの実機検証や安全性監査とは扱わない。

保護タスクの章はメモ帳と検索の例からプロセス・スレッド・資源権限を比較する。CPU間通信の章はSMPと共有状態、接続の単一所有者、操作の応答を測る条件を説明する。SQLiteの章ではWAL/保存基盤統合の構想と、本章のPERSISTによるホスト検証を分ける。追加の実装や実機測定は行わず、既存証拠の範囲を維持する。
